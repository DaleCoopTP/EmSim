# Инструкции для агентов EmSim

Этот файл относится ко всему репозиторию. Он описывает текущую архитектуру, порядок работы и особые правила для тренажёра оператора 112. Перед изменением конкретного участка сверяйте его с кодом и действующими контрактами: планы содержат и уже выполненные, и будущие срезы.

## Проект и источники решений

EmSim — автономный тренажёр для диспетчера ДДС и оператора 112. Это модульный Go-монолит: один бинарник `emsim` с командами `migrate`, `api`, `worker`, `bootstrap-admin`, `import`; PostgreSQL 16 хранит данные и долговечную очередь задач. React/TypeScript SPA в `web/` собирается и раздаётся API. В `seed/` лежат учебные сценарии и медиа.

При расхождении документов используйте такой порядок:

1. Текущее требование пользователя и уже принятые в разговоре уточнения.
2. Новые принятые ADR, изменяющие старые решения; для первого вызова 112 — `design-docs/adr/021-operator112-first-intake-slice.md`.
3. Для очередности и состава режима 112 — `slice-planning-112.md` и детальный `slice-112-1-plan.md`. Они заменяют старое требование закончить ДДС до начала 112 из `slice-planning.md`, ADR-015 и `CLAUDE.md`.
4. `design-docs/rfc-001-emsim.md`, актуальные схемы и OpenAPI в `design-docs/contracts/`, затем `slice-planning.md` для работ ДДС.
5. `README.md`, `web/README.md`, `seed/README.md` — запуск и текущее пользовательское поведение. `docs/` и исходные PDF/XLSX — контекст и материалы заказчика, а не доказательство того, что функция уже реализована.

Если документ противоречит исполняемому коду или другому действующему решению, установите фактическое поведение и явно зафиксируйте выбранное толкование в изменении. Не объявляйте план готовой функцией.

## Карта кода и границы

- `cmd/emsim/` собирает приложение и связывает реализации; `internal/auth`, `content`, `training`, `assessment`, `reporting`, `media` содержат продуктовые модули; `internal/platform/` — PostgreSQL, очередь, аудит, HTTP, наблюдаемость и realtime.
- `internal/training/dds/` и `internal/training/operator112/` содержат отдельные чистые правила упражнений. `internal/training/` управляет общими занятиями, командами, транзакциями и evidence. Выбор правил идёт по `exercise_type`.
- `internal/assessment/` содержит рубрики, экспертные ревизии и оценивание. Критерии ДДС находятся в `internal/assessment/dds/`; первая версия 112 использует отдельную ручную рубрику `design-docs/contracts/rubric.operator112.json`.
- `internal/content/` импортирует и валидирует версии сценариев; `design-docs/contracts/` определяет внешние JSON/API-контракты; `migrations/` содержит изменения БД; `web/src/routes/trainee/Operator112Workplace.tsx` — рабочее место 112.
- `orchestration-core-main/` и архив рядом — исходный материал для уже перенесённого платформенного кода. Не импортируйте и не редактируйте их для обычных задач EmSim.

Сохраняйте модульный монолит без новых сетевых сервисов между продуктовыми модулями. Модуль меняет собственные таблицы; межмодульное взаимодействие оформляется узкими портами. Доменная логика не зависит от HTTP, SQL, файлов и моделей. Интерактивные команды исполняются в короткой транзакции API, а долговечные фоновые задачи идут через `platform/tasks`. Связанные изменение доменного состояния, аудит, уведомление и постановка задачи должны быть атомарны там, где это требуется процессом.

## Общие инварианты

- Одобренные версии сценариев, снимок отправленной карточки, закрытые evidence и история ревизий оценки неизменяемы.
- Роль пользователя (`admin`, `instructor`, `trainee`), тип упражнения (`dds_processing`, `operator112_intake`) и режим занятия — разные измерения. Одно занятие и его сценарии имеют согласованный `exercise_type`; каждый участник получает независимое состояние.
- Обучаемому нельзя отдавать эталон, скрытые факты, будущие реплики и служебные поля сценария. Сервер выдаёт только сведения, уже доступные по состоянию упражнения; преподавателю доступен разбор.
- Серверное время и часы PostgreSQL определяют порядок действий, блокировки и реальные сроки. Сценарное время вызова используется для отображения и не становится дедлайном само по себе.
- Для команд сохраняйте `command_id`, digest запроса и `expected_seq`: повтор возвращает прежнюю квитанцию без второго эффекта, устаревшая версия конфликтует. `stop` — барьер: эффект либо попал в итоговый evidence до него, либо отклонён/отменён после него.
- Ручное оценивание работает без STT/LLM. Экспертная ревизия имеет приоритет над поздним автоматическим результатом. История, прогресс и отчёты не смешивают ДДС с 112.

## Режим оператора 112: текущий срез

В коде реализован первый пилот `operator112_intake` (112-1), включая сценарий `seed/scenarios/pilot-112-medical-01.json`, отдельное рабочее место, преподавательский разбор и интеграционные проверки. ДДС получает уже заполненную входящую карточку и обрабатывает её; оператор 112 принимает входящий звонок и составляет карточку с нуля. Не переиспользуйте для 112 начальное состояние, команды, эталон или критерии ДДС по умолчанию.

Текущий процесс 112: `open` → `answer_incoming`; затем можно завершить разговор (`end_incoming`) и сохранить черновик (`save_intake_draft`) в любом порядке. Отправка (`dispatch_intake`) требует сохранённого черновика и фиксирует одну запись с адресатом, серверным временем и снимком карточки. После отправки редактирование закрыто. Для `complete_intake` требуются завершённый разговор и отправка; последние два действия допустимы в любом порядке. Неполный черновик можно сохранить, его качество определяет преподаватель. Повтор той же команды не создаёт новую отправку.

Карточка различает `unanswered`, `unknown`, `negative` и `known`; `negative` допустим для `victims_present`. При выдаче задания доступны АОН и сценарное время, а подготовленные реплики раскрываются после ответа. Evidence содержит разговор, действия, итоговую карточку и снимок отправки. При обновлении страницы восстанавливается подтверждённое сервером состояние.

Ограничения 112-1: одно обращение в назначении, `training/easy`, одна учебная служба, подготовленные текстовые реплики, без норматива времени и автоматической оценки. Рубрика 112-1 — ручная: полнота карточки 40%, достоверность 40%, передача 20%, порог 70. ДДС-профиль обучаемого для назначения 112 не требуется; для ДДС прежняя проверка сохраняется. Отправка происходит внутри симулятора, а не в реальную службу.

Срезы 112-2…112-9 в `slice-planning-112.md` описывают будущие возможности: ветвящийся опрос, профильные карты, несколько служб и связь с симулируемой ДДС, развитую оценку и отчёты, редактор сценариев, очередь и обрывы, ИИ-собеседника и голос. Реальный SIP и совместное занятие двух обучаемых не входят в текущий план. Не представляйте эти функции как существующие. При развитии 112 сохраняйте отдельные варианты сценария, команд, состояния, evidence и рубрики, расширяя общие механизмы только там, где это действительно общее поведение.

## Порядок изменений и проверок

1. Посмотрите `git status`, последние относящиеся к задаче записи `LOG.MD`, актуальный план и затрагиваемый код. Не затрагивайте посторонние изменения в рабочем дереве и не читайте/публикуйте содержимое `.env`.
2. Делайте законченный вертикальный результат: миграция, модель и правила, хранилище, API/схемы, интерфейс, нужный seed и проверки. Стабилизируйте правила и API перед UI, но включайте UI в тот же срез.
3. Для внешнего поведения синхронно обновляйте `design-docs/contracts/openapi.yaml`, JSON-схемы, генерируемые типы веб-клиента и соответствующую документацию. Миграции пишите вперёд, с учётом существующих данных ДДС и PostgreSQL 16.
4. Проверяйте существенные инварианты тестами правил и сквозными проверками БД/API/UI, когда изменение касается всей цепочки. Для 112 особенно проверяйте скрытые данные, независимость участников, replay/stale/stop, неизменяемый снимок отправки и регрессию ДДС. Не ослабляйте тесты ради прохождения.
5. Используйте `gofmt`, затем подходящие проверки: `make verify`; для БД, очереди, восстановления и межпроцессного поведения — `make test-integration` (Docker или отдельная пустая БД через `TEST_DATABASE_URL`); для контрактов — `python3 design-docs/contracts/check.py`; для клиента — `make verify-web`, `cd web && npm run lint`; для сквозного браузерного сценария — `cd web && npm run test:e2e`. Указывайте, что действительно запускали.
6. После значимой реализации или архитектурного решения добавьте краткую запись в `LOG.MD`: изменённые файлы, выполненные проверки, оставшиеся риски и следующий шаг. Не переписывайте историю журнала и не записывайте секреты или персональные данные.

Коммит создавайте только по просьбе пользователя; не добавляйте агента в авторы или соавторы.
