# Срез 2 — план реализации каталога пилотных сценариев

Статус: уточнённый план после обсуждения 19 сентября 2026. Реализация ещё не начата.

Основа: предложенный пользователем план C1–C7, `slice-planning.md` §3, актуальные RFC/ADR и контракты. Этот документ уточняет объём второго среза. Изменения исполняемых контрактов перечислены как будущая работа, а не как уже реализованные возможности.

## 1. Результат и границы

Преподаватель входит, открывает каталог, фильтрует сценарии и просматривает входящую карточку, эталон и сведения о версии. Отображение — подписанные поля и читаемые блоки, не набор JSON-полей. Администратор выбирает службу обучаемого из справочника. Подготовленные файлы загружаются штатной CLI-командой.

Начальный комплект — ровно два пилотных кейса по предоставленному скриншоту из «Гайд_Работа с АРМ-112 для ДДС от ОКр_ГСИ.pdf». Дополнительные фикстуры нужны для тестов, но 8–12 полноценных кейсов, несколько целевых служб и полный классификатор не являются условием приёмки.

Во втором срезе нет назначения, исполнения упражнения, исправления поля обучаемым, завершения карточки или подсчёта оценки. Нет редактора преподавателя, генерации, телефонии, озвучки и планировщика событий. UI делается после модели, правил и API в рамках этого же среза; стилизация под АРМ-112 остаётся отдельным проходом.

Ответ организатора о полном workflow не блокирует этот каталог. Он нужен для окончательных правил третьего среза. Сокращённая цель «принять» и возможность исправить округ — явно обозначенные пилотные допущения, не подтверждённые правила реальной ДДС.

## 2. Проверка исходного плана и внесённые исправления

Архитектурная основа подходит: модуль `content`, схема и семантическая валидация, PostgreSQL-адаптер, CLI, неизменяемые версии, API и UI преподавателя, интеграция справочника служб с `auth`.

Необходимые исправления:

1. Вместо автоматического `n+1` при изменении файла — явная версия. Одинаковая версия с другим содержимым вызывает ошибку; новую версию автор файла задаёт осознанно.
2. Вместо 8–12 кейсов и обязательной сверки всех workflow — два согласованных пилота и минимальные справочники. Исключения 103/104 и полный маппинг XLSX не блокируют старт.
3. Текущего `reference` недостаточно для эталона исправления поля. Нужен структурированный ожидаемый результат и порядок действий; текст в `notes` этого не заменяет. Поле округа уже существует: `card.address.okrug`; `district` — район, «Чертаново Южное».
4. `contacts.minItems = 1` не подходит кейсам без звонков. Разрешить пустые контакты при отсутствии ссылок на них; не добавлять фиктивные номера и реплики для прохождения схемы.
5. Прямая FK-миграция на существующей БД с пользователями и пустой `services` может упасть до сидирования. Нужен поэтапный переход без удаления БД и без `docker compose down -v`.
6. В `schema.sql` переход `approved → superseded` с сохранённым `approved_at` сейчас нарушает `scenario_versions_approval_shape`. При реализации исправить ограничение, сохранить сведения об утверждении и добавить тест перехода. Текущий триггер защищает UPDATE содержимого, но не DELETE версии; защиту удаления добавить явно.
7. Публичную проекцию строить по разрешённым полям. Простого удаления нескольких закрытых ключей и поиска их названий в сериализации недостаточно, особенно при расширении схемы.
8. Не вводить безусловный `has_voice=false` как описание любого будущего содержимого. В пилоте аудио отсутствует; семантику этого поля сверить с контрактом (наличие подготовленного аудио, а не просто контактов).
9. `--actor` — атрибуция локального импорта, не способ аутентифицировать человека одним логином. CLI предназначен оператору установки с доступом к БД; для пилота actor — активный admin. Преподавателю доступен просмотр через API.
10. Шаги C1–C7 — этапы работы, не разрешение автоматически создавать коммиты. Коммиты выполняются по отдельному запросу пользователя.

Утверждения из исходного текста о проверенном коммите, пройденных тестах, числе строк XLSX и точных номерах его колонок в рамках этого пересмотра заново не проверялись. Они не являются результатом текущего ревью и не заменяют проверки при реализации.

## 3. Два пилотных кейса

Общая основа со скриншота:

- происшествие: дерево упало во дворе; пострадавших нет;
- адрес: Россия, Москва, ЮАО, Чертаново Южное, Чертановская улица, дом 58, корпус 2, подъезд 2;
- целевая служба для пилота: «Управа Чертаново Южное»;
- дополнительно показанные получатели: «Префектура ЮАО», «Департамент природопользования» — названия расшифровываются из сокращений как пилотные обозначения, без заявления об официальном справочном соответствии;
- звонки, комментарии и события для достижения цели пилота не требуются; `events=[]`, `contacts=[]`, `reference.call.required=false`.

| Свойство | Кейс 01 | Кейс 02 |
|---|---|---|
| Название в каталоге | Дерево во дворе — 01 | Дерево во дворе — 02 |
| Исходный `card.address.okrug` | `ЮАО` | `ЮАР` |
| Требуемое действие | Принять | Исправить округ на `ЮАО`, затем принять |
| Эталон | Первичное решение `accepted` | Исправление конкретного поля до решения `accepted` |
| Остальные исходные поля | Общая основа | Те же значения, что в кейсе 01 |

Нейтральное название второго кейса не раскрывает ошибку. Обоим назначить одинаковую техническую сложность `1`; это стартовое значение для каталога, не экспертная калибровка сложности.

Файлы создаются при C3. Для данных, отсутствующих или обрезанных на скриншоте, используются явно обозначенные учебные значения. Не восстанавливать неизвестное по догадке как достоверные данные гайда. В `seed/README.md` перечислить источник, перенесённые поля и тестовые дополнения, включая описание происшествия, относительное время регистрации и справочные коды. Абсолютное время из старого скриншота не превращать в время будущего прохождения.

`address.text`, если присутствует, должен соответствовать исходным структурированным полям: во втором кейсе не оставлять в нём скрытое правильное `ЮАО`. Исправление и единый способ формирования отображаемого адреса проектируются для третьего среза.

Минимальные справочники содержат все службы, на которые ссылаются карточки, и один тип происшествия. Технические ключи служб можно выбрать локально, например `pilot_chertanovo_uprava`, `pilot_yuao_prefecture`, `pilot_nature_department`, и документировать как учебные. Для типа сначала проверить подходящую строку исходного XLSX; если однозначного соответствия нет, использовать явно учебный код `pilot_tree_courtyard`, не выдумывая официальный числовой код. Такой маппинг уточняется отдельно и не блокирует пилот.

Workflow целевой службы содержит только минимальный пилотный путь до `accepted` (системные `added/received` и первичное решение). Не добавлять `accepted` в глобальный список терминальных статусов ДДС и не придумывать цепочки бригад для остальных служб. Ограниченность workflow явно описывается в документации seed и в просмотре сценария.

## 4. Решения для реализации

### Формат файла и версии

Добавить `scenario-file.schema.json` с обёрткой:

```json
{
  "schema": "emsim/scenario-file/v1",
  "key": "pilot-tree-01",
  "version": 1,
  "title": "Дерево во дворе — 01",
  "origin": "manual",
  "body": {}
}
```

В примере `body` — заглушка; настоящий файл обязан соответствовать `scenario.schema.json`. Все JSON Schema и используемая рубрика доступны бинарнику локально; сетевые загрузки схем при импорте запрещены. Выбор реализации валидатора 2020-12 (кандидат из исходного плана — `github.com/santhosh-tekuri/jsonschema/v6`) и её совместимость проверяются при C2.

- Добавить `scenarios.source_key text UNIQUE`, nullable для будущего авторства без файлов.
- Идентичность версии: `(source_key, version)`. UUID назначает приложение; `key` не зависит от пути файла.
- Первая версия — 1; следующая новая — максимальная существующая + 1. Неявное повышение запрещено.
- Повтор существующей версии с тем же нормализованным телом — no-op; иное тело — конфликт с файлом, ключом и версией в сообщении.
- В рамках CLI среза 2 `title`, `origin`, `target_service` закреплены за ключом: их изменение отклоняется явно, даже при совпавшем digest. Это убирает молчаливое изменение метаданных при повторном импорте; расширенное редактирование — отдельная задача.
- Явная следующая версия создаётся `approved`, предыдущая текущая становится `superseded`; исторические версии сохраняются. Повтор старой версии не возвращает её в текущие и не откатывает сложность сценария.
- `scenarios.difficulty` отражает текущую версию; `body`, `digest`, `difficulty`, `exercise_type` исторической версии неизменяемы. Сведения об утверждении сохраняются после `superseded`.
- Конкурентные импорты защищаются ограничениями БД и блокировкой по ключу сценария; одновременно текущая approved-версия не может стать неоднозначной.
- Digest: SHA-256 детерминированного JSON тела. До реализации определить нормализацию чисел; не использовать без проверки `json.Unmarshal(any)` с потерей точности через `float64`. Дублирующиеся JSON-ключи отклонять. Тестировать порядок ключей, пробелы, числовые формы и отсутствие потери значений.

### Эталон и закрытые данные

Минимальное расширение контракта второго среза:

- `reference.field_corrections`: список `{path, expected_value, before_status}`. Для кейса 02 — `path=/card/address/okrug`, `expected_value=ЮАО`, `before_status=accepted`; для кейса 01 список пуст.
- Для пилота разрешён только этот путь и строковый результат. Это описание ожидаемого действия, не API произвольного JSON Patch.
- `reference.pilot_goal`: необязательное фиксированное значение `accept_card`, явно помеченное как цель пилота. Не является командой закрытия и не меняет смысл статусов. Оба пилота используют это значение; старые сценарии без поля сохраняют прежние правила.
- `reference.primary_decision.status=accepted`, `comment_required=false`, `expected_chain=[]`: после первичного решения пилот не требует дальнейших статусов. Не дублировать первичное решение в цепочке последующих статусов.
- Существующие `scoring` сохраняются как формат поправок; не подменять исправление поля проверкой устного адреса и не добавлять фиктивные критерии в рубрику. Автоматический оценщик появится в срезе 6.

Обновить схему, описания и примеры согласованно. Старый `scenario.example.json` остаётся примером более полного сценария, а не третьим обязательным seed-кейсом. Пилотные расширения не меняют enum `exercise_type`: оба сценария остаются `dds_processing`.

Проекция входящей карточки строится из явно разрешённых типизированных полей. Она не содержит `reference` целиком, `pilot_goal`, `field_corrections`, `hints`, происхождение генерации, полный таймлайн будущих событий, `events[].expects` и служебные параметры оценки. Использовать тесты точной формы DTO и контрольные закрытые значения, включая вложенные неизвестные поля.

### Импорт и справочники

- CLI: `emsim import services|classifier|scenarios --actor <login> <path>`; порядок — службы, классификатор, сценарии. Actor — существующий активный admin; операции аудируются.
- Каждый запуск одной подкоманды атомарен. Три отдельных запуска не являются одной общей транзакцией. Ошибка импорта сценариев откатывает весь каталог этого запуска, но не ранее загруженные справочники.
- Ошибки содержат файл, JSON-путь и понятную причину. Дубли `(key, version)` в одном наборе, конфликтующие определения справочников и неизвестные ссылки отклоняются до записи. Связанные записи проверяются согласованно внутри транзакции.
- Идемпотентные повторы не меняют доменные timestamps/сведения об утверждении. Повторные технические audit-записи допустимы и не считаются дубликатами контента.
- Для справочников пилота: вставка отсутствующих записей, повтор идентичных — no-op, конфликтующее определение — ошибка. Слепой upsert workflow опасен для будущих прохождений; политика обновления и снимки workflow требуют отдельного решения к третьему срезу.
- Полный конвертер XLSX, маппинг всех колонок и административный HTTP-импорт классификатора не входят в обязательный объём. Для пилота достаточно проверяемого минимального JSON с документированным происхождением.
- Не вносить изменения в `users` напрямую из `content`; межмодульные операции идут через порты.

### Переход с БД первого среза

- Сначала создать content-таблицы; FK `users.service_code → services(code)` добавить как `NOT VALID`, чтобы не сканировать старые значения до сидирования. Новые ссылки всё равно проверяются PostgreSQL.
- После загрузки служб штатная проверка обновления перечисляет отсутствующие коды. Существующие профили не очищаются и не переименовываются автоматически. Нужные службы добавляются осознанно либо профиль исправляется через `auth`/админ-API.
- Затем выполнить `VALIDATE CONSTRAINT` штатным шагом обновления, описанным в README/Makefile. На чистой demo-БД этот шаг автоматизируется после seed. На существующей БД конфликт выдаёт диагностируемую ошибку, без удаления тома.
- Закрытие среза требует проверенного сценария обновления поверх 00003 с непустой таблицей пользователей и успешной валидацией FK после согласования справочника. `NOT VALID` не считается конечным состоянием успешной установки.
- Порт `ServiceCatalog` в `auth` проверяет существование/доступность службы при её назначении; неизвестный код возвращает 422. Ошибка чтения справочника не маскируется под «неизвестный код».

## 5. Шаги реализации

### C1 — контракты и миграция

Добавить content-таблицы, `source_key`, ограничения версий, защиту содержимого и удаления, поэтапный FK. Пустая `tickets` допустима как минимальная зависимость существующего FK, без реализации импорта билетов. Добавить файловую схему, пилотные поля эталона, возможность пустых контактов. Исправить сохранение атрибуции superseded-версий. Обновить `schema.sql`, `check-invariants.sql` и соответствующие описания RFC/OpenAPI; не изменять правила завершения `training` этим шагом.

### C2 — домен и валидация `internal/content`

Типы домена, файловый и схемный адаптеры, семантическая валидация и публичная проекция. JSON Schema-библиотека и чтение файлов остаются на границе; доменные правила не зависят от HTTP/SQL/файлов. Компоновка — в `cmd/emsim`.

Проверять активную целевую службу, все службы уведомления, ровно один `mine=true` для целевой службы, классификатор, согласованность названий с выбранным справочником, уникальные ключи контактов/событий, ссылки эталона и событий, достижимость первичного решения и цепочки по workflow, допустимые статусы/опорные точки событий, известные критерии `scoring`. Пустые контакты допустимы только без требуемых звонков и ссылок на них. Для `spawn_card` проверить существование и совместимость ссылок, если такой контент импортируется, не реализуя исполнение событий.

Учебная опечатка `ЮАР` должна проходить валидацию: это намеренно неверное входное значение в корректно описанном упражнении. Нельзя требовать, чтобы исходное поле уже совпадало с эталоном. При этом закрытый путь исправления, тип и ожидаемое значение проверяются строго.

### C3 — хранилище, CLI и два seed-кейса

Реализовать импорт по §4, audit, блокировки, детерминированное сравнение. Создать `seed/services.json`, `seed/classifier.json`, два файла `seed/scenarios/*.json`, `seed/README.md`. Не выполнять импорт при старте каждого API-процесса; отдельная команда сохраняет воспроизводимость и понятные ошибки.

### C4 — API каталога

- `GET /services`: admin + instructor через отдельную группу доступа; `/scenarios*`: instructor-only. Доступ admin к службам не расширяет доступ к эталонам.
- `GET /scenarios`: service, status, difficulty_min/max, page/page_size; проверка диапазонов и устойчивый порядок выдачи. Для пилота обе записи approved и одной сложности; другие комбинации фильтров покрывают технические фикстуры.
- `GET /scenarios/{id}`: текущая версия с закрытым содержимым только преподавателю.
- `GET /scenarios/{id}/versions`: история метаданных. Отображение полного тела каждой старой версии не обязательно для пилота; не обещать это в UI без отдельного endpoint.
- `GET /scenarios/{id}/preview`: только преподавателю; публичная проекция карточки и отдельно эталон, с явными схемами ответа в OpenAPI. Preview не создаёт item/run. Время регистрации показывается как относительное, например «за 60 с до выдачи»; не подставлять выдуманную дату в обязательное `CardView.registered_at` — для preview нужен отдельный DTO.
- Изменяющие маршруты редактора, generate/regenerate/approve остаются нереализованными с пометкой позднего среза в контракте.

### C5 — интеграция с auth

Потребительский порт справочника в `auth`, адаптер и композиция, 422 на неизвестную службу, сохранение прежних правил обязательности службы по ролям. В админ-UI — выбор службы из API. Проверки доступа обновляются в единой таблице ролей и тестах.

### C6 — UI преподавателя

Каталог, фильтры, пагинация, карточка просмотра, блок эталона, история версий. Карточку показывать подписанными полями, пригодными для повторного использования в третьем срезе. Закрытые блоки располагаются отдельно и не передаются общему компоненту входящей карточки.

Эталон кейса 02 отображает «Округ: ЮАР → ЮАО; до принятия», кейса 01 — «Принять». Видна пометка «Пилот: цель — принятие карточки; полный порядок обработки уточняется». Блок событий показывает «Событий нет», звонков — «Не требуются». Нет кнопок действий обучаемого и редактирования сценария. Состояния загрузки, пустого каталога и ошибок обрабатываются явно.

### C7 — запуск, документация и приёмка

Поставлять seed и встроенные схемы в сборке; `.dockerignore` и Dockerfile должны действительно включать необходимые файлы. Demo-порядок: migrate → bootstrap → seed → проверка/валидация FK → API. Worker для каталога не требуется. Добавить `make seed`, документированный путь обновления существующей БД, команды повторного импорта и диагностику конфликтов. Проверить, что повторный штатный запуск seed идемпотентен; не полагаться на повторный запуск уже завершённого Compose-контейнера без проверки поведения.

`check.py` должен проверять обёртку и тело всех seed-файлов; семантические зависимости проверяют Go-тесты импортера. Обновить README и LOG.MD по фактическим результатам.

## 6. Проверки и Definition of Done

- Миграции: пустая БД и обновление поверх 00003 с существующими service_code; нет потери пользователей и данных.
- Штатная загрузка двух кейсов, справочников и последующая валидация FK без ручных INSERT.
- Повтор seed без дубликатов и изменения версий; независимость digest от порядка ключей и пробелов.
- Конфликт той же версии, явная следующая версия, повтор старой версии без отката текущей, конкурентные импорты.
- Ошибка одного файла откатывает весь импорт сценариев; сообщение указывает место ошибки. Неверные ссылки и некорректный эталон отклоняются; намеренная опечатка во входящей карточке принимается.
- UPDATE содержимого/сложности и DELETE утверждённых/исторических версий запрещены; superseded сохраняет атрибуцию утверждения.
- Trainee получает 403 на всех зарегистрированных маршрутах каталога и preview; admin имеет доступ к службам, но не сценариям; без сессии — 401. Публичная проекция проверена отдельно по полям и закрытым контрольным значениям.
- UI преподавателя: каталог → фильтр → оба кейса → различие округов → эталоны → метаданные версий; без JSON как основного отображения.
- Администратор создаёт/редактирует обучаемого со службой из списка; неизвестный код отклоняется.
- Повторное использование версии подтверждается неизменяемостью модели; реальные независимые назначения и прохождения тестируются в срезе 3, поскольку их пока нет.
- Выполнить `make verify`, `make test-integration`, `make verify-web`, `npm run lint` из web, `python3 design-docs/contracts/check.py`, проверку Compose и ручной запуск/UI. Записывать только реально выполненные проверки. Не создавать лишние повторные прогоны без изменений или нерешённых проблем.

## 7. Что остаётся к третьему срезу

Два кейса достаточны для пилотного пути «назначение → открытие → действия → сохранённый результат». К этому этапу нужны команда исправления разрешённого поля в состоянии конкретного item, журнал старого/нового значения, порядок исправления и принятия, защита сценария от изменения и независимость прохождений разных людей.

`accepted` сейчас не разрешает обычный `close` по ADR-011/RFC. Поле `reference.pilot_goal` само по себе этого не меняет. Перед реализацией завершения пилота нужно явно согласовать и отразить в ADR/RFC/контрактах, как учебная цель разрешает завершение с сохранением evidence; не подменять принятие вымышленным `completed`. Полный workflow и право ДДС исправлять входящие поля уточняются у организатора. До этого нельзя объявлять весь третий срез закрытым по текущему DoD.

Открытые замечания первого среза (конкурентные изменения последнего администратора/профиля, инвалидирование сессий при изменении роли/РМ, аудит отклонённых входов) сохраняются в LOG.MD. Они не включаются незаметно в реализацию каталога и требуют отдельной постановки.
