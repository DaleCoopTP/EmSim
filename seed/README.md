# seed/ — пилотный комплект слайса 2

Готовые данные для `emsim import` (slice-planning.md §3, `slice-2-plan.md`). Два пилотных
кейса взяты со скриншота стр. 23 гайда «Работа с АРМ-112 для ДДС от ОКр ГСИ»
(«Происшествие 881412») и строки классификатора с кодом `14080106`
(«Дерево упало во дворе»).

## Файлы

- `services.json` — четыре учебные службы: `dds_district` (ДДС района — служба
  обучаемого), `pilot_yuao_prefecture` (Префектура ЮАО), `pilot_nature_department`
  (Департамент природопользования и охраны окружающей среды, расшифровка
  сокращения «Деп. природ.» со скриншота). У всех — один и тот же минимальный
  workflow (`added → received → accepted|not_accepted`, `not_accepted → accepted`),
  этого достаточно для UC5/UC5 пилота; полный workflow служб — не предмет слайса 2.
  `pilot_ambulance` — учебный адресат отправки в разговорном 112; для новых
  кейсов дополнительно добавлены `pilot_gas_104` и `pilot_fire_101`.
  Наличие этих служб в справочнике не означает реального оповещения.
- `intake-catalog.json` — неизменяемая версия каталога типов происшествий,
  карт 104/101 и пилотных правил предложения учебных служб. Загружается
  отдельно от кейсов и фиксируется для занятия при его запуске.
- `classifier.json` — одна строка классификатора: код `14080106`, признаки —
  колонки XLSX «признак 1/2/3» и «группа», `notify` — коды трёх служб выше
  (в исходном XLSX это колонки 74 «Территориальные ОИВ» и 66 «Департамент
  ППиООС»; здесь они развёрнуты в конкретные пилотные коды служб, а не оставлены
  общей категорией).
- `scenarios/pilot-tree-01.json`, `scenarios/pilot-tree-02.json` — два прохождения
  одной и той же карточки:
  - **01** — карточка заполнена корректно, эталон — просто принять (`primary_decision.status:
    accepted`, `field_corrections: []`).
  - **02** — округ в карточке намеренно испорчен (`ЮАР` вместо `ЮАО`);
    `reference.field_corrections` требует исправить `/card/address/okrug` на
    `ЮАО` до статуса `accepted`. Само поле обучаемому не подсказывается —
    несовпадение исходного значения и `expected_value` и есть ошибка, которую
    он должен найти (design-docs/contracts/scenario.schema.json's
    `$defs.reference.field_corrections`).

  Оба файла: `registered_at_offset_s`, номер карточки и телефон в формате
  `+7XXXXXXXXXX` — учебные добавления (скриншот показывает только неформатированный
  «+7 (749) 512-34-56», перенесённый в `card.phones.provided` как есть). Звонки и
  события в пилоте не нужны (`contacts: []`, `events: []`) — `slice-planning.md`
  §3 ограничивает срез 2 загрузкой и просмотром.
- `scenarios/pilot-phone-01.json` — immutable-пилот среза 5: до `accepted`
  требуется завершить звонок руководителю бригады (учебный номер 4152) с
  адресом, типом происшествия и принятыми мерами.
- `scenarios/pilot-112-medical-01.json` — первый текстовый вызов оператора
  112: заявитель звонит о себе, принимает один обучаемый, сведения раскрываются
  после ответа и направляются учебной скорой помощи. Время `02:03 МСК` —
  время сценария; серверное время действий фиксируется отдельно. ФИО, пол и
  квартира не заданы и не должны выводиться из описания.
- `scenarios/pilot-112-medical-01-v2.json` — новая утверждённая версия того
  же вызова с выбором вопросов. Старая версия 1 сохраняется для ранее
  назначенных занятий; повторный импорт обеих версий идемпотентен.
- `scenarios/pilot-112-address-01.json` и `pilot-112-victims-01.json` —
  учебные задания на неполный адрес, уточнение числа пострадавших и сведения,
  которых заявитель не знает. Это фикстуры диалога, а не медицинские советы.
- `scenarios/pilot-112-gas-explosion-01.json`,
  `pilot-112-road-traffic-fire-01.json` и
  `pilot-112-gas-road-traffic-fire-01.json` — три самостоятельных назначения
  без разговора (`intake112.mode="card_only"`). Их закрытый эталон хранит
  ожидаемый тип, а карты появляются только после действия обучаемого
  «Добавить тип происшествия». Прохождения, начатые с 112-4, заканчиваются
  единым действием «оповестить и сохранить карточку»
  (`notify_services`/`complete_intake`) вместо прежних
  `review_service_selection`/`complete_profile_case`.
- `scenarios/pilot-112-full-gas-road-traffic-fire-01.json` — срез 112-4,
  `intake112.mode="full_case"`: разговор про запах газа рядом с ДТП
  (`dialogue`, как у `pilot-112-medical-01-v2`) в одном задании с картами
  104/101 (`card_only`'s type/profile catalog). Закрытый эталон —
  `reference.expected_types`/`expected_services`
  (`["pilot_gas_104","pilot_fire_101"]`), без `recipient_services` —
  это поле относится только к прежнему `incoming_call`.
- `voice-assets/manifest.json` и два PCM WAV-файла — greeting/ack этого
  контакта (mono, 16-bit, 16 kHz). `import seed` после сценариев импортирует
  их идемпотентно в content-addressed `BLOB_ROOT`.

## Порядок загрузки

Три шага, в этом порядке — каждый следующий читает данные, которые должен был
записать предыдущий (сценарии ссылаются на `target_service`/`notification_list`
службы и на `incident.type_code` классификатора):

```bash
emsim import services --actor <login-администратора> seed/services.json
emsim import classifier --actor <login-администратора> seed/classifier.json
emsim import intake-catalog --actor <login-администратора> seed/intake-catalog.json
emsim import scenarios --actor <login-администратора> seed/scenarios
```

или одной командой:

```bash
emsim import seed --actor <login-администратора> seed
```

`--actor` — логин активного администратора (проверяется тем же способом, что и
любой другой admin-запрос); импорт от имени неактивного пользователя или не-admin
отклоняется.

Повторная загрузка того же набора **идемпотентна**: уже загруженные строки/версии,
если их содержимое не изменилось, пропускаются (без дублей и без новой
`created_at`/`approved_at`); попытка изменить уже загрученный код/версию другим
содержимым отклоняется с ошибкой конфликта, ничего не записывается.

## Обновление существующей установки

Миграция `migrations/00004_content_catalog.sql` добавляет
`users.service_code_fkey` как `NOT VALID` (проверяется только для новых
записей; существующие `users.service_code` не сканируются на месте — см.
комментарий в самой миграции). После `emsim migrate up`:

1. `emsim import services --actor ... seed/services.json` (или свой набор служб).
2. Если у существующей установки есть `users.service_code`, отсутствующие в только что
   загруженном справочнике, команда выше сообщит их коды (без ФИО/логинов) и завершится
   ошибкой `orphan_service_codes` — добавьте недостающие службы или поправьте профили
   пользователей.
3. После того как каждый `users.service_code` присутствует в `services`, та же команда
   на повторном запуске валидирует ограничение
   (`ALTER TABLE users VALIDATE CONSTRAINT users_service_code_fkey`) и завершается успешно.
