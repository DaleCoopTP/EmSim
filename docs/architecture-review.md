## 1. Что документ делает правильно (и лучше исходных набросков)

### 1.1. Доменная модель сверена с первоисточниками — и совпадает
Я проверил каждое утверждение про предметную область:

- **Статусы реагирования** (`added / received / accepted / not_accepted / responding / arrived / working / completed / refused`) — 1:1 с таблицей памятки стр. 21–22.
- **30 секунд с момента *направления* карточки, а не открытия** — памятка стр. 21 ("в течение 30 секунд после направления карточки в службу"). Правильно.
- **Исключения 103 и 104** (`completed_without_team`; комментарий для 104 по отдельной policy) — памятка стр. 23. Правильно.
- **`completed`/`refused` закрывают редактирование; ошибка после — через отдел контроля** — памятка стр. 22, 32. Правильно.
- **Статус карточки выводится отдельно от реакций служб** (`unnotified`, `refusal`, `unfinished` через 48 ч) — памятка стр. 27. Правильно.
- **`not_accepted → accepted` разрешён, прямого обратного нет** — памятка стр. 25. Правильно.
- **XLSX: три строки многоуровневой шапки, условные колонки служб** — проверил: строки 1–3 = шапка, 104 колонки, колонки M+ вида «Служба 101 (выбран признак …)». Правильно.

Это не тривиально: большинство команд возьмут плоский список служб и потеряют условную маршрутизацию.

### 1.2. Анализ orchestration-core точен
Все 15 утверждений в `02-core-reuse.md` совпадают с кодом:
- `CHECK (kind IN ('dialogue','judge'))`, `UNIQUE (kind, run_item_id)` — в `00001_orchestration_core.sql`.
- Бинарный скоринг `score_basis_points ∈ {0, 10000}` — там же.
- `turnLoop` вызывает `simulator.Simulate` и `client.Reply` в одном цикле, коммит после — `dialogue/service.go:170`.
- Lease 120 с / heartbeat 30 с — `recovery/policy.go:28`.
- Один `X-API-Key` — `httpapi/api.go:69`.

Вывод документа верен: **переносить kernel (queue/lease/fencing/recovery/idempotency + 33 интеграционных теста), а не приложение**. Core — это bot-to-bot harness; человек в цикле требует одной durable-задачи на реплику. Правильное решение, а не «подкрутить enum».

### 1.3. Исправлены ошибки исходных набросков
| В набросках | В документе | Почему правильно |
|---|---|---|
| «Patient Simulator» | `CallerSimulator` | Медицина — лишь часть кейсов |
| Задача 1 = «чат» | Диалог **+ заполнение карточки** | ТЗ стр. 14 прямо требует карточку |
| «HTTPS на входе + закрытая сеть» | TLS на всех hop, PostgreSQL `verify-full`, SRTP | ТЗ: «шифрование всех передаваемых данных внутри контура» |
| «Внешний S3» | Другой узел **внутри** контура | ТЗ: изолированный контур |
| «Первая версия — CLI» | CLI только отладочный адаптер | ТЗ требует web-UI + имитацию АРМ-112 |
| Нет Lesson/Assignment | `Lesson → Assignment → Run → Item` | Без этого нет stop преподавателем, нет источника карточек |

### 1.4. Ключевые архитектурные решения — здравые
- **Модульный монолит + несколько процессов по нагрузке** (ADR-01) — единственно разумно для 100 пользователей.
- **Одна durable-задача на ответ симулятора** (ADR-04) — worker свободен, пока человек думает. Это то, что core не умеет.
- **Stop = транзакционный barrier по строке lesson + epoch** (ADR-06, `05 §3`) — поздний ответ LLM физически не может попасть в run. Порядок блокировок задан. Правильно.
- **Допустимость ≠ правильность** (`01 §6`): UI запрещает только процедурно невозможное; содержательно неверный отказ с комментарием сохраняется и получает ошибку при оценке. Это ключевая педагогическая идея — без неё тренажёр решает задачу за ученика.
- **`unavailable` не превращается в 0 баллов** (ADR-08) — технический сбой judge ≠ провал ученика.
- **Snapshot/evidence неизменяемы, оценка — ревизиями** (ADR-07) — исторические оценки проверяемы, экспертная правка с audit (требование ТЗ стр. 11).

## 2. Где документ избыточен (и что это стоит)

Ниже — механизмы, которые **корректны**, но для прототипа на хакатон дают минимум ценности при большой стоимости.

| Механизм | Где | Ценность на хакатоне | Стоимость | Рекомендация |
|---|---|---|---|---|
| 9 bounded contexts (`identity, curriculum, catalog, teaching, training, assessment, reporting, operations, platform`) | 01 §2 | Низкая | Высокая (9 пакетов × domain/app/ports/adapters) | **Свернуть до 5:** `identity`, `content` (curriculum+catalog), `training` (teaching+training), `assessment` (+reporting), `platform` |
| Outbox + inbox + reconcilers между модулями одного процесса и одной БД | 04 §5, 05 §4 | Низкая | Средняя | Прямые вызовы application-сервисов в той же транзакции. Outbox только для SSE-уведомлений |
| Двухуровневый snapshot (`RunSnapshot` + `ItemSnapshot`) | 01 §3 | Средняя | Средняя | Один snapshot на item достаточен |
| `execution.scopes` с полиморфным owner + consistency checker | 02, 05 | Низкая | Средняя | `tasks.run_id` + `dedup_key` |
| `recovered_inputs` + `recovered_only` receipt + supplemental evidence | 01 §10, 04 §1 | Низкая | Высокая (UI разбора конфликтов) | После stop — отклонить с понятным сообщением; клиентский буфер сохранить |
| Media chunks с digest + локальный capture в IndexedDB + `playback_epoch`/barge-in | 01 §9, 05 §5 | Низкая | Очень высокая | Отложить. ТЗ: «через виртуальную IP-телефонию **или текстовые сообщения**» |
| Asterisk + WebRTC + media gateway + STT + TTS | 01 §9, W9 | Средняя (wow-эффект) | Очень высокая | Сначала текст. Голос — browser WebRTC → простой gateway со STT/TTS. Asterisk только если останется время (для демо SIP-телефона) |
| HA: sync-реплика + quorum + fencing + резерв inference | 01 §11, ADR-13 | Нулевая для демо | Очень высокая | Описать как профиль поставки в документации. Демо — single-node + ежедневный `pg_dump` |

| Три параллельных журнала (audit / domain events / execution logs) | 07 | Средняя | Средняя | Оставить audit + events; execution logs = обычный structured log |

**Оценка избыточности:** ~40 % механизмов. При этом **каждый по отдельности обоснован** — документ нигде не «изобретает» сложность; он просто проектирует production-систему для госзаказчика, а не хакатонный прототип. Отсюда и «5/10 как план»: в документе нет MVP-среза и нет приоритизации по критериям жюри.

## 3. Что в документе слабо или отсутствует (важно для победы)

Критерии финальной экспертизы из ТЗ §17: идея/оригинальность; качество кода/интеграция/скорость; **проверка прогнозирования и достоверности** (= точность judge vs эксперт); **настраиваемые параметры**; **объективность диаграмм**; **UX/UI**; питч. Документ силён в «качество кода/интеграция» и молчит в остальном.

### 3.1. UI/UX — один абзац на 1260 строк
Документ: «Конкретный UI framework не влияет на доменные контракты». Верно, но жюри увидит **экран**, а не lock order. ТЗ требует «имитацию интерфейса АРМ-112» — а в памятке на стр. 15–18 есть точный референс карточки (адресный блок, опросная карта, формализованные признаки, список оповещения с «карандашом» статусов). Ни макетов, ни выбора стека, ни списка экранов с приоритетом. **Это самый большой пробел для победы.**

### 3.2. AI-стек и качество — отложены «до W0»
Не выбраны: модель (Qwen/…), сервинг (vLLM/llama.cpp), STT/TTS (Whisper/Vosk, Silero/Piper). Нет примера prompt'а, схемы `DisclosurePolicy` (как fact IDs попадают в ответ и как валидируются), схемы JSON judge-ответа с примером. Нет плана калибровки на «Билетах и задачах» (источник данных из ТЗ стр. 15 — документ его не использует). Критерий «оценка достоверности» жюри проверит именно здесь.

### 3.3. Workflow преподавателя по ТЗ стр. 14 — 6 строк
Категория → генерация эталона → **частичное/полное подтверждение** → предпросмотр с подсветкой правильных ответов → **коррекция по комментарию в контекстном поле** → загрузка материалов → проверка грамматики. Это самый демонстрируемый сценарий, и он покрыт схематично. Нет примера JSON сценария/рубрики.

### 3.4. Аналитика и диаграммы
Reporting описан как projections. Какие графики/тепловые карты (опциональные по ТЗ, но в критериях жюри «объективность диаграмм») — не спроектировано.

### 3.5. Оригинальность
В документе нет ни одной фразы «в чём идея». Кандидаты, которые уже есть в архитектуре, но не названы: (а) «допустимость ≠ правильность» как педагогический принцип; (б) карточки учеников из задачи 1 становятся источником для задачи 2 (замкнутый учебный цикл); (в) детерминированные правила + LLM с evidence refs, а не «чёрный ящик»; (г) `unavailable ≠ 0 баллов`.

## 5. Логирование и безопасность: выполняются ли требования

### Что есть (сверх ожиданий)
- **Audit append-only** в той же транзакции, что и бизнес-команда: actor, action, resource, scope, command/request ID, server time, outcome, before/after refs, причина. Логируются denied/login/read/export. Роль writer **без UPDATE/DELETE**. Помесячные партиции; guard от удаления партиции с событиями свежее cutoff; **6 календарных месяцев, не «180 дней»**; архив на независимый узел. Это закрывает ТЗ («аудит всех действий», «журналы ≥ 6 месяцев») с запасом.
- **Разделение audit / evidence / execution logs** с общим correlation ID — правильно (разные ACL, payload, retention).
- **TLS на всех hop** (reverse proxy→API, PostgreSQL `verify-full`, object storage, inference, SIP-TLS/SRTP), локальная CA в runbook.
- **RBAC + принадлежность ресурса + permission**: администратор не видит учебные тексты и не меняет оценки (ТЗ стр. 10 — прямое ограничение); преподаватель не видит чужие занятия; оператор — чужие результаты. ACL на REST, SSE, скачивание, media-token. Блокировка отзывает сессии.
- Сессии `HttpOnly/Secure/SameSite` + CSRF; секреты не в snapshot/metrics; XML без XXE; загрузки с MIME/размер/карантин; **prompt injection: текст ученика — данные, не инструкции; LLM без инструментов и сети**.
- Матрица прав (04 §6) с отрицательными тестами.

### Пробелы
1. **«Многоуровневая аутентификация»** (ТЗ стр. 7, 13) — только «второй фактор согласно политике учреждения». Нужно конкретно: TOTP для admin/instructor как минимум, или step-up на privileged операции.
2. **Нет защиты `/auth/login`**: lockout после N попыток, rate limit, задержка. Одна строка, но жюри по безопасности спросит.
3. **152-ФЗ**: есть обезличивание ученических карточек и least privilege, но нет перечня ПДн и политики хранения/удаления по запросу. Для хакатона — абзац в документации.
4. Целостность журналов (hash-chain) не упомянута — необязательно, но дёшево и эффектно на защите.

**Оценка безопасности/логирования: 9/10 по проектной полноте.** Реализовать всё — дорого, но минимальный набор (audit-таблица в транзакции, RBAC с scope, TLS через reverse proxy + `sslmode=verify-full`, партиции) укладывается в хакатон.

## 6. Мелкие замечания и нестыковки

- `card_fill_limit = 30 с` от открытия карточки до `SubmitItem` (01 §7) — как *дефолт* для задачи 1 выглядит нереалистично (заполнить карточку АРМ-112 за 30 с). ТЗ говорит «по умолчанию 30 сек» про тайминг заданий вообще; памятка — про 30 с на первичный статус в задаче 2. Для задачи 1 стоит дефолт 3–5 мин, а 30 с оставить задаче 2. Иначе на демо каждый прогон будет с «просрочкой».
- Зависимости `curriculum/catalog → teaching → training → assessment → reporting`, но `training → catalog` (кандидат карточки) — обратное ребро. Признано в 08, но в 01 §2 не оговорено.
- «Билеты и задачи» (источник данных ТЗ стр. 15) нигде не используются — а это готовый калибровочный набор для judge.
- `FOR SHARE` на lesson для каждой интерактивной команды — работает, но при желании упростить: проверять `lesson.epoch` под `run FOR UPDATE` с epoch, сохранённым в run при старте; stop обновляет epoch во всех runs занятия батчем. Не критично.
- Документ пишет «XML для конфигураций» как обязательный формат — в реальности это чекбокс: один XML-файл конфигурации рабочего места с XSD.
- `validation.md` честно указывает, что Mermaid-парсер не запускался и тесты core не гонялись — надо прогнать `go test ./...` в core перед переносом.

## 8. Что делать: MVP-срез для 1-го места

**Оставить как есть (ядро победы):** модульный монолит Go + PostgreSQL; перенос kernel из core (queue/lease/fencing/recovery + тесты); одна задача на реплику; stop-barrier по epoch; immutable snapshot; `RunEvidence → Assessment`; детерминированные правила + LLM-judge с evidence refs; append-only audit в транзакции; сессии + RBAC + scope; идемпотентные команды с `command_id`; SSE.

**Свернуть:** 9 контекстов → 5; outbox/inbox → прямые вызовы; два snapshot → один; `recovered_inputs` → отклонение после stop; `execution.scopes` → `run_id + dedup_key`; 14 task kinds → 5.

**Отложить в документацию («профиль поставки»):** HA/sync-реплика/fencing; ops-agent; OIDC; media chunks/barge-in; offline-bundle/SBOM.

**Добавить (чего нет, а жюри проверит):**
1. **UI**: макеты 6 экранов — карточка АРМ-112 по памятке стр. 15–18 (адрес, опросная карта, признаки, список оповещения с «карандашом»), входящий звонок, задача 2 с реакцией службы, монитор преподавателя со stop, конструктор сценария с частичным подтверждением и полем коррекции, отчёт с диаграммами. Стек выбрать в первый день.
2. **AI**: одна локальная модель (например Qwen2.5-3B/7B Instruct через vLLM или llama.cpp), JSON-schema для реплики (`text + disclosed_fact_ids`) и для judge (`criterion_id, status, score, evidence_refs, explanation`); калибровка на «Билетах и задачах» с 1–2 экспертными разметками; таблица precision/recall по критическим ошибкам — в презентацию.
3. **Голос**: текстовый режим first; затем browser WebRTC → gateway → Whisper/Vosk + Silero/Piper. Замерить транспорт (≤150 мс) и полный ответ (честно 2–5 с). Asterisk — только если останется время.
4. **Цифры для защиты**: k6 на 100 пользователей (чтение+команды), 100 транзакций/с с audit, отчёт ≤30 с, обрыв 30 с с replay — скрипты и raw-метрики в репозиторий.
5. **Безопасность**: TOTP для admin/instructor, lockout на login, партиции audit, `sslmode=verify-full` — всё дёшево, всё видно на защите.
6. **Питч**: сформулировать идею — «тренажёр, который не решает за ученика, а фиксирует и объясняет его ошибки с доказательствами; карточки учеников становятся следующими кейсами».

Если это сделать, архитектурный пакет становится не грузом, а козырем: у вас будет и работающий прототип, и документация уровня, которого у конкурентов не будет.
