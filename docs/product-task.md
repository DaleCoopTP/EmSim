Версия 1.0 · 17 сентября 2026 · статус: на согласование команды.

## 1. Problem statement

Учебно-методический центр ГО ЧС (УМЦ) готовит диспетчеров дежурно-диспетчерских служб (ДДС) города: районных ДДС, управляющих компаний, Мосводоканала, Мослифта и др. Диспетчер ДДС работает в АРМ-112: получает от системы-112 готовую карточку происшествия, принимает решение (принять / не принять), докладывает руководству по телефону, ведёт статусы реагирования до закрытия, пишет комментарии. Ошибки — отказ от профильного происшествия, пропущенный статус, искажённый адрес, отсутствие комментария при отказе — попадают в отдел контроля и в реальной жизни стоят времени реагирования.

Сейчас обучение идёт «делай как я» на бумажных билетах и без доступа к боевому АРМ-112. Нет тренажёра, на котором курсант отрабатывает карточку в интерфейсе, похожем на рабочий, под нормативное время, а преподаватель видит результаты по группе.

**Задача:** локальный веб-тренажёр, в котором группа курсантов одновременно отрабатывает карточки происшествий в копии интерфейса АРМ-112, а преподаватель готовит задания, наблюдает ход занятия, получает автоматическую оценку с возможностью её исправить и отчёты по прогрессу.

Что **не** решаем (снято заказчиком на Q&A, ТЗ в этой части устарело):
- приём звонка заявителя оператором 112 и заполнение карточки с нуля (ТЗ, сценарий 1) — «на следующий год» [40:58, 64:32];
- реальная IP-телефония, SIP, голосовой диалог с ветвлением [10:17–11:05, 39:01–43:23];
- интеграция с боевой системой-112 [36:22].

## 2. Пользователи и роли

| Роль | Кто | Что делает | Сколько |
|---|---|---|---|
| **Обучаемый** (диспетчер) | Курсант УМЦ, действующий или будущий диспетчер ДДС | Проходит занятие на своём рабочем месте: обрабатывает карточки, звонит, пишет комментарии. Смотрит свои результаты и историю | 20–30 в классе одновременно; до 100 в базе |
| **Преподаватель** | Методист УМЦ | Готовит и утверждает сценарии, раздаёт задания по рабочим местам, ведёт занятие (старт / монитор / стоп), проверяет и исправляет оценки, смотрит отчёты по группе | 1–2 на занятие |
| **Администратор** | Техник УМЦ | Ставит систему, заводит пользователей и рабочие места, следит за состоянием, делает backup. Не имеет доступа к содержимому занятий и оценкам | 1 |

Аутентификация: логин + пароль, три роли, без 2FA и без доменной интеграции — «всё, больше просто» [52:31–52:45]. Обучаемый привязан к номеру рабочего места (РМ), номер РМ попадает в отчёт.

## 3. Предметная область (то, что нельзя придумывать)

Всё ниже — из памятки АРМ-112, стр. 21–34. Интерфейс и правила должны «точно копировать рабочую программу, меньше самодеятельности» [25:24].

**Карточка происшествия** (то, что приходит из 112): номер, дата/время, телефон и ФИО заявителя, адрес (структурированный), формализованные признаки → итоговый тип по классификатору, текстовое описание, **список оповещения** — перечень служб, которым направлена карточка, со статусом каждой.

**Статусы реагирования службы** (пункт списка оповещения, который ведёт диспетчер):

```
Добавлена → Получена → Принята ──→ Начало реагирования → Прибытие → Проведение работ → Работы завершены
                     └→ Не принята (комментарий обязателен) → может стать Принята
              Принята / Начало / Прибытие / Работы ──→ Отказ (комментарий обязателен)
```

- «Получена» ставится автоматически при открытии карточки.
- «Работы завершены» и «Отказ» закрывают редактирование; ошибка после закрытия → «Сообщить в отдел контроля».
- Служба 103: вместо «Не принята / Отказ» — «Завершено без выезда бригады». Служба 104: комментарий не всегда обязателен.
- Норматив: отреагировать на направленную карточку в течение **30 с**; отработать карточку — **3 мин** [34:54–35:24].

**Нарушения из памятки** (стр. 26–31), которые тренажёр обязан ловить: карточка без первичного статуса («Не оповещено»); отказ от профильного происшествия; принятие непрофильного; отказ без комментария / без указания, куда передано; пропущенные этапы реагирования; искажение адреса в комментарии; не доложено руководству, когда требовалось.

**Классификатор** (XLSX, 1310 типов × 104 колонки): по признакам определяет итоговый тип и список служб для оповещения. Нужен, чтобы сгенерированные карточки были правдоподобны и чтобы знать, «профильное» ли происшествие для службы курсанта.

**Службы** в прототипе: 3–5 приоритетных ДДС (районная ДДС, УК, Мосводоканал, Мослифт — уточнить), с расширением через данные, не код [59:14].

## 4. Сценарии использования

### 4.1 Подготовка (преподаватель, до занятия)

1. Заводит/выбирает **сценарии**. Сценарий = карточка (все поля) + **эталон** (ожидаемое решение, обязательные элементы комментария, кому звонить, ожидаемая цепочка статусов, критические ошибки, лимиты времени) + **события** по таймлайну (например, через 40 с после принятия — сообщение «бригада выехала», через 90 с — «прибыли»; возможно — появление второй карточки) + сложность 1–10.
2. Источник сценариев: (а) ручной ввод; (б) 96 билетов заказчика; (в) генерация локальной LLM по категории/службе/сложности из билетов и классификатора. Сгенерированное — только черновик: преподаватель смотрит, правит, просит перегенерировать по комментарию, утверждает. Неутверждённое в занятие не попадает [ТЗ стр. 12–13, Q&A 21:46].
3. Утверждённому сценарию озвучиваются фразы принимающей стороны и события (мужские/женские голоса, интонация по категории) [40:02–40:16].

### 4.2 Занятие

1. Преподаватель создаёт занятие: выбирает **режим** и **уровень**, галочками назначает задания на рабочие места («первому — задание 1, пятому — задание 3») [54:01], стартует.
2. Обучаемый логинится на своём РМ, видит список карточек в интерфейсе АРМ-112. Карточки появляются по расписанию занятия; на уровне hard — новые приходят до завершения текущей.
3. По каждой карточке обучаемый: открывает (таймер 30 с) → читает → «Принята» / «Не принята» + комментарий → **звонит** руководителю бригады / начальнику по симулятору телефона: набирает номер, слышит «Слушаю вас», докладывает голосом, слышит «Информация принята» [39:29–40:35], заполняет запись «отработки» как в 112 — «Кто принял», «Суть сообщения» → по событиям сценария ведёт статусы → закрывает (таймер 3 мин) → следующая.
4. Преподаватель на своём ПК в реальном времени видит по каждому РМ: кто, какая карточка, статус, таймеры, последнее действие; может открыть ленту действий любого обучаемого. Может остановить занятие — незавершённые карточки фиксируются как прерванные.

### 4.3 Оценка (после карточки, автоматически)

Каждая закрытая карточка оценивается по настраиваемой рубрике (веса и пороги с дефолтами [27:46–34:13]):

| Критерий | Как | Чем |
|---|---|---|
| Время открытия ≤ 30 с, первичного статуса ≤ 30 с, отработки ≤ 3 мин | сравнение серверных меток | детерминированно |
| Первичное решение совпадает с эталоном; отказ от профильного — критическая ошибка | сравнение с эталоном | детерминированно |
| Комментарий есть там, где обязателен | правило | детерминированно |
| Цепочка статусов полная и в порядке, соответствует событиям сценария | сравнение с эталоном/событиями | детерминированно |
| Звонок сделан, когда требовался | факт действия | детерминированно |
| Содержание комментария: причина, куда передано, суть | локальная LLM по эталону | ИИ |
| Содержание доклада по телефону: адрес, тип, меры | STT записи → LLM | ИИ (пропускается, если STT недоступен) |
| Грамматика и опечатки; искажение адреса — критическая ошибка | LLM + сравнение адреса | ИИ + правило |

Итог — балл 0–100, критические ошибки ограничивают балл сверху, порог «зачёт». Рубрика (критерии, веса, критичность) одна на систему и версионируется; эталон каждого кейса может переопределить веса, объявить критерий критичным (искажение адреса при пострадавших) или отключить (LLM-проверка комментария там, где комментарий не нужен) — только отличия от дефолта, шкала 0–100 общая для всех кейсов. Оценка ИИ — предварительная: **преподаватель видит её, может исправить, исправленная становится итоговой** [14:12, 37:33]; исправления накапливаются как размеченные примеры.

### 4.4 Результаты и прогресс

- Обучаемый: свои карточки, баллы, разбор ошибок с ссылкой на пункт памятки, история по занятиям, текущий уровень и рекомендация.
- Преподаватель: по занятию и по группе — ФИО, номер РМ, балл, время, число грамматических ошибок, уровень; таблицы и графики; «кто лидер, кто отстаёт и почему» [53:04]; экспорт (CSV/PDF).
- **LLM-совет «над чем работать»**: по агрегатам ошибок обучаемого за занятие модель формулирует 3–5 предложений с ссылками на пункты памятки; попадает в отчёт и в ЛК.
- **Адаптивный уровень** («прогнозирование» [45:22]): по истории результатов система рекомендует перевести обучаемого на уровень выше/ниже; преподаватель подтверждает.

### 4.5 Режимы обучения

1. **Ознакомительный** — тот же интерфейс АРМ-112 с подсказками: что где находится, что означает каждый статус, пошаговое прохождение одной карточки без оценки.
2. **Тренировочный** — основной, три уровня:
   - *easy* — выборка простых типовых карточек, по одной, события с большим запасом времени;
   - *medium* — карточки сложнее (непрофильные, дубли, требующие отказа с обоснованием);
   - *hard* — medium + редкие/экзотические типы + новые карточки приходят каждые ~2,5 мин, не дожидаясь завершения текущей.

   Уровни отображаются на шкалу сложности 1–10 сценариев [57:45].

## 5. Функциональные требования (MVP)

Обязательно к защите:

- **F1** Логин/пароль, три роли, привязка обучаемого к РМ.
- **F2** Интерфейс АРМ-112: список карточек, карточка с аутентичными полями, список оповещения, смена статусов по правилам памятки (недопустимые переходы заблокированы), комментарии, кнопка «Сообщить в отдел контроля».
- **F3** Симулятор телефона: набор номера, воспроизведение фразы, запись микрофона, вторая фраза; запись сохраняется.
- **F4** События сценария по таймлайну (сообщения от бригады, появление новых карточек), таймеры 30 с / 3 мин.
- **F5** Сценарии: ручной ввод, импорт билетов, генерация LLM, правка, утверждение, сложность.
- **F6** Занятие: режим/уровень, назначение по РМ, старт, live-монитор, стоп.
- **F7** Автооценка по рубрике (детерминированная + ИИ), ревизия преподавателем.
- **F8** Результаты обучаемого, отчёты преподавателя (таблицы, графики, CSV, **PDF**), LLM-совет «над чем работать», рекомендация уровня.
- **F9** Ознакомительный режим с подсказками.
- **F10** Администрирование: пользователи, РМ, состояние сервисов, backup.

Желательно (если остаётся время): STT доклада и его оценка; импорт классификатора из XLSX в UI (иначе — скриптом при установке).

Roadmap (слайд, не код): звонок заявителя и заполнение карточки с нуля; SIP-телефония; MFA и доменная авторизация; мобильная версия.

## 7. Критерии успеха на защите

Жюри (эксперты УМЦ) оценивает «насколько похоже на наше видение, помощник в повседневной работе»; сложная модель с кучей параметров — минус, оригинальность сама по себе — не плюс [55:38–56:24]. Проверять будут произвольными сценариями и билетами с известными ответами [51:32].

Значит, побеждает:
1. Интерфейс, который эксперт узнаёт как АРМ-112.
2. Живой прогон: преподаватель раздал → 3–5 курсантов одновременно отработали (с телефоном) → монитор показал ход → оценка пришла и совпала с мнением эксперта → отчёт.
3. Генерация правдоподобной карточки из билета на глазах у жюри (заранее прогретая).
4. Цифры нагрузки на слайде (30 РМ, p95).

## 8. Неприятные технические вопросы (для discovery)

Ответы — там, где они уже следуют из требований; остальное — открыто.

| Вопрос | Ответ / статус |
|---|---|
| **Source of truth** для действий обучаемого? | Сервер. Клиент только отправляет команды; серверное время — единственное, по которому считаются нормативы. Клиентское время — справочно. |
| Что при **повторной отправке** команды (двойной клик, ретрай после обрыва)? | Команда несёт клиентский id; повтор возвращает тот же результат, второй раз не применяется. |
| Что **нельзя потерять**? | Журнал действий (основа оценки), записи звонков, ревизии оценок преподавателя, утверждённые сценарии. Всё в PostgreSQL + файлы; ежедневный backup. |
| Что если обучаемый **закрыл вкладку / отвалилась сеть**? | При переподключении получает текущее состояние карточки с сервера; таймеры идут на сервере и не сбрасываются; ненаправленный текст комментария хранится в браузере. |
| Что если преподаватель нажал **стоп**, а команда обучаемого в пути? | Команда отклоняется; карточка помечается «прервана», оценивается по тому, что успел сделать. |
| Что если **LLM недоступна / зависла / ответила мусором**? | Детерминированные критерии считаются всегда; ИИ-критерии → «требует проверки преподавателем», балл предварительный. Занятие не блокируется никогда. |
| Что если **STT не распознал** доклад? | Критерий содержания звонка пропускается, факт звонка засчитан. |
| Как понять, что **сценарий изменили** после того, как курсант его прошёл? | Утверждённая версия неизменяема; карточка ссылается на конкретную версию. |
| Изменение **рубрики/весов** задним числом? | Оценка хранит версию рубрики; пересчёт — явное действие преподавателя, старая оценка сохраняется как ревизия. |
| **Одна карточка — один обучаемый?** | Да. Один сценарий может быть выдан многим, но у каждого своя копия карточки. Конкуренции за одну запись нет. |
| Сколько **реально запросов**? | ~30 человек × действие раз в 10–20 с ≈ 2–3 запроса/с + 30 push-соединений. Один PostgreSQL — запас на три порядка. Тяжёлое (LLM, STT) — в фоновой очереди. |
| Что **уже есть** и переиспользуем? | `orchestration-core` (Go): очередь фоновых задач с lease/retry/reaper, HTTP-middleware, наблюдаемость — переносится. Его доменная модель (диалоги) — нет. |
| Какая **модель**? | Кандидат T-Lite 2.1 8B (Q4, ~5 ГБ RAM, ~40–90 с на оценку комментария на 6 ядрах); запасной — Qwen3-4B. Решается замером в первую неделю. |
| Откуда **голоса**? | Piper/Silero TTS при утверждении сценария, либо 10–20 заранее записанных файлов. В занятии синтеза нет. |
| **Открыто**: создаёт ли обучаемый карточку по звонку, поступившему напрямую в ДДС? | Задать заказчику анонимно. По умолчанию — нет, только карточки из 112. |
| **Открыто**: точный список приоритетных служб и их workflow-исключений. | Взять из памятки, подтвердить у заказчика. |
| **Открыто**: «дообучение по правкам преподавателя» — реальное дообучение или накопление примеров для промпта/оценки? | Для MVP — накопление размеченных примеров + few-shot; fine-tune — roadmap. |

## 9. Глоссарий

- **АРМ-112** — рабочее место диспетчера, в котором приходят карточки из системы-112.
- **Карточка** — запись о происшествии с полями и списком оповещения.
- **Список оповещения** — службы, которым направлена карточка; у каждой свой статус реагирования.
- **Сценарий** — карточка + эталон + события + сложность; учебная единица.
- **Занятие** — сеанс преподавателя с группой: назначения по РМ, старт, стоп.
- **РМ** — рабочее место, компьютер курсанта с номером.
- **Эталон** — ожидаемые действия по сценарию, по которым считается оценка.
- **Событие сценария** — сообщение или новая карточка, которое приходит обучаемому по таймеру.
- **Ревизия оценки** — исправление преподавателем автоматической оценки; хранится вместе с исходной.
