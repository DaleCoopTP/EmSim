# Разработка

## 1. Окружение

- Go 1.26
- Node.js 22 (только для веб-клиента)
- Docker — для интеграционных тестов (testcontainers) и e2e; без Docker интеграционные тесты можно запустить на отдельной пустой базе PostgreSQL 16
- Python 3 с `PyYAML` и `jsonschema` — для проверки контрактов

`go build` и `make verify` не требуют Node: в `web/dist` лежит заглушка, и бинарник собирается без веб-клиента. Такой `api` на любой путь вне `/api/` отвечает ошибкой с подсказкой выполнить `make web-build`.

## 2. Команды

```bash
make verify              # gofmt, сборка, go vet, unit-тесты, staticcheck
make verify-web          # веб-клиент: npm ci, генерация типов из OpenAPI, tsc, сборка
make test-integration    # интеграционные тесты на реальном PostgreSQL и процессах api/worker
make compose-config      # проверка compose-файлов без сборки образов
python3 design-docs/contracts/check.py   # проверка OpenAPI, JSON-схем и примеров
cd web && npm run lint   # oxlint
cd web && npm run test:e2e   # браузерные сценарии в изолированном compose-стеке
```

Без Docker:

```bash
TEST_DATABASE_URL="postgres://user@localhost:5432/emsim_test?sslmode=disable" \
  go test -tags=integration -count=1 ./test/integration/...
```

База должна быть отдельной и пустой: тесты пересоздают схему.

Разработка веб-клиента с горячей перезагрузкой — [web/README.md](../web/README.md).

## 3. Тесты

| Уровень | Где | Что проверяет | Объём |
|---|---|---|---|
| Unit | `internal/**/*_test.go`, `cmd/emsim/*_test.go` | доменные правила ДДС и 112, критерии рубрик, классификатор фактов заявителя, валидация сценариев, конфигурация | 649 тестов в 105 файлах |
| Интеграционные | `test/integration/` | очередь задач и восстановление, протокол команд и гонки, остановка как барьер, перезапуск сервера, SSE, полный путь «занятие → карточка → оценка → отчёт» через настоящие процессы `api` и `worker` | 134 теста в 52 файлах |
| e2e | `web/e2e/` | пользовательские сценарии в Chromium поверх отдельного compose-стека: ДДС, все маршруты 112, чат с заявителем, диктовка, редактор сценариев, настройка занятия, экраны администратора | 16 сценариев в 13 файлах |
| Контракты | `design-docs/contracts/check.py` | схемы, примеры, ссылки OpenAPI; при заданном `DATABASE_URL` — инварианты DDL | — |

e2e-стек поднимается без моделей (`compose.no-llm.yaml`, диктовка — заглушка), в качестве микрофона подаётся WAV из `seed/voice-assets/`. После прогона удаляются только его контейнеры и тома.

Точность ИИ-судьи комментариев ДДС измеряется отдельно на живой модели:

```bash
JUDGE_LLM_URL=… JUDGE_LLM_MODEL=… \
  go test -tags=llmlive -run Live -v ./internal/assessment/dds/commentjudge/
```

Размеченный набор — `internal/assessment/dds/commentjudge/testdata/comments.json`.

## 4. CI

GitHub Actions (`.github/workflows/verify.yml`) на каждый push: `make verify` и `make compose-config`, `make test-integration`, `make verify-web` и e2e в браузере. Проверку контрактов и линт веб-клиента запускают локально.

## 5. Соглашения

- **Границы модулей.** Модуль пишет только в свои таблицы; чужие данные — через интерфейсы, объявленные у потребителя. Сборка — только в `cmd/emsim`. Новых сетевых сервисов между модулями не вводим.
- **Транзакции.** Доменное изменение, аудит, уведомление и постановка задачи — одна транзакция `pgx.Tx`; commit и rollback делает вызывающий код.
- **Миграции** только вперёд, в `migrations/`, семантика PostgreSQL 16.
- **Контракты.** Изменение внешнего поведения обновляет `openapi.yaml` и JSON-схемы в том же изменении.
- **Неизменяемость.** Утверждённая версия сценария, снимок прохождения, отправленная карточка 112 и ревизии оценки не редактируются — только новая версия или ревизия.
- **Секреты.** Эталоны и скрытые факты не попадают в ответы обучаемому; логи не содержат паролей, текстов и ФИО.
- **Модели** вызываются только вне транзакций команд, в узко разрешённых местах (см. [architecture.md](architecture.md#8-модели)).
- **Стиль.** `gofmt`, стандартная библиотека, если зависимость не даёт явной пользы; ошибки наружу — безопасные коды, детали — в структурированных логах.

## 6. Как добавить сценарий

Сценарий 112 с ИИ-заявителем удобнее создавать в веб-редакторе. Сценарий ДДС или 112 с подготовленным диалогом — JSON-файлом в `seed/scenarios/`: формат описан в [seed/README.md](../seed/README.md) и схеме [scenario-file.schema.json](../design-docs/contracts/scenario-file.schema.json). Затем `make seed` или `emsim import seed`. Изменение существующего сценария — новый файл с тем же `key` и `version` на 1 больше.

## 7. Архитектурные решения

Значимое изменение архитектуры оформляется новым ADR в `design-docs/adr/` до реализации: контекст, варианты, решение, последствия. Изменение прежнего решения — новый ADR со ссылкой на заменяемый.
