# Архитектурное решение

## 1. Граница продукта

EmSim — автономный учебный комплекс. Он имитирует диалог заявителя с оператором, заполнение карточки и работу ДДС с карточками. Реальные вызовы, реальные отправки экстренным службам, подключение к промышленной 112 и внешний интернет в runtime исключены. Интеграция с инфраструктурой означает локальный доступ, SIP, мониторинг, форматы и визуальное соответствие.

Все ресурсы поставляются локально: web bundle, шрифты, справочники адресов, при необходимости картографические тайлы, модели и токенизаторы, методические материалы, образы и зависимости. Веб-интерфейс на русском языке с адаптивной компоновкой. CLI из DDD-наброска допустим как отладочный адаптер, но не закрывает обязательный пользовательский интерфейс.

Два обязательных режима:

- **`call_card` (задача 1):** входящий учебный текстовый/голосовой вызов → разговор с заявителем → ручное заполнение карточки → сохранение → оценка разговора, карточки и времени.
- **`card_workflow` (задача 2):** случайная карточка из выбранного преподавателем источника → действия профильной службы → завершение карточки → следующая карточка до остановки занятия.

Название `Patient Simulator` из исходных схем заменяется в публичном языке на `CallerSimulator` / «симулятор заявителя»: медицинские ситуации — только часть кейсов.

## 2. Размещение и границы модулей

Начальная продуктовая архитектура — **модульный монолит по бизнес-логике, несколько процессов по профилю нагрузки**. Bounded context не означает отдельный микросервис. Один Go-модуль, явные порты, отдельные PostgreSQL schemas и владельцы таблиц; API не держит состояние сессии в памяти. UI — TypeScript web application. Конкретный UI framework не влияет на доменные контракты.

| Контекст / модуль | Ответственность и владелец | Не делает |
|---|---|---|
| `identity` | Пользователи, аутентификация, роли, полномочия, привязка локального IdP, блокировка | Не назначает учебные задания |
| `curriculum` | Сценарии/версии, эталоны, рубрики, сложность, генерация, материалы, публикация | Не изменяет опубликованный снимок активного прогона |
| `catalog` | Версии ЕКП, службы, правила соответствия признаков, карточки-источники и происхождение | Не использует чужой результат как автоматически правильный эталон |
| `teaching` | Группы, занятия, назначения, политики времени/выборки, start/finish/stop, мониторинг | Не исполняет LLM и не хранит горячие реплики |
| `training` — core domain | Прохождение, элементы, чат, черновик карточки, действия, workflow, evidence | Не вычисляет итоговую оценку и не меняет IAM |
| `assessment` — core domain | Детерминированная оценка, семантика/грамматика, доказательства ошибок, агрегирование, экспертные ревизии | Не меняет исходное прохождение |
| `reporting` | История, прогресс, проекции, отчёты, CSV/PDF, групповые рекомендации | Не запускает повторный judge при запросе отчёта |
| `operations` | Аудит, техсостояние, разрешённые административные операции, backup/restore/update | Не даёт техническому администратору право менять оценки |
| `platform/execution` | Durable tasks, leases, retries, fencing, recovery, worker lifecycle | Не знает, что такое правильный ответ оператора |
| Адаптеры `media`, `inference`, `postgres`, `http` | Протоколы и внешние устройства внутри контура | Не являются самостоятельными учебными доменами |

Зависимости: `curriculum/catalog → teaching → training → assessment → reporting`. Стрелка означает предоставление версионированного контракта, не импорт всей внутренней реализации. IAM проверяется на входе и в application services. Аудит вызывается портом в той же транзакции. Composition root связывает реализации.

Публикуемый язык между доменами: `PublishedScenario`, `LessonPlanSnapshot`, `CardSourceSnapshot`, `RunEvidenceV1`, `AssessmentResultV1`. Отдельные DTO для оператора и преподавателя: скрытые факты, эталоны, ключи критериев и prompts не попадают в DTO оператора.

## 3. Агрегаты и инварианты

| Агрегат | Состав | Основные инварианты |
|---|---|---|
| `Scenario` | Identity, mutable draft, immutable versions | Назначать можно только опубликованные версии; частично одобренные материалы остаются draft, либо публикуется только одобренное полное подмножество кейсов |
| `Lesson` | Преподаватель, группа, режим, план, состояние, epoch | Start замораживает план/выборку; stop запрещает новые изменения всех участников в одной линейной точке |
| `Assignment` | Оператор, lesson, service profile, attempt policy | Оператор видит своё назначение; повторная попытка — новый run; максимум активных попыток задаёт политика |
| `TrainingRun` | Assignment, snapshot, run state, active item, event sequence, epoch | Один активный item по умолчанию; подтверждённые события упорядочены; terminal-run не возобновляется |
| `RunItem` | Сценарий/исходная карточка, conversation, card, reactions | Горячая запись сериализуется run-lock; принадлежность item/run неизменна; transcript хранится построчно, не загружается целиком для любой команды |
| `IncidentCard` | Адрес, заявитель, признаки, описание, список служб | Структурно корректна; автоматически добавленные службы оператор не удаляет; task 2 не даёт редактировать входную карточку как автору |
| `ServiceReaction` | ServiceId, статус, история комментариев | Пользователь действует только за назначенную службу; terminal-реакция закрыта для редактирования; отказ требует комментария с учётом опубликованного правила службы |
| `Assessment` | Evidence ref/digest, rubric snapshot, компоненты, ревизии | Один результат версии на комбинацию evidence+rubric+evaluator; ошибка вычисления не преобразуется в 0 баллов |
| `CardTemplate` | Source kind, immutable snapshot, provenance, approval | Ученическая карточка обезличена и утверждена; её корректность не предполагается; эталон проверяется отдельно |

`RunItem`, `IncidentCard` и `ServiceReaction` логически относятся к `training`, но для первой реализации consistency boundary изменения — `TrainingRun` + активный item. Это исключает сложную eventual consistency между карточкой и её доказательствами. Большие коллекции событий и сообщений — append-only таблицы, не поля загружаемого Go-объекта. Выделить item в независимый aggregate можно, если потребуется несколько одновременно активных карточек у одного оператора.

Снимки двух уровней: `RunSnapshot` фиксирует общий план, профиль службы, правила времени/выборки и manifest разрешённых версий; `ItemSnapshot` фиксирует конкретный выбранный сценарий/карточку, её эталон, рубрику и исходные реакции служб. Это необходимо для run с несколькими разными карточками: один общий эталон не подходит всем item. Frozen source pool уже содержит допустимые пары source/scenario/rubric versions; выдача item не читает `latest`.

### Независимые оси состояния

- Lesson: `draft → ready → running → stopping → finished`; причина завершения отдельно (`normal`, `instructor_stop`, `technical_abort`).
- Run: `active → sealing → completed | stopped | failed`; `failed` только техническая невозможность продолжить, `stopped` — решение преподавателя/досрочное прекращение. Завершение всего run не является синонимом окончания отдельной карточки.
- Item: `offered → in_progress → submitted | interrupted | technical_failure`.
- Assessment: `pending → evaluating → ready | needs_review | unavailable`; новая оценка — новая revision, не перезапись старой.
- Task: `pending → leased → done | failed | dead_letter | cancelled`; retry возвращает в `pending`.
- Media connectivity (`connected`, `reconnecting`, `disconnected`) не является состоянием учебной успешности.

## 4. Подготовка занятия

1. Преподаватель выбирает несколько категорий ЕКП, сложность, режим, локацию и параметры заявителя.
2. `GenerateScenario` ставит durable job. Локальная LLM выдаёт draft по JSON schema, используя утверждённый набор материалов. Генерация не публикует результат сама.
3. Сервер проверяет ссылки ЕКП, структуру, полноту эталона, допустимость workflow и отсутствие противоречий между фактами/оценкой. Неоднозначные факты показываются преподавателю.
4. Преподаватель просматривает вопросы и правильные действия, редактирует, вводит комментарий для регенерации выбранного фрагмента, запускает проверку грамматики, утверждает.
5. Публикация фиксирует версии scenario/rubric/classifier/workflow/materials, manifests моделей и prompts. Удаление опубликованной версии — архивирование; она сохраняется для старых попыток.
6. Создание lesson фиксирует назначения операторов и их профиль службы/территории. Start делает снимок плана и eligible source pool; дальнейшее редактирование создаёт новое занятие/версию.

Для задачи 2 `SourcePolicy` содержит `system`, `student`, `mixed`, фильтры категорий/сложности/службы, веса источников, seed и repeat policy. «Системные» включают подготовленные и утверждённые сгенерированные карточки. Для `mixed` проектный default — 50/50, без молчаливой замены пустого источника; преподаватель видит невозможность запустить такой набор. Политика исчерпания явно выбрана: остановить выдачу с `pool_exhausted` либо начать следующий перемешанный цикл. Выдача детерминирована по seed и сохранённому порядку источников; фактический выбор обязательно сохраняется.

Ученическая карточка поступает из **завершённого item задачи 1**: копирование → обезличивание → preview → утверждение преподавателем → новая `CardTemplateVersion`. Ссылка на исходный run доступна только уполномоченному преподавателю; получатель карточки не видит автора. Карточку с ошибками можно использовать как отдельный утверждённый учебный кейс с корректным эталоном действий; исходные ошибки нельзя выдавать за нормативный ответ.

## 5. Задача 1: диалог и заполнение карточки

`StartRun` атомарно создаёт run, item, snapshot, первый `simulator.turn` task и event. Задача симулятора создаёт одну законченную реплику заявителя. После этого worker свободен, даже если оператор думает несколько минут.

Каждое сообщение оператора сначала фиксируется в IndexedDB, затем отправляется командой с `command_id`, `expected_version`, `client_seq`, `item_id` и `interaction_epoch`. В транзакции сервер проверяет полномочия, активность lesson/run/item, дедупликацию и версию; сохраняет сообщение, событие, аудит и следующую задачу симулятора. Ответ API содержит подтверждённую версию и sequence. До ACK интерфейс не показывает «сохранено на сервере».

`simulator.turn` получает сохранённые факты, disclosure state, предыдущие сообщения и конфигурацию. Вызов inference идёт вне транзакции. Результат публикуется только при актуальных lesson/run epochs, lease token и `pending_turn_id`. Одновременно допускается один ответ симулятора на conversation. Несколько новых реплик оператора могут быть объединены в следующий вход или отклонены `turn_in_progress` по опубликованной turn policy; default — одна ожидающая ответ реплика. Редактирование карточки при этом разрешено и не инвалидирует LLM-ответ: fencing по conversation epoch/turn, а не по общей версии каждого поля карточки.

Факты и раскрытие отделены от текста: `DisclosurePolicy` определяет разрешённые fact IDs; LLM формулирует ответ. Выдуманные/противоречащие фактам значения блокируются валидатором; bounded retry, затем утверждённая fallback-реплика и сигнал инструктору. Семантическая полнота проверки не гарантируется схемой JSON — нужна предметная оценка качества модели на тестовых кейсах.

Заполнение карточки — отдельные команды; сохранение черновика не запускает judge. `SubmitItem` фиксирует окончательную карточку и закрывает диалог. `EvidenceBuilder` создаёт нормализованный вход оценки: transcript, версии карточки, принятые/отклонённые действия, временные отметки, техпаузы, snapshot. При следующих кейсах создаётся новый item. Закрытие run формирует итог по всем item.

## 6. Задача 2: действия с карточками

`OfferNextCard` под блокировками lesson/run проверяет, что занятие продолжается и активной карточки нет, выбирает следующий source из frozen pool, создаёт рабочую копию карточки и реакцию назначенной службы. Один command ID даёт один item. Если stop получил блокировку первым, новая карточка не выдаётся.

Список оповещения рассчитывается по **версии ЕКП**: сочетание признаков → итоговый тип → условные правила маршрутизации служб. XLSX — не плоский список названий: первые три строки составляют многоуровневую шапку, дополнительные признаки влияют на набор служб. Импортёр нормализует данные с provenance до исходной ячейки и отчётом неоднозначностей; не forward-fill произвольные пустые ячейки. Политики территорий/компетенций задаются отдельно, если отсутствуют в классификаторе.

Статусы реагирования по памятке:

- `added` — служба включена; `received` — карточка открыта/получена (технические события).
- Первичный ответ: `accepted` либо `not_accepted`; норматив по умолчанию 30 секунд **с направления карточки службе**, не с открытия.
- `not_accepted → accepted` разрешён; комментарий при `not_accepted` обязателен по правилу службы.
- После `accepted` доступны этапы `responding`, `arrived`, `working`, `completed`, `refused`. Нельзя навязать обязательное прохождение каждого промежуточного этапа: памятка на стр. 25 показывает варианты после принятия. Допустимость скачков определяется версией workflow и фиксируется в рубрике; отсутствие необходимых по кейсу этапов оценивается отдельно.
- `completed` и `refused` закрывают редактирование реакции этой службы. Прямого перевода обратно в `accepted` нет; учебное обращение к контролю — отдельное действие, не скрытое изменение истории.
- Для 103 используются исключения (`completed_without_team` вместо двух отказов); для 104 — версия правила обязательности комментария, а не глобальное послабление для всех служб (памятка, стр. 23).

Статус всей карточки выводится отдельно из состояния регистрации/проверки и набора реакций: `registered`, `processed`, `checked`, `unnotified`, `refusal`, `unfinished`, `completed`. Тревожные признаки допускают одновременное существование; UI выбирает приоритет отображения по версии политики и показывает остальные флаги. `unnotified` возникает при просрочке первичного статуса; `unfinished` — после 48 часов по памятке. Для тренажёра ускоренное время задаётся явно в snapshot и не смешивается с реальным таймером реакции оператора.

**Разделение допустимости и правильности:** нельзя менять чужую службу/закрытый item/недопустимый переход. Но содержательно неверный отказ с формально заполненным комментарием должен сохраниться и получить ошибку при оценке. Иначе UI решал бы задачу за обучающегося. Отклонённые попытки команд тоже сохраняются как evidence при валидной авторизации.

Дополнительные действия: комментарий, направление/запрос другой службы, обращение к контролю, завершение карточки. Они моделируют учебные операции; никаких реальных внешних звонков. Для упражнений ДДС «вызвать другую службу» — имитация запроса по процедуре памятки, не произвольное редактирование статусов другой службы.

## 7. Время и остановка преподавателем

Тайминги — `TimingPolicy`: `primary_response_limit=30s` по умолчанию; длительность диалога, заполнения карточки и занятия — отдельные параметры. Базовый норматив ТЗ 30 сек применяется к заданному преподавателем измеряемому действию; не означает, что любой полный голосовой разговор должен длиться 30 сек. Начальная и конечная точки каждой метрики зафиксированы в рубрике.

Конкретные defaults редактора: для задачи 1 `card_fill_limit=30s` от открытия карточки для ввода при принятии вызова до `SubmitItem`; для задачи 2 `primary_response_limit=30s` от направления карточки службе до первичного статуса. Это независимые настройки, явно показанные преподавателю и замороженные в snapshot. Полная длительность разговора/занятия и hard timeout настраиваются отдельно.

Источник времени — сервер/БД, синхронизированные локальным NTP. UI считает countdown от server time. Планировщик хранит deadlines в БД, восстанавливает пропущенные таймеры после рестарта. Истечение норматива ставит факт просрочки, а не обязательно закрывает item; hard timeout задаётся отдельно.

`FinishLesson` и `StopLesson` немедленно закрывают приём новых учебных действий и выдачу карточек. Отличие — `normal` или `instructor_stop`, полнота текущих item и статус в отчёте. Оба сохраняют накопленное и инициируют оценку имеющихся данных. `AbortLesson` предназначен для технического прекращения, не обнуляет успеваемость.

**Точка остановки:** транзакция блокирует lesson, меняет `running → stopping`, увеличивает `interaction_epoch`, пишет `stopped_at`, audit, event и job завершения. Все команды и commits интерактивных workers обязаны сначала взять совместимую shared-блокировку lesson и проверить состояние. Поэтому после commit stop ни один поздний LLM-ответ или next-card не может примениться. Запрос stop не ждёт LLM и не держит блокировку на время сетевого вызова.

Затем maintenance идемпотентно обрабатывает runs: замораживает `cutoff_seq`, помечает текущий item `interrupted`, отменяет `simulator.turn` и команды воспроизведения media, создаёт evidence и assessment job, переводит run в `stopped`. Уже завершённые item и assessments сохраняются. Judge, sealing, отчёт и операции сохранения — **не отменяются вместе с интерактивными задачами**. Lesson становится `finished`, когда все runs sealed; итоговые оценки могут ещё быть `pending`. Сломанный judge не удерживает занятие открытым.

## 8. Оценка и прогресс

Вход `RunEvidenceV1` неизменяем и включает `evidence_digest`, snapshot/rubric/classifier/workflow versions, message/action refs, карточку, нормативы, часы событий, stop reason и полноту записи. Нормализаторы двух режимов различны, общий формат результатов един.

| Компонент | Метод | Пример доказательства |
|---|---|---|
| Структура и обязательные поля | Детерминированные правила | `card.address.house` отсутствует |
| Классификация и службы | ЕКП и правила компетенций | Требуемая служба отсутствует в оповещении |
| Последовательность действий | Workflow + rubric | Отказ после принятия без причины |
| Тайминг | Серверные события + timing policy | `first_reaction=42s`, `limit=30s`, `overrun=12s` |
| Содержание карточки / комментария | Локальный semantic judge | Отрицание «пострадавших нет» пропущено; ссылка на реплику и поле |
| Грамматика | Локальный evaluator | Диапазон текста, ошибка, предлагаемая коррекция |
| Общение / раскрытие фактов | LLM + сценарные критерии | Не уточнён адрес; evidence IDs, без выдуманной цитаты |

Каждый критерий: `criterion_id`, `status=met|not_met|partial|not_applicable|unavailable`, `score`, `weight`, `evidence_refs`, `explanation`. Структурная валидация проверяет диапазоны, ссылки и соответствие rubric IDs. Текст ученика/материалов считается данными, не инструкциями judge. LLM не имеет инструментов записи и доступа к произвольной сети.

Агрегатор считает `100 × Σ(weight × normalized_score) / Σ(applicable_weight)`; правила critical errors, partial credit, округления и pass threshold — в версии рубрики. `not_applicable` исключается из знаменателя, `unavailable` **не исключается молча**: итог остаётся provisional/needs_review до экспертного решения. Недостаточные данные, обрыв media и stop не равны провалу; отчёт явно показывает coverage. Прогресс сравнивает только совместимые версии шкал либо выводит отдельные серии.

Преподаватель может оставить комментарий, подтвердить или изменить результат с обязательной причиной; создаётся `AssessmentRevision` с before/after, actor, time и audit. Автоматическая оценка остаётся неизменной. Пользователь видит автоматическую и экспертную версии и опубликованный итог. Новый judge run с той же рубрикой — новая evaluator revision по явной команде, не скрытый пересчёт исторической оценки.

`Reporting` поддерживает результаты item/run, историю оператора, прогресс по навыкам/сложности, распределение ошибок группы, время реакции и превышение норматива. Проекции обновляются из versioned events; уникальный event ID исключает двойной учёт. После корректировки оценки вклад старой версии заменяется новой, а не добавляется ещё одна попытка. Отчёт читает готовые результаты и показывает время актуальности/незавершённые оценки. Групповые AI-рекомендации рассчитываются фоном на агрегатах и имеют ссылки на типовые ошибки.

## 9. Голос и локальный inference

Media plane отделён от control plane:

`Web browser ↔ WSS/SIP + WebRTC DTLS-SRTP ↔ Asterisk ↔ local media gateway ↔ streaming STT / CallerSimulator / TTS`.

IP-телефон использует локальные SIP-TLS/SRTP endpoints. PSTN trunks и внешние маршруты отсутствуют; dialplan допускает только учебные extensions. Для удалённого контроля — управляемая сеть/VPN учебного центра и локальный TURN при необходимости. Развёртывание WebRTC в Asterisk требует соответствующих защищённых transport/media настроек; это подтверждается [документацией Asterisk](https://docs.asterisk.org/Configuration/WebRTC/Configuring-Asterisk-for-WebRTC-Clients/).

Media gateway принимает аудио, VAD/STT сегментирует высказывания, финальные сегменты становятся командами training с детерминированным `utterance_id`. Partial STT отображается временно и не является подтверждённым evidence. Полная реплика заявителя сначала сохраняется, затем TTS воспроизводит её; запись фиксирует реально воспроизведённые диапазоны и прерывания. Barge-in увеличивает `playback_epoch`; запоздавшее аудио старой реплики отбрасывается. Внешнее физическое воспроизведение нельзя гарантировать exactly-once: `playback_id` и progress предотвращают автоматический повтор уже подтверждённого воспроизведения; неопределённый исход требует восстановления текущего состояния звонка, а не повтора всего ответа.

Звонки привязаны к `media_session_id`, run/item и connection epoch. Контрольная команда stop прекращает bridge/playback; короткоживущая подписанная media authorization проверяется периодически, чтобы потеря уведомления не оставила независимый звонок навсегда. Фактический бюджет отключения — измеряемый критерий испытаний.

**150 мс:** отдельно измеряется односторонняя задержка аудиотранспорта в LAN (capture/packetization/network/jitter/decode). Время распознавания, очереди LLM, генерации и синтеза — отдельная метрика ответа заявителя. Для неё проектный UX-бюджет начального ответа — до 2 сек, если заказчик включает его в общий отклик; достижимость проверяется spike на выбранном железе. Асинхронность не сокращает inference latency.

Пулы inference изолированы: interactive turn/STT/TTS получают резерв мощности; judge и генерация — отдельные квоты. Ограничение выставляется на весь локальный inference endpoint, а не на каждый API-процесс; реализация admission в gateway или общей DB-таблице permits с leases. Число workers не равно числу доступных GPU slots. Модель/квантизация/CPU-GPU профиль выбираются испытанием качества и нагрузки, а не предположением о 20 LLM-ответах одновременно.

На минимальном сервере из ТЗ GPU не указан. Продукт должен иметь CPU-профиль локального запуска и отдельный опциональный ускоренный inference host. Соответствие минимальному железу при полной нагрузке — обязательный ранний gate. Если модель не укладывается, меняются модель/промпты/подготовка реплик либо согласуется ресурсный профиль; нельзя объявлять обязательным GPU и считать исходное требование выполненным.

## 10. Сеть, восстановление и границы сохранности

Browser сохраняет черновики, command IDs и сообщения до отправки в IndexedDB. ACK выдаётся только после DB commit; повтор после потерянного ответа возвращает тот же результат. Reconnect читает snapshot + `last_event_seq`, затем догружает события и повторяет неподтверждённые команды в исходном порядке. При конфликте версия не перетирается: приложение предлагает восстановленный черновик и повтор валидной команды.

SSE — доставка сохранённых событий конкретного run, `id=run_id:sequence`, после reconnect возможны дубли. Сервер хранит факты, клиент дедуплицирует. `LISTEN/NOTIFY` может будить reader, но не заменяет журнал; fallback poll читает БД. [PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html) используется только как сигнал. [SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) предоставляет event IDs и reconnect, но replay реализуется сервером. Instructor dashboard читает компактную проекцию с poll ≤1 сек и открывает SSE только для выбранного run, не 100 отдельных потоков.

При коротком обрыве сеть возвращается, команды досылаются, состояние продолжает существовать. Если за время обрыва занятие остановлено, восстановленные данные сохраняются в `recovered_inputs`, но не изменяют sealed evidence и оценку автоматически. Инструктор может создать явно отмеченную ревизию с supplemental evidence. Это сохраняет данные и не позволяет задним числом обойти stop. `client_occurred_at` — вспомогательная метка, не доверенный источник времени; offline-тайминг отмечается для разбора, автоматическое наказание за технический сбой исключено.

Аудио требует отдельного решения: browser capture записывает локальные пронумерованные chunks, media gateway пишет серверные сегменты; после восстановления загружаются недостающие локальные chunks с digest. При полном разрыве пути IP-телефона без локальной записи несохранённый звук восстановить нельзя. В приёмочной конфигурации такой endpoint должен иметь локальную запись/шлюз либо при потере media разговор явно приостанавливается и просит повторить незаписанную реплику. Нельзя обещать одновременно непрерывный звонок, потерю сети и отсутствие пропавшего несохранённого звука. Граница «без потери данных» и допустимая пауза должны быть зафиксированы в протоколе испытаний до реализации voice path.

RTO reconnect: проверять и обрыв длительностью до 30 сек, и автоматическое восстановление в пределах 30 сек после возврата связи; второй предел — консервативная проектная конкретизация. RPO=0 для подтверждённых данных требует устойчивого PostgreSQL commit; при отказе узла БД — синхронной реплики и fencing старого primary. Ежедневный backup сам по себе RPO=0 не обеспечивает.

## 11. Доступ, аудит, эксплуатация

Аутентификация через локальный IdP (OIDC adapter) либо встроенные локальные учётные записи. Session cookies `HttpOnly`, `Secure`, `SameSite`, CSRF для команд; refresh/revocation через server-side session store. JWT — допустимый вариант, но не обязательное требование. Для privileged операций — повторная аутентификация/локальный второй фактор согласно политике учреждения. Интеграционный механизм локальной системы доступа подтверждается discovery; порт не зависит от конкретного поставщика.

Authorization = роль + принадлежность ресурса + назначенная группа/служба + конкретное permission. Администратор по умолчанию не видит учебные тексты/персональные данные и не меняет оценки/сценарии; преподаватель не видит чужие занятия; оператор не видит чужие результаты. ACL применяется к REST, SSE, скачиванию файлов, media token и запросам отчётности. Блокировка пользователя отзывает активные сессии и подписки.

TLS используется на всех сетевых hop внутри контура: reverse proxy→API, PostgreSQL `verify-full`, object storage, inference, SIP signaling; media — SRTP. Закрытая сеть не заменяет шифрование. Локальная CA, выдача/ротация сертификатов и сроков действия входят в install/runbook. Секреты не входят в immutable snapshots или metrics.

Аудит append-only: actor, action, resource, scope, request/command ID, server time, outcome, before/after refs, причина. Успешная бизнес-команда и audit фиксируются атомарно; denied/login/read/export тоже имеют audit path. Пароли, cookies, полные prompts и сырой чувствительный текст не логируются. Audit writer не имеет UPDATE/DELETE; отдельная retention/backup роль. Журналы безопасности — минимум 6 календарных месяцев, защита от раннего удаления, архивирование на независимый локальный storage; полный срок хранения учебных результатов задаётся политикой учреждения.

Административный UI обращается к `operations` API. Отдельный `ops-agent` с минимальными правами выполняет только allowlist действий: restart утверждённого сервиса, backup, verify, restore/update по процедуре. API не получает Docker socket и произвольный shell. Остановка самой платформы управляется внешним supervisor/локальной консолью, иначе UI не сможет себя включить. Изменения конфигурации версионируются, валидируются и применяются с audit.

Backup не реже одного раза в сутки: PostgreSQL + object manifests/версии аудио и материалов + конфигурация, сертификаты/секреты отдельным защищённым набором. «Внешний S3» из предложений означает **другой узел/хранилище внутри локального контура**, не публичное облако. WAL archive/PITR дополняют ежедневный backup. Restore в чистый контур обязан проверить FK, hashes, последний audit, роли, аудио и запуск двух учебных сценариев.

HA-профиль для обязательной устойчивости к потере узла: два API, реплицируемые workers, PostgreSQL primary + synchronous standby + quorum/fencing, независимый backup, реплицируемый object storage, резерв media/inference ёмкости. Single-node Compose — профиль разработки/демо и сам по себе не закрывает отказ узла. Active RTP при падении media-node может потребовать повторного подключения; сохранность данных отделена от непрерывности аудиопотока. Особенности synchronous replication описаны в [документации PostgreSQL](https://www.postgresql.org/docs/current/warm-standby.html).

```text
    domain/{run,item,card,reaction,conversation,timing}/
    application/{start,command,turn,nextcard,seal,reconnect}/
    ports/              # CallerSimulator, SnapshotReader, Transaction
    adapters/{postgres,http}/
  assessment/{domain,application,ports,adapters}/
  reporting/{application,projections,adapters}/
  operations/{application,audit,adapters}/

```

Domain packages не импортируют pgx, HTTP, vendor LLM SDK или другой bounded context. Application services зависят от узких ports. Адаптеры БД реализуют специальные транзакционные операции (например, `ApplyCommand`, `CommitTurn`, `SealRun`), а не раздают произвольный SQL любому модулю. Межмодульный process manager находится в composition/application слое и вызывает scoped transaction API; одной общей `Repository.SaveEverything` нет.

UI screens: оператор — назначения, АРМ, входящий звонок, таймеры, connection/unsaved indicator, история и разбор; преподаватель — scenario builder/review, набор карточек, группы/назначения, мониторинг, stop, экспертная оценка и отчёты; администратор — пользователи, настройки, metrics/logs, backups и обновления. Преподаватель видит две шкалы: прохождение и готовность оценки. Материалы доступны локально, мобильная версия переупорядочивает панели, не скрывая обязательные действия.
