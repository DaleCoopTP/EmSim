# Архитектурные решения и защита

## ADR-01. Модульный монолит, отдельные процессы по нагрузке

**Решение:** один продуктовый Go-модуль и PostgreSQL, доменные модули с ports, API/workers/media/ops раздельно. Для 100 пользователей и 20 сессий ключевой риск — inference/media и сохранность, а не отсутствие микросервисов. Локальные транзакции значительно упрощают stop/evidence/task атомарность.

**Цена:** дисциплина импортов и владельцев таблиц; shared DB требует согласованных migrations. **Альтернатива:** микросервис на каждый context увеличивает distributed transaction/outbox/reconciliation работу без доказанной потребности. **Когда пересмотреть:** независимые команды/релизы или измеренная изоляция нагрузки/безопасности потребуют выделения конкретного модуля. Media и inference уже имеют границы процесса.

## ADR-02. Переносить kernel core, а не всё приложение без изменений

**Решение:** сохранить lease/fencing/retry/atomic enqueue/snapshot protocols; заменить interactive domain и scoring. В исходном коде bot-to-bot loop, binary score, dialogue foreign keys и отсутствие cancellation объективно не соответствуют учебному flow.

**Цена:** generic queue/SQL всё равно требует адаптации, новые tests обязательны. **Альтернатива:** адаптировать человека как `ClientBot` с долгим ожиданием; это занимает leased worker, усложняет restart и не сохраняет каждый шаг. **Когда пересмотреть:** для автономной оценки моделей старый pipeline полезен как отдельный harness.

## ADR-03. Занятие и техническая задача — разные сущности

**Решение:** Lesson→Assignment→Run→Item и отдельный Task. Source pool/stop instructor — уровень lesson; успех оператора — assessment; worker state — execution.

**Цена:** больше явных сущностей. **Альтернатива:** одно поле `run.status` для всех процессов делает невозможным различить завершённое обучение, ожидающую оценку, прерванный звонок и упавший worker. **Защита:** границы совпадают с владельцами решений, а не с текущими таблицами core.

## ADR-04. Одна durable task на ответ симулятора

**Решение:** вход оператора зафиксирован → turn task → fenced output commit. Ожидание пользователя — состояние run, без worker. **Цена:** несколько SQL транзакций вместо одного batch commit. **Выгода:** прогресс/восстановление/stop на границе каждого действия. Показ streaming tokens опционален; provisional tokens не evidence до commit.

## ADR-05. PostgreSQL tasks + outbox/inbox

**Решение:** адаптировать проверенный в core queue protocol, не вводить брокер в начальный контур. **Цена:** следить за index bloat, polling, connection budget и vacuum. **Альтернатива:** Redis queue без нужной durability теряет требуемые гарантии; Kafka/Temporal могут быть обоснованы позже, но сейчас добавляют отдельный кластер и новую модель failure. **Когда пересмотреть:** измеренная нагрузка/число workflow требуют другого scheduler; handler ports остаются.

## ADR-06. Stop — транзакционный barrier + асинхронный drain

**Решение:** lesson row lock/state/epoch линеаризует stop; worker делает проверку непосредственно в effect commit. **Цена:** общий lesson read-lock на короткие команды и обязательный lock order. **Альтернатива:** только `context.Cancel()` либо только update task rows допускает поздний commit/новую карточку. **Защита:** уведомление может потеряться, доменная проверка не зависит от доставки уведомления. Inference физически отменяется best effort, учебные изменения запрещены строго.

## ADR-07. Snapshot и evidence неизменяемы

**Решение:** версия сценария/рубрик/ЕКП/model manifest frozen; raw evidence не редактируется; оценка/исправление имеют revision. **Цена:** хранение старых версий и явная политика retention. **Альтернатива:** ссылки на latest scenario сделают исторические оценки непроверяемыми. Seed фиксирует выбор источников, но сам по себе не гарантирует побитовую повторяемость LLM/GPU; точный replay использует сохранённые outputs, controlled reevaluation — отдельную версию.

## ADR-08. Детерминированные правила плюс семантическая оценка

**Решение:** время, переходы, обязательные поля и routing проверяет код; язык/смысл — калиброванный local judge с evidence refs. **Цена:** разработка rubric/domain fixtures и human review. **Альтернатива:** одна LLM-оценка непрозрачна и способна путать отсутствие данных с ошибкой ученика. **Защита:** критические учебные выводы проверяемы, technical unavailable не превращается в fail.

## ADR-09. Реальное realtime media отдельно от очереди бизнес-задач

**Решение:** WebRTC/SIP-SRTP и media gateway; REST/SSE — команды/события. **Цена:** SIP/STT/TTS/recording отдельный инженерный контур. **Альтернатива:** передавать voice chunks обычными REST tasks не обеспечивает low-latency двусторонний звонок. **Защита:** queue обеспечивает durable orchestration, не realtime packet delivery. 150мс и response latency модели разные измерения.

## ADR-10. Строгая граница offline replay и final evidence

**Решение:** подтверждённые данные в БД, неподтверждённые intents на клиенте; после stop сохранять как supplemental, не применять задним числом. **Цена:** UI конфликта/recovered-only и экспертная ревизия. **Альтернатива:** слепой replay позволяет действовать после stop; discard нарушает сохранность данных. **Защита:** фиксируем и исходный факт остановки, и восстановленный ввод, не переписывая историю.

## ADR-11. Ученики поставляют карточки, но не нормативную истину

**Решение:** immutable copied card → redaction → instructor approval → separately validated reference. **Цена:** очередь review. **Альтернатива:** любой student draft сразу в следующий lesson приводит к утечке автора, несогласованным данным и оцениванию против ошибки предыдущего ученика. **Защита:** обязательный выбор источника полностью реализован, provenance и качество контролируются.

## ADR-12. Локальный контур включает storage/CA/models/assets

**Решение:** все runtime зависимости внутри LAN, TLS на внутренних hop, backup на другом локальном узле. **Цена:** offline packaging и управление сертификатами/моделями. **Альтернатива:** публичный S3/CDN/LLM или plaintext внутри Docker network нарушают исходную границу. **Защита:** «отдельный сервер» не означает «внешняя сеть».

## ADR-13. HA — профиль поставки, а не свойство Docker Compose

**Решение:** dev single-node и отдельный acceptance HA profile с sync DB replication, quorum/fencing, durable replicated blobs и резервом compute/media. **Цена:** дополнительные узлы; минимум серверного железа в ТЗ описывает узел, а не автоматически готовый отказоустойчивый кластер. **Альтернатива:** restart policy + ежедневный backup не сохранят последние подтверждённые действия при потере узла. **Защита:** честно различаем auto-restart, reconnect, failover и restore.

## ADR-14. Полномочия admin не означают владение обучением

**Решение:** ресурсные scopes и отдельные permissions, ops-agent с allowlist, admin не меняет оценки/активные сценарии. **Цена:** больше отрицательных authorization tests. **Альтернатива:** `if role==admin allow all` прямо конфликтует с ограничениями ТЗ. **Защита:** роль описывает техническое обслуживание, а не безусловный доступ к персональным учебным данным.

## Вопросы, на которые архитектура должна выдержать ответ

**Почему не использовать весь core через HTTP?** Его API умеет только создать batch run и прочитать результат. Ни действий человека, ни карточек, ни lesson stop, ни подробной оценки нет. Обёртка всё равно потребовала бы второй state machine и согласования двух БД; перенос execution protocol даёт меньше противоречий.

**Почему не изменить пару enum и оставить SQL?** В БД есть уникальность одного task данного kind на item, обязательные dialogue refs, binary score check и условия finalization. Ограничения связаны; локальные косметические правки дадут некорректные состояния.

**Как доказать, что ответ LLM не появится после stop?** Stop и effect commit конкурируют за lesson barrier; оба проверяют epoch/state внутри своих транзакций. Ответ, который завершился позже в сети, не проходит guard. Это проверяется race integration тестом с управляемой задержкой inference.

**Зачем одновременно audit, domain events и execution logs?** Audit отвечает «кто и с каким правом сделал действие», evidence — «что сделал ученик», execution logs — «почему handler не сработал». Они ссылаются на общий command/request ID, но различаются ACL, payload и retention. Не требуется triplicate сырого текста.

**Это event sourcing?** Нет. Актуальные aggregates в обычных таблицах плюс append-only evidence/events, outbox для доставки и projections для чтения. Полная реконструкция любого состояния из событий не является обязательным runtime механизмом.

**Как обеспечить 100 пользователей без 100 LLM одновременно?** Read/control API обслуживают всех; до 20 active call/card sessions и их burst profile проверяются отдельно. Inference имеет резерв и глобальные квоты. Недостаток мощности показывается admission до старта; очередь не считается доказательством latency SLA.

**Можно ли гарантировать все числа ТЗ только диаграммой?** Нет. Архитектура определяет механизмы и измерения. Производительность/AI-качество/голос подтверждаются на целевой конфигурации в W0/W11; здесь не заявлены вымышленные результаты тестов.

**Почему два статуса для карточки и службы?** Одна карточка направляется нескольким службам. Их реакции различаются; карточка может иметь overdue/refusal flags из состояния только одной службы. Памятка прямо описывает обе модели.

**Почему не запретить все неверные ответы на UI?** Тренажёр должен фиксировать содержательные ошибки для обучения. Запрещаются технически/процедурно невозможные действия; формально допустимый, но неверный по ситуации ответ принимается и оценивается.

**Что происходит с отчётом, если judge упал?** Отчёт о действиях/времени доступен с явным unavailable/provisional assessment. Получение отчёта не перезапускает LLM. Преподаватель может провести экспертную оценку с audit; техническую ошибку ученику не ставят.

**Какие риски остаются существенными?** В первую очередь производительность local inference на минимальном сервере, качество русскоязычной семантики, интерпретация «без потери аудио», неоднозначности ЕКП/workflow и доступность реальной локальной инфраструктуры. Для каждого есть ранний spike, port и критерий приёмки в W0/W11.
