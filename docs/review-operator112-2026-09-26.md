# Ревью EmSim: оператор 112

Дата: 26.09.2026. Проверен рабочий код на `9c1a660`. Продуктовый код не изменялся.

Вывод: основа тренажёра реализована на сервере, архитектура подходит для дальнейшего развития. Но статус «112-7 завершён» завышен: есть воспроизводимые дефекты доступа к черновикам, предпросмотра, проверки сценариев и редактирования. В 112-6 найдена ошибка расчёта времени. Полное соответствие исходному ТЗ и готовность ИИ для учебного класса пока не подтверждены.

## Основания и границы

Сопоставлены текущий план, планы 112-5b/112-6/112-7, ADR-021–027, контракты, код и журнал. Первичные материалы: [ТЗ](</Users/lucifer/Documents/EmSim/9. Из PDF извлечён текст; попиксельная приёмка интерфейса и экспертная проверка профильных карт в это ревью не входили.

При конфликте старого DDS-only scope и нового плана использован новый план 112 и принятые ADR. Отложенные голос, SIP, генерация сценариев и ДДС не объявлены ошибками текущей реализации. При этом соответствие согласованному срезу и полное соответствие исходному ТЗ — разные результаты проверки.

Не проверялись реальная модель на целевом оборудовании, внешние уязвимости версий зависимостей и нагрузка учебного класса. `.env` и содержимое посторонних файлов `AGENTS.md`/`c.txt` не изменялись; `.env` не читался.

## Замечания по приоритету

### 1. P1 — чужой закрытый черновик можно прочитать через копирование

[editor.go:167](/Users/lucifer/Documents/EmSim/internal/content/editor.go:167): `readVersionForCopy` принимает только ID версии, загружает её тело без проверки владельца или статуса. `CreateOperator112Scenario` отдаёт это тело в новой копии чужому преподавателю. Дополнительно [read.go:96](/Users/lucifer/Documents/EmSim/internal/content/read.go:96) позволяет перечислять версии сценария без проверки владельца; зная ID ранее опубликованного сценария, можно получить ID его новых черновиков.

Воспроизведено против PostgreSQL: преподаватель A создал `draft`, преподаватель B успешно скопировал его через `CopyFromVersionID` и получил содержание. Проверка прямого чтения чужого черновика при этом действительно запрещает доступ — обход находится в другом use case.

Это нарушает правило «черновик и эталон видит только автор» и DoD §11 плана. В ADR-027 есть внутренняя коллизия: начальные принятые решения требуют приватности, а раздел «Копирование» разрешает любую версию. Для сохранения приватности разрешать собственные версии и доступные чужие утверждённые версии; фильтровать и список версий. Нужен негативный интеграционный тест копирования чужого `draft`.

### 2. P1 — предпросмотр не получает асинхронный ответ заявителя

[ScenarioPreview.tsx:27](/Users/lucifer/Documents/EmSim/web/src/routes/instructor/ScenarioPreview.tsx:27) использует `useItem`, но не подключает SSE. Сам [useItem](/Users/lucifer/Documents/EmSim/web/src/api/workplace.ts:41) не имеет периодического опроса. В обычном рабочем месте подписка есть в `Workplace.tsx`; переиспользование одного `Operator112ProfileCase` её не переносит.

После отправки сообщения команда обновляет UI до `pending`. Позднее worker сохраняет `answered`, но экран продолжает показывать «Заявитель печатает…» и запрещает следующий ввод. Воспроизведено браузером на отдельном compose-стенде: прямое чтение API уже возвращало `answered`, в UI оставались ожидание и ноль реплик заявителя; после перезагрузки ответ появился. Возврат фокуса или другая команда также могут случайно устранить зависание, скрывая дефект.

Исправление: подписать предпросмотр на поток его занятия с инвалидацией item, обработать reconnect; добавить браузерный тест реального обмена сообщениями. Существующий `operator112-editor.spec.ts` проходит кейс вообще без отправки сообщения заявителю.

### 3. P1 — ожидание ИИ после оповещения улучшает оценку времени заполнения

[timing.go:94](/Users/lucifer/Documents/EmSim/internal/assessment/operator112/timing.go:94) суммирует ожидание всех завершённых ходов. Эта сумма вычитается из интервала `answered_at → notified_at`, хотя разговор разрешено продолжать после оповещения.

Проверка чистого оценщика: 200 секунд до оповещения дают `T_FILL=0`; дополнительные суммарные 110 секунд ожидания **после** оповещения превращают результат в `T_FILL=1` при нормативе 90 секунд. На реальном пути сумма может набраться из нескольких сообщений. Таким образом, время после фиксации карточки меняет оценку её заполнения.

Исправление: учитывать только пересечение каждого интервала ожидания с `[answered_at, notified_at]`, включая ход, начавшийся до оповещения и завершившийся после него. Проверить отсутствие, частичное и полное пересечение.

### 4. P2 — редактор не проверяет часть обязательной структуры сценария

[editor.go:498](/Users/lucifer/Documents/EmSim/internal/content/editor.go:498) намеренно обходит JSON Schema. Однако [Validate](/Users/lucifer/Documents/EmSim/internal/content/validate.go:31), на который он полагается, написан с предположением, что схема уже проверена. Семантический валидатор не заменяет проверки формата АОН, времени, часового пояса и непустой подписи факта.

Воспроизведено: валидное тело с `aon="invalid"`, `local_time="99:99"`, `time_zone="bad-zone"` и пустой `facts[0].label` получает `issues=[]`. Утверждение использует тот же валидатор. Более того, начальное значение АОН в UI — `"+7"`, и штатный e2e утверждает сценарий, не дополняя его до номера, соответствующего контракту.

Разрешать хранение незавершённого черновика нормально; разрешать его утверждение как валидного — нет. Нужна структурная проверка корректной проекции 112 либо эквивалентный полный валидатор перед approve/preview. Объяснение в ADR, почему неудобно сериализовать общий `Body`, не устраняет потерянные ограничения.

### 5. P2 — правило «сначала ответить на звонок» защищено только UI

[profile_rules.go:316](/Users/lucifer/Documents/EmSim/internal/training/operator112/profile_rules.go:316): `add_incident_type` разрешён для `ItemOpened` при `call_status=ringing`. Команда переводит item в `in_progress`; `answer_incoming` требует строго `ItemOpened`.

Воспроизведено на доменных правилах: `open → add_incident_type(gas_explosion)` принят, последующий `answer_incoming` отклонён. Получается зависшее прохождение: звонок всё ещё входящий, но ответить уже нельзя. Обычный UI скрывает форму до ответа и поэтому не обнаруживает ошибку.

Исправление: серверная проверка состояния звонка для команд редактирования типа; сохранить разрешённую работу `card_only` и работу после завершённого разговора. Нужен негативный тест прямой команды до ответа.

### 6. P2 — предпросмотр запускает заведомо ошибочный черновик

[preview.go:72](/Users/lucifer/Documents/EmSim/internal/training/preview.go:72) проверяет владельца, статус и общий тип упражнения, но не `ValidateDetailed` и блокирующие issues. HTTP-обработчик также не выполняет эту проверку. Кнопка предпросмотра не проверяет `errorCount`; это пробел обеих сторон, а не только обход клиентской блокировки.

Воспроизведено против PostgreSQL: сценарий без обязательного `expected_types` получает `invalid_full_case / severity=error`, но `StartPreview` создаёт реальное занятие и item. До проверки нового сценария также останавливается предыдущий активный preview.

Исправление: валидировать именно запрошенную сохранённую версию на сервере до создания прогона и до остановки предыдущего; возвращать предусмотренный `has_blocking_issues`. Нельзя доверять ранее выполненному клиентом `/validate` — тело могло измениться.

### 7. P2 — свежий сценарий из UI неизбежно теряет 25 баллов за профильные карты

[ScenarioEditor.tsx:270](/Users/lucifer/Documents/EmSim/web/src/routes/instructor/ScenarioEditor.tsx:270) позволяет задать типы, службы и обычные поля, но не `reference.expected_profiles`. [emptyIntake112Body](/Users/lucifer/Documents/EmSim/web/src/api/content.ts:135) также не задаёт этот эталон. [profiles.go:103](/Users/lucifer/Documents/EmSim/internal/assessment/operator112/profiles.go:103) при отсутствии эталона профиля оставляет заработанную долю равной нулю; критерий в целом не исключается. Вес блока — 25.

Следствие: для созданного с нуля через UI кейса даже правильные ответы профильной карты не могут принести эти 25 баллов. Копия импортированного сценария может сохранить уже имеющийся эталон — это другой случай. Без эталона адреса теряются дополнительные баллы, но его UI хотя бы позволяет заполнить.

В детальном плане отсутствие отдельного UI для `expected_profiles` явно задокументировано как сужение. Поэтому это не скрыто пропущенный пункт, но у сужения есть существенное последствие для заявленного результата «создать полноценный оцениваемый кейс». Нужен ввод эталона профильных карт либо отдельно согласованная политика применимости оценки; молча ослаблять рубрику нельзя.

### 8. P2 — `base_digest` не защищает изменение названия от потери

[editor.go:259](/Users/lucifer/Documents/EmSim/internal/content/editor.go:259) сравнивает digest тела. Название хранится отдельно в `scenarios`, и изменение только названия не меняет digest.

Воспроизведено против PostgreSQL: два клиента читают один digest; первый сохраняет название A, второй со старым digest успешно сохраняет название B. Вместо `stale_draft` первая правка теряется. Это возможно последовательно, без гонки запросов.

Дополнительно выбор текущей версии не блокирует строку сценария: `ScenarioByID` и `MaxVersion` выполняют обычный SELECT. Одновременный PUT может упереться в уникальность номера версии вместо предусмотренного конфликта; этот дополнительный сценарий отдельно не воспроизводился.

Исправление: сравнивать версию/ревизию, охватывающую и метаданные, и тело; сериализовать изменение сценария или делать атомарный compare-and-swap. Добавить проверки двух вкладок и конкурентного сохранения.

### 9. P2 — сервер считает байты, UI и контракт считают символы

[profile_rules.go:481](/Users/lucifer/Documents/EmSim/internal/training/operator112/profile_rules.go:481) ограничивает сообщение через `len(text)>500`. В Go это байты UTF-8. В [CallerChat.tsx](/Users/lucifer/Documents/EmSim/web/src/routes/trainee/CallerChat.tsx:5) и OpenAPI ограничение — 500 символов. Воспроизведено: 251 буква `я` отклоняется сервером, хотя находится внутри клиентского лимита.

Та же ошибка есть в [intake.go:131](/Users/lucifer/Documents/EmSim/internal/training/intake.go:131) и проверке текстового профильного ответа: русское описание на 1999 символов фактически ограничивается примерно 999 русскими буквами. UI чата очищает набранную фразу сразу после отправки, поэтому отклонение дополнительно затрудняет исправление.

Исправление: единообразно считать Unicode-символы, согласовать поведение для emoji, проверить русские строки на границах ограничений. Сохранять текст отклонённого сообщения для повторной отправки.

### 10. P2 — автооценка предпросмотра существует в БД, но недоступна из его экрана

[ScenarioPreview.tsx:47](/Users/lucifer/Documents/EmSim/web/src/routes/instructor/ScenarioPreview.tsx:47) выводит только сообщение «Оценка появится в разборе карточки». ### 11. P2 — фоновое обновление редактора стирает несохранённые правки

[ScenarioEditor.tsx:80](/Users/lucifer/Documents/EmSim/web/src/routes/instructor/ScenarioEditor.tsx:80) перезаписывает `title`/`body` при любом изменении `existing.dataUpdatedAt`. Вопреки комментарию, это не инициализация один раз на scenario ID. React Query использует стандартный refetch при возвращении к вкладке и восстановлении сети.

После локального редактирования возврат в окно может загрузить прежнюю сохранённую версию и заменить ею текущую форму. Это вывод по исполняемому коду; отдельный браузерный тест этого сценария в ревью не запускался.

Исправление: отделить первоначальную загрузку от фонового обновления, хранить dirty-состояние, не заменять текущую форму без разрешения конфликта.

## ИИ-заявитель

С архитектурной стороны выбран хороший способ интеграции: узкий `CallerReplier`, worker и отдельный пул `caller`; модель не держит транзакцию команды открытой. Состояние восстанавливается из сохранённого разговора. Результат принимается только для ещё ожидающего хода живого занятия; поздний ответ не меняет закрытый evidence. Эталон, рубрика и правильные службы не передаются модели. Источник ответа, модель, версия промпта и параметры сохраняются. Fallback отличается от ответа модели в данных разбора.

Однако это пока «правила распознают вопрос, модель формулирует ответ»: доступ к фактам определяется RE2-паттернами. Перефразировка, не покрытая паттернами, не становится понятной системе автоматически благодаря LLM. Полный текст ответа после `CleanReply` принимается без проверки фактической согласованности; `DiscloseReveals` лишь размечает известные факты, не запрещая выдуманный текст. Поэтому корректность промпта и тесты протокола не доказывают педагогическую достоверность собеседника. Нужен приёмочный набор русских перефразировок, повторов, отрицаний, неизвестных сведений и попыток изменить роль/факты на выбранной реальной модели.

Дополнительные технические риски:

- [client.go:38](/Users/lucifer/Documents/EmSim/internal/platform/llm/client.go:38): `temperature=0` допустима конфигурацией, но удаляется `omitempty` из HTTP-запроса. Evidence запишет 0, а сервер модели получит отсутствие параметра. Следует различать явно заданный ноль и отсутствие значения.
- `CleanReply` удаляет только закрытый `<think>…</think>`. Незакрытый блок при обрыве генерации может пройти как обычная реплика. Текущий выбор модели с выключенным reasoning уменьшает вероятность, но код не гарантирует очистку.
- История запроса растёт без явного бюджета контекста; отдельный пул ограничивает параллелизм, но не доказывает задержку всего класса. Отменённый ход может ещё потратить вызов модели до отклонения результата. Это вопросы W0 и управления очередью, а не основание заявлять готовность под 20 диалогов.

По умолчанию compose запускает `stub`; модели в составе compose нет. Это соответствует обозначенному «этапу 1», но свежий запуск проекта не является автономной поставкой ИИ-тренажёра.

## Зависимости

Очевидных лишних производственных зависимостей не обнаружено. React, Router и React Query соответствуют SPA; клиент модели использует стандартный `net/http`, отдельный SDK/агентный фреймворк не добавлен. PostgreSQL используется и для данных, и для очереди: дополнительных брокеров и сетевых продуктовых сервисов нет. Во фронтенде не найдены ссылки на внешние CDN/шрифты, необходимые для работы.

Проверен `go mod why`: Docker/containerd, OpenTelemetry и `purego` в цепочке происходят от `testcontainers` для интеграционных тестов; они не означают обязательность этих сервисов в рабочем приложении. `fpdf` реально используется отчётами, хотя помечен `indirect` — это небольшая несогласованность `go.mod`, не лишняя библиотека. Проверка известных уязвимостей зависимостей не проводилась.

Из связности, которую стоит улучшить: исключение preview из отчётов опирается на `INNER JOIN workstations` при NULL workstation, а не явный фильтр режима. Сейчас это работает и покрыто интеграционным тестом, но изменение JOIN для иной задачи может незаметно вернуть предпросмотры в статистику. Две реализации предложений служб — в исполнении и авторской проверке — также требуют общей чистой функции или проверки эквивалентности: один вариант учитывает `answer.Values`, другой только `answer.Value`.
