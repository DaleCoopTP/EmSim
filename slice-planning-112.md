# План вертикальных срезов: оператор 112

Дата: 2026-09-22. Статус: план реализации; перечисленные возможности ещё не означают готовую поддержку 112.

## 1. Цель и порядок работ

Добавить в EmSim упражнение `operator112_intake`: обучаемый принимает вызов заявителя, уточняет сведения, заполняет основную и профильные опросные карты, определяет службы, направляет им информацию и завершает обработку. При необходимости связывается с симулируемой ДДС. Преподаватель готовит задания, наблюдает прохождение и оценивает результат по самостоятельной рубрике 112.

По решению пользователя разработка 112 начинается **поверх существующего функционала, до завершения оставшихся работ по ДДС**. После реализации согласованного объёма 112 работа над ДДС продолжается с учётом полученных уточнений. В части очередности этот документ заменяет положение «112 только после завершения ДДС» в [основном плане](slice-planning.md) и [ADR-015](design-docs/adr/015-dds-first-operator112-extension.md). Архитектурное разделение упражнений из ADR-015 сохраняется.

Каждый срез включает модель и хранение, правила, API, интерфейс, подготовленные задания и проверки, необходимые для конкретного пользовательского результата. UI реализуется после стабилизации правил и API **внутри того же среза**. Отдельного большого среза «написать весь backend», за которым следует «сделать весь UI», нет.

### Рабочие допущения

- Ранний заявитель — детерминированный текстовый собеседник с подготовленными репликами и вопросами. Свободный диалог с ИИ добавляется позднее; первая версия не зависит от моделей.
- Под эмуляцией IP-телефонии в этом плане понимается телефонное рабочее место в браузере: входящий вызов, соединение, удержание, завершение, перевод и конференция по мере реализации срезов. В текстовой версии содержание разговора отображается текстом; голосовой канал добавляется в срезе 112-9.
- Настоящий SIP-сервер, подключение внешних телефонных номеров и боевых служб не требуются для этой эмуляции. Это соответствует выбранному для проекта подходу [ADR-005](design-docs/adr/005-phone-simulator-without-sip.md). Подключение реального SIP при появлении такого требования — отдельное расширение с проверкой связи и развёртывания.
- В первой версии ДДС играет сценарный симулятор. Совместное занятие двух обучаемых «112 → ДДС» не является зависимостью этого плана.
- «Дополнительная карта» — профильный набор вопросов и полей внутри происшествия. Карточка может содержать несколько таких наборов. Предварительный пилот: скорая помощь, пожарно-спасательная служба, полиция; точные поля берутся из материалов заказчика и проверяются профильным экспертом.
- Нормативы времени, веса критериев и условия обязательной связи с ДДС задаются отдельно для 112. Нормативы ДДС автоматически не переносятся.

## 2. Что расширяем в существующем приложении

| Существующая возможность | Использование в режиме 112 |
|---|---|
| Авторизация, роли, рабочие места | Сохраняем `admin`, `instructor`, `trainee`; 112 — тип упражнения, а не новая роль доступа. Устраняем зависимость назначения 112 от профиля конкретной ДДС, сохраняя проверки профиля для ДДС. |
| Каталог и неизменяемые версии сценариев | Добавляем вариант сценария с фактами заявителя, диалогом, пустой/частично заполненной карточкой и отдельным эталоном 112. |
| Занятия, назначения, прогоны, очереди | Используем общий механизм; одно занятие имеет один тип упражнения. Одна версия сценария создаёт независимое прохождение каждому участнику. |
| Команды, журнал, SSE, stop/recovery | Сохраняем общие гарантии; добавляем команды, события и состояние 112. |
| Телефон ДДС, записи, медиахранилище | Повторно используем подходящие компоненты. Текущий исходящий звонок с greeting/ack не считаем готовым входящим диалогом с заявителем. |
| Оценивание и экспертные ревизии | Добавляем самостоятельную рубрику и обработчик 112; сохраняем ручную оценку, историю и приоритет эксперта. |
| Монитор, история, CSV/PDF | Расширяем проекции и фильтры по типу упражнения; не смешиваем показатели и ошибки ДДС и 112. |
| React-приложение и общие компоненты | Добавляем отдельное рабочее место 112. Формы преподавателя и общую навигацию расширяем. |

Точки расширения уже обозначены в `internal/training/exercise.go` и `internal/assessment/evaluator.go`, но фактические типы, структуры карточки/evidence, JSON-схемы и ограничения БД пока ориентированы на ДДС. Срез 112-1 должен расширить их согласованно, а не только добавить значение в переключатель UI.

Правила нового упражнения размещаются в отдельном компоненте `training/operator112`, правила оценки — в `assessment/operator112`. Общими остаются транзакции, авторизация, квитанции команд, аудит и инфраструктура. Универсальный конструктор процессов и новые сетевые сервисы между продуктовыми модулями не нужны.

| 112-5 | Получить отдельную оценку 112 с основаниями и отчётом | 112-4 |

После **112-1** доступен первый сквозной пилот. После **112-5** — основной текстовый MVP по всем пяти блокам пользователя: эмулятор телефона, заявитель, карты, оценка, отдельный UI. После **112-7** преподаватель самостоятельно готовит и проводит расширенные текстовые занятия. Срезы **112-8–112-9** добавляют свободное общение с ИИ и голос; пригодность этих режимов для всего класса подтверждается измерениями.

## 4. Срез 112-1 — первый вызов и карточка с нуля

### Пользовательский результат

Преподаватель назначает готовый сценарий 112. Обучаемый принимает текстовый вызов, заполняет основную карточку, направляет её одной выбранной службе и завершает обработку. Преподаватель видит ход работы, итоговую карточку и может вручную оценить прохождение.

### Объём

- Добавить `operator112_intake` в каталог, занятия, прогоны, состояние, снимки и вход оценки. Расширить миграциями ограничения БД и контракты; сохранить чтение старых данных ДДС.
- Ввести отдельные варианты сценария, команд, состояния и evidence 112. Черновик не обязан соответствовать схеме готовой входящей карточки ДДС.
- Подготовить один простой сценарий: входящий вызов, небольшая фиксированная последовательность текстовых реплик, один тип происшествия, одна служба. Сценарий импортируется штатным загрузчиком и выбирается в каталоге.
- Разделить закрытые факты/эталон и данные, доступные обучаемому. Карточка изначально пуста, кроме разрешённых метаданных вызова, например АОН и времени.
- Базовый телефон: входящий → принят → разговор завершён. Полный управляемый опрос появляется в 112-2.
- Основная форма: телефоны, заявитель и его статус, адрес/описание места, тип происшествия, сведения о пострадавших, описание со слов заявителя. Отличать отсутствие ответа от отрицательного ответа и от «заявителю неизвестно».
- Сохранение черновика, выбор службы, явная отправка в симулятор, отметка о завершении обработки. Завершение разговора, сохранение, отправка и завершение карточки — разные события.
- Минимальная отправка фиксирует адресата, время и снимок отправленных данных; повтор команды не создаёт вторую отправку. Развитая маршрутизация — в 112-3–112-4.
- Подключить существующий монитор, stop, восстановление и разбор для нового типа. С самого начала сохранять реплики, действия, времена и отправленную версию карточки.
- Начальная рубрика 112 для ручного разбора: полнота/достоверность основной карточки и направление информации. Отсутствие автоматических правил явно обозначается; обработчик и рубрика ДДС к 112 не применяются.
- Отдельный экран обучаемого: телефон и текст разговора рядом с редактируемой карточкой, список служб и действия обработки. Начальная компоновка соответствует [референсу АРМ-112](docs/reference-ui/README.md).

### Сквозная проверка и Definition of Done

1. Преподаватель через UI назначает пилот и запускает занятие.
2. Обучаемый принимает вызов, читает реплики, заполняет карточку, отправляет её и завершает обработку.
3. Преподаватель видит ход работы и сохранённые доказательства, выставляет ручную оценку; обучаемый видит безопасный результат в истории.

- Обновление страницы восстанавливает подтверждённый черновик и состояние вызова, не раскрывая закрытые данные сценария.
- Повтор команды, устаревшая версия и stop во время работы сохраняют существующие гарантии журнала и evidence.
- Одинаковый сценарий у двух участников даёт независимые карточки и диалоги.
- Один сквозной тест проходит через API/БД и UI; существующий сценарий ДДС продолжает работать.

## 5. Срез 112-2 — уточняющий опрос текстового заявителя

### Пользовательский результат

Обучаемый самостоятельно выбирает уточняющие вопросы и получает только те сведения, которые сообщил заявитель. Преподаватель видит, какие вопросы были заданы и что осталось невыясненным.

### Объём

- Заменить линейный пилот сценарием с начальной репликой, доступными вопросами, условиями раскрытия фактов и подготовленными ответами.
- В раннем интерфейсе вопрос выбирается из набора реплик. Свободный текст не считается автоматически понятым без соответствующего механизма; свободное общение появляется в 112-8.
- Описать факты, которые заявитель сообщает сразу, после вопроса или не знает. Предусмотреть повтор вопроса, уточнение, неполный ответ и завершение диалога.
- Хранить состояние диалога на сервере; браузер получает только доступные реплики и разрешённые варианты вопросов, без всего дерева ответов и эталона.
- Ввести независимый контракт симулятора заявителя, который позже сможет реализовать ИИ-адаптер. Телефон отвечает за соединение, заявитель — за содержание разговора.
- Сохранять идентификатор и текст каждой произнесённой реплики, автора, серверное время и связь с вызовом. Для подготовленных вопросов сохранять идентификатор проверяемого навыка/темы.
- Добавить удержание и возврат к разговору; состояние телефона ограничивает возможность получить следующую реплику.
- Подготовить задания с недостающим адресом, уточнением числа пострадавших и неизвестными заявителю сведениями. Это учебные фикстуры, не универсальные инструкции по оказанию помощи.
- В разборе преподавателя показывать диалог вместе с изменениями карточки. Не переносить полученные ответы в поля автоматически: заполнение остаётся действием обучаемого.

### Definition of Done

- Два разных порядка вопросов дают согласованные ответы и одинаковые неизменяемые факты происшествия.
- Не заданный вопрос не раскрывает скрытый ответ; повтор отправки вопроса не создаёт вторую реплику.
- Перезагрузка страницы продолжает текущую ветку без повторного запуска сценария.
- После завершения вызова или stop новая реплика не добавляется.
- Преподаватель может проверить по журналу, был ли выяснен конкретный факт и правильно ли он перенесён в карточку.

## 6. Срез 112-3 — профильные карты, классификация и подбор служб

Детальный план среза: [slice-112-3-plan.md](slice-112-3-plan.md). Уточнение
пользователя от 23.09.2026 задаёт первые пилотные карты 104 и 101 и три
задания без симуляции разговора. Это уточнение заменяет первоначальный состав
пилотных профилей и пример комбинированного случая; медицинский и
полицейский профили остаются отдельным последующим расширением.

### Пользовательский результат

Обучаемый выбирает тип происшествия в одном из трёх заданий: взрыв газа,
ДТП с пламенем или их комбинация. После выбора появляются карты 104 и/или
101; обучаемый заполняет их и проверяет предложенный набор учебных служб.
Само назначение кейса не создаёт профильные карты.

### Объём

- Ввести версионированные определения опросных карт: поля, вопросы, признаки/теги, варианты ответов, условия видимости и обязательности, связи с классификатором.
- Поставить первые два подготовленных профиля по предоставленным скриншотам:
  104 (газ) и 101 (пожар/транспорт). Три самостоятельных учебных кейса
  назначаются из каталога без подготовленного разговора и без вложенных карт.
  Состав вопросов и соответствие кейсов этим картам проверяются профильным
  экспертом; скриншот 104 показывает признаки запаха газа, а не отдельные
  признаки взрыва.
- Поддержать основной и дополнительные типы происшествия, несколько профильных карт в одном происшествии, общий адрес и общие сведения о заявителе.
- Признаки выбираются оператором; автоматическое извлечение тегов из произвольной речи не входит в этот срез.
- Разделить формальную валидацию формы и оценку учебной правильности. UI не должен выдавать эталон или запрещать всякое ошибочное решение только потому, что оно неверно по сценарию.
- При смене типа явно показывать последствия для заполненных разделов; не терять значения незаметно и не включать неактивные ответы в отправку.
- Рассчитывать предложенные службы по типам/признакам и применимым данным адреса из справочников. Использовать версионированные правила, а не закрытый эталон конкретного задания.
- Показывать основание предложения, разрешать ручную корректировку по установленным правилам; сохранять исходное предложение, итоговый выбор и действия оператора.
- Правила удаления автоматически назначенных служб выделить явно. До уточнения инструкции действуют документированные пилотные ограничения, без неподтверждённого запрета на все изменения.
- Фиксировать версии опросных карт и правил подбора при старте, чтобы изменение справочника не меняло идущее занятие.

### Definition of Done

- Через UI назначаются и проходят три кейса: взрыв газа → 104, ДТП с
  пламенем → 101, комбинация → 104 и 101. До выбора типа ни одна из
  профильных карт не показана; симуляции разговора в этих кейсах нет.
- В комбинированном случае доступны несколько карт и объединённый список служб без дубликатов.
- Противоречивые значения, неизвестные признаки и нарушения условий формы обрабатываются предсказуемо; «неизвестно» не превращается в «нет».
- Смена типа, ручная корректировка служб и повторное открытие черновика не теряют данные или историю решений.
- Фикстуры проверяют правила классификации и подбора независимо от UI и эталона задания.

## 7. Срез 112-4 — отправка информации и взаимодействие с ДДС

### Пользовательский результат

Обучаемый направляет карточку нескольким службам, видит результат каждой передачи, при необходимости звонит в ДДС, переводит заявителя или организует конференцию и фиксирует результат общения.

### Объём

- Расширить отправку из 112-1 до списка адресатов с индивидуальными состояниями передачи и ответами симулятора ДДС.
- Различать сохранение черновика, направление карточки, получение сообщения службой и её дальнейшее реагирование. Оператор 112 не выполняет за диспетчера все статусы ДДС.
- Хранить неизменяемые версии отправленных данных. Исправление черновика после отправки не меняет уже переданную информацию; дополнение отправляется отдельным действием.
- Предусмотреть частичный успех, временную недоступность адресата и повтор отправки без повторного эффекта у уже получивших служб.
- Добавить сценарные контакты ДДС, текстовый исходящий разговор, перевод вызова с удержанием и текстовую конференцию.
- Расширить модель телефонной сессии для заявителя и контакта ДДС. Существующее ограничение телефона ДДС «один незавершённый звонок на карточку» нельзя механически применять к консультации с удержанием или конференции; правила участников и соединений задаются явно.
- Запись отработки: служба/контакт, кто принял, суть сообщения, результат и связанные отправки/звонки.
- Завершение обработки фиксирует состояние карточки и незавершённые обязательные операции по правилам упражнения. Требования к действию и его фактическая правильность оцениваются раздельно.
- Добавить панели служб, управления вызовом и отработок в рабочее место 112, а их историю — в монитор и разбор.

### Definition of Done

- Сценарий с двумя службами проходит полностью; сбой одной передачи не отменяет успешную другую.
- Повторная отправка того же запроса не создаёт дубликат; отправка дополнения сохраняет обе версии и порядок.
- Пройден сценарий связи с ДДС: удержание заявителя, консультация, возврат; отдельно проверены перевод и конференция.
- Каждая реплика относится к правильному участнику и соединению; после завершения/stop поздний ответ симулятора не изменяет закрытый результат.
- Преподаватель видит, что, кому и когда было направлено и что сообщил оператор при дополнительном звонке.

## 8. Срез 112-5 — самостоятельная оценка и отчёт по 112

### Пользовательский результат

Обучаемый получает результат по навыкам оператора 112. Преподаватель видит основания каждого вывода, исправляет оценку и получает отчёт по занятию без смешивания с ДДС.

### Объём

- Развернуть начальную рубрику 112-1 в самостоятельный версионированный набор критериев с поправками конкретного сценария.
- Проверять кодом доступные факты: приём вызова и время этапов, темы выбранных вопросов, заполнение основной и профильных карт, классификацию, выбор служб, отправленные версии, необходимые контакты и завершение обработки.
- Сравнивать с эталоном не только финальный черновик, но и сведения, реально направленные службам. Исправление после отправки не исправляет прошлую передачу задним числом.
- Допускать альтернативные правильные ответы и наборы действий, если они заданы в эталоне. Для адреса использовать структурированные компоненты и явно допустимые варианты.
- Полноту и достоверность свободного описания, качество формулировок и содержательность разговора первоначально проверяет преподаватель. Непустое поле не означает правильное содержание.
- Каждый вывод содержит ссылку на поле, реплику, действие или отправку. Отсутствие технической возможности проверки даёт `unavailable`/`needs_review`, а не ошибку обучаемого.
- Веса, критические ошибки, пороги и нормативы 112 хранить отдельно. Численные значения в пилоте явно считать учебными настройками до подтверждения экспертом.
- Расширить подготовку входа оценки и обработчик по типу упражнения; сохранить неизменяемые входы, ручную оценку без автоматической, ревизии и приоритет эксперта.
- Обновить экран разбора, личную историю, сводку, CSV/PDF. Во всех выборках и агрегатах учитывать `exercise_type`; не выводить общий уровень из несопоставимых критериев.
- `intro` не создаёт итоговую оценку и не влияет на прогресс. Stop и технические прерывания учитываются отдельно от учебных ошибок; недостигнутые этапы не получают автоматический штраф за сбой системы.

### Definition of Done

- Подготовлены эталонные прохождения: корректное, с ошибочным адресом, пропущенным вопросом, неверным набором служб и исправлением после отправки.
- Одна и та же доказательная база даёт одинаковый результат детерминированных правил.
- Для свободного описания без семантического проверяющего явно показана необходимость ручной проверки.
- Преподаватель исправляет критерии, итоговая ревизия попадает в историю и отчёт; поздняя автоматическая оценка её не заменяет.
- У одного пользователя результаты 112 и ДДС доступны раздельно; отчёты и безопасная обратная связь не раскрывают закрытый сценарий.

## 9. Срез 112-6 — редактор и проверка сценариев преподавателем

### Пользовательский результат

Преподаватель без редактирования JSON создаёт собственный текстовый кейс 112, проходит его в предпросмотре, утверждает и назначает группе.

### Объём

- Расширить существующий каталог редактором сценариев 112: название, сложность, сведения о происшествии и заявителе, начальная реплика, вопросы/ответы, условия раскрытия фактов.
- Задавать типы и опросные карты, ожидаемые поля и допустимые варианты, нужные/лишние службы, контакты и поведение симулятора ДДС, обязательные действия и поправки к оценке.
- Разделять текст заявителя, закрытые факты и эталон. Факт, которого заявитель не знает и который невозможно получить другим предусмотренным способом, не должен становиться безусловно обязательным ответом обучаемого.
- Проверять ссылки, достижимость веток, согласованность фактов, карт, служб и критериев; выдавать понятные ошибки в UI.
- Добавить предпросмотр полного прохождения, который не попадает в историю обучаемых и учебную статистику.
- Утверждённая версия неизменяема. Редактирование создаёт новый черновик; старые назначения и результаты сохраняют свои версии и определения форм.
- До этого среза сценарии поставляются через импорт. Редактор 112 реализуется независимо от отложенного редактора ДДС; общую часть можно использовать позднее.
- Генерация всего сценария ИИ и универсальный конструктор произвольных форм в этот срез не входят. Преподаватель использует поставленные профильные карты и справочники.

### Definition of Done

- Преподаватель через UI создаёт, проверяет, утверждает и назначает новый сценарий; обучаемый проходит его, получает оценку.
- Ошибочная ссылка, недостижимый обязательный факт и противоречивый эталон препятствуют утверждению с конкретным объяснением.
- Изменение сценария не меняет активное занятие и результат завершённого прохождения.
- Чужой преподаватель и обучаемый не получают доступ к закрытым сценарным данным или редактированию.

## 10. Срез 112-7 — сложные вызовы и занятия группы

### Пользовательский результат

Группа проходит последовательность неодинаковых вызовов: обычные, оборванные, повторные, с уточнением ранее переданных сведений. Преподаватель управляет занятием, видит загрузку рабочих мест и разбирает ошибки.

### Объём

- Расширить уже используемые назначения/очереди и монитор особенностями 112: ожидающие вызовы, занятость оператора, активный разговор и незавершённые карточки.
- Разделить очередь входящих вызовов и работу над карточками после разговора. На одном РМ допускается один активный разговор с заявителем; конференция из 112-4 — участники той же сессии, а не независимый второй заявитель.
- Добавить сценарные события обрыва, отсутствия контакта и обратного звонка. Реальный сбой приложения отличать от учебного обрыва.
- Добавить повторное обращение, поиск совпадений по доступным телефону/адресу и явную привязку карточек. Совпадение — повод проверить связь, а не автоматическое объединение.
- Определить в сценарии область связанных обращений одного участника. Не искать совпадения по копиям заданий других обучаемых и не раскрывать чужие карточки.
- Новые сведения по завершённому обращению фиксировать связанным дополнением/новой карточкой. Не переписывать запечатанный evidence и прежнюю оценку.
- Расширить редактор событиями и связанными обращениями, оценку — критериями обратного звонка, связи карточек и своевременного дополнения.
- Добавить ознакомительное прохождение с подсказками поверх тех же правил; обучающий UI помогает понять форму и порядок действий, тренировочный не раскрывает эталон.
- Доработать расположение полей, панели, состояния и горячие клавиши по материалам оператора 112; проверить удобство разговора и заполнения на одном экране.

### Definition of Done

- Проходится занятие из нескольких кейсов: обычный вызов, обрыв с обратным звонком, повтор с новым существенным сведением и неполным адресом.
- Очередь не создаёт два независимых активных разговора на одном РМ; состояние чужого участника не влияет на прохождение.
- Стоп, рестарт, переподключение и одновременное событие/действие сохраняют порядок, дедлайны и доказательства без дублей.
- Повторное обращение связано с исходным, а прежние отправки, evidence и оценки неизменны.
- Выполнен измеряемый групповой прогон текстового режима на целевом числе РМ (ориентир текущего проекта — 20–30); результаты и ограничения записаны в приёмочный отчёт.
- Преподаватель проводит всё занятие через UI: подготовка, назначение, монитор, остановка, разбор и отчёт.

## 11. Срез 112-8 — ИИ-заявитель в текстовом разговоре

### Пользовательский результат

Обучаемый задаёт вопросы своими словами, а ИИ-заявитель отвечает в пределах заданной ситуации. Карточки, телефонные действия и направление информации работают так же, как в детерминированном режиме.

### Условие перехода

[ADR-003](design-docs/adr/003-llm-outside-interactive-path.md) запрещает обращения к моделям во время прохождения. Перед реализацией этого среза требуется отдельное архитектурное решение, которое явно разрешает интерактивного заявителя для 112 и описывает его ресурсы, задержки и поведение при сбоях. Предыдущие срезы от этого изменения не зависят. Существующие ограничения целевого сервера без GPU нельзя считать автоматически достаточными для свободного диалога всего класса.

### Объём

- Сначала измерить задержку и качество локальной модели на русском языке, затем зафиксировать допустимое число одновременных диалогов и профиль запуска. Модели и необходимые ресурсы доступны без внешнего интернета.
- Подключить ИИ-адаптер к контракту заявителя из 112-2: факты, знание заявителя, история разговора, допустимое поведение и ограничения на раскрытие.
- Не передавать модели рубрику, баллы и правильный набор служб как инструкции заявителю. Она играет участника ситуации и не оценивает обучаемого в том же ответе.
- Зафиксировать версию модели, шаблона инструкций и параметры в прохождении. Сохранять фактический диалог для воспроизводимого разбора; повторная генерация не считается восстановлением прошлого ответа.
- Вынести ожидание модели за пределы транзакции команды. Результат принимать только для актуального вызова, версии хода и действующего занятия; поздний ответ после stop или завершения отклоняется.
- Предусмотреть ограничение очереди, таймаут, отмену, явный статус ожидания и переход к подготовленному ответу/сценарному режиму. Техническая задержка не считается ошибкой обучаемого.
- Расширить редактор настройкой поведения заявителя и предпросмотром ИИ-диалога. Детерминированный режим остаётся выбираемым и полностью работоспособным.
- Добавить отдельную фоновую семантическую проверку свободных вопросов и описания после прохождения. Её выводы имеют ссылки на реплики, калибруются на экспертных примерах и при недоступности оставляют ручной разбор.

### Definition of Done

- Пройдены кейсы со свободными перефразировками вопросов, повторными уточнениями и попытками заставить заявителя раскрыть эталон или изменить исходные факты.
- Собрана экспертная выборка качества ответов и семантической оценки; зафиксированы известные ограничения и основания для ручного разбора.
- При таймауте модели интерфейс остаётся рабочим, состояние диалога не повреждается и доступен заявленный fallback.
- Повтор запроса, отмена, stop и поздний ответ не создают лишних реплик или изменений закрытого evidence.
- Измерены задержки ответа, нагрузка и число одновременных диалогов на выбранном оборудовании; UI не обещает неподтверждённую ёмкость класса.

## 12. Срез 112-9 — голосовое общение через эмулятор телефона

### Пользовательский результат

Обучаемый слышит заявителя, задаёт вопросы голосом и параллельно заполняет карточку; при необходимости соединяет его с симулируемой ДДС. Преподаватель разбирает запись и расшифровку того же прохождения.

### Объём

- Добавить микрофон, воспроизведение голоса заявителя, STT реплик оператора и TTS ответов. Голос использует уже работающий диалог и телефонные состояния, а не отдельный сценарный процесс.
- Первая голосовая версия может работать по очереди реплик с явным завершением ввода; перебивание и непрерывный полнодуплексный разговор не заявляются без отдельной реализации и проверки.
- Связать аудио, расшифровку, участников и события вызова устойчивыми идентификаторами. Хранить исходный результат распознавания и отмечать исправления/неуверенность, чтобы ошибка STT не превращалась в доказанную ошибку оператора.
- Расширить текущие медиахранилище, права доступа, манифесты, загрузку и прослушивание для двух сторон разговора и конференции.
- Сохранить завершённые факты и метаданные даже при потере записи; поздняя разрешённая загрузка медиа не переписывает запечатанный evidence. Правила сроков загрузки и подготовки входа оценки согласовать с существующим конвейером.
- При отсутствии микрофона, отказе распознавания/озвучивания или потере медиаканала явно предложить текстовый режим. Недоступность голоса учитывается отдельно от навыка обучаемого.
- Управление вызовом и доменные команды остаются короткими операциями API; потоковое аудио, если потребуется, не передаётся как последовательность обычных фоновых бизнес-задач.
- Подготовить локальные модели/ассеты и инструкции по разрешениям браузера, защищённому подключению в LAN и гарнитуре. Проверить ресурсы STT/TTS вместе с ИИ-заявителем, API и оцениванием.

### Definition of Done

- Голосом проходится сквозной кейс: принять вызов, уточнить сведения, заполнить карты, направить информацию, связаться с ДДС, завершить и открыть разбор.
- Преподаватель сопоставляет запись, реплики, поля и отправки; частично отсутствующие данные явно отмечены.
- Проверены отказ в микрофоне, ошибка STT/TTS, обрыв воспроизведения, повтор загрузки и stop во время ответа.
- Текстовый режим остаётся доступен без моделей голоса и без потери подтверждённой карточки.
- Измерены задержка распознавания/ответа/озвучивания и допустимое число одновременных голосовых вызовов. Голосовой режим поставляется с проверенным профилем ресурсов.

## 13. Сквозные требования к реализации

- **Версии и миграции.** Изменения схемы применяются поверх существующей БД. Старые сценарии, evidence и отчёты ДДС продолжают читаться; новые схемы имеют явный тип и версию. Нельзя заново интерпретировать старое прохождение по обновлённой форме или рубрике.
- **Авторизация.** Обучаемый работает только со своим прохождением; преподаватель — со своими занятиями/сценариями. Эталоны, полное дерево диалога и закрытые факты не попадают в trainee API, SSE или клиентский бандл.
- **Команды.** Сохраняются `command_id`, digest запроса, `expected_seq`, квитанция и серверное время. Подтверждённое изменение, журнал, уведомление и связанная задача фиксируются атомарно там, где это необходимо.
- **Stop и восстановление.** Остановка является барьером для полей, реплик, отправок и ответов моделей. Перезагрузка восстанавливает подтверждённое состояние. Неподтверждённый ввод показывается как таковой и не применяется задним числом после stop.
- **Доказательства.** С самого первого среза сохраняются доступный разговор, действия, состояния вызова, изменения карточки и отправленные версии. Дальнейшая оценка не должна зависеть от реконструкции истории по одному финальному черновику.
- **Разделение правильности и допустимости.** Система запрещает нарушения протокола и невозможные состояния. Учебные ошибки, которые реальный интерфейс допускает, фиксируются и оцениваются; эталон не используется как скрытая блокировка любого неверного ответа.
- **UI.** Отдельное рабочее место 112 поставляется по частям в каждом срезе. Поля и действия сверяются с инструкцией оператора; раздел «Что не берём» в старом референсе относился к этапу ДДС и сам по себе не исключает функции 112.
- **Проверки.** Для каждого среза нужны целевые проверки правил и контрактов, интеграционные проверки важных транзакций, хотя бы один сквозной пользовательский сценарий и ручная проверка затронутых экранов. Тесты ДДС остаются обязательной защитой общей платформы.
- **Документация.** Вместе с реализацией обновляются актуальные OpenAPI/JSON-схемы, инструкции запуска и запись в `LOG.MD`. Архитектурные изменения оформляются до реализации соответствующего поведения.

Для каждого изменения выполняются применимые команды проекта: `make verify`, `make verify-web`; при изменении БД, stop/recovery и взаимодействия API/worker — `make test-integration`; при изменении рабочего потока — соответствующие browser e2e. Полный набор проверок не заменяет ручную приёмку полей и правил профильным экспертом.

## 14. Уточнения и границы объёма

Эти вопросы не блокируют создание первого текстового пилота, но должны быть разрешены до соответствующего среза. До уточнения используются явно обозначенные пилотные настройки, а не предполагаемые нормативные правила.

| Уточнение | Когда требуется |
|---|---|
| Точные поля основной карточки и допустимые неизвестные/неполные значения | Перед приёмкой 112-1 |
| Состав и обязательность профильных карт; перечень первых служб; правила ручного удаления назначений | Перед приёмкой 112-3 |
| Основания звонка, перевода, конференции и условие «Отработана» | Перед приёмкой 112-4 |
| Критерии, веса, критические ошибки, нормативы и допустимые альтернативы | Перед приёмкой 112-5 |
| Правила повторных обращений, обратного звонка и поиска связанных карточек | Перед приёмкой 112-7 |
| Модель, оборудование, ёмкость класса и допустимые задержки ИИ/голоса | До фиксации профилей 112-8–112-9 |

За пределами этого плана: интеграция с боевой системой-112, реальные вызовы в службы, обязательный SIP-сервер, совместный прогон двух обучаемых 112/ДДС, полноценные GIS/СМС/видеозвонки, автоматическая генерация всех учебных сценариев и автоматические рекомендации уровня. Эти возможности можно добавлять отдельными вертикальными срезами без включения их в первый MVP.

Следующий шаг реализации — детализировать 112-1 по конкретным контрактам, миграциям, API и первому пилотному сценарию, затем провести его от назначения до ручного разбора через UI.
