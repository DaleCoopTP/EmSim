# EmSim

Тренажёр диспетчера ДДС/112: одна Go-программа `emsim`
(`migrate | api | worker | bootstrap-admin | import | bench-llm`), PostgreSQL как БД и очередь
задач, веб-фронтенд поверх (см. `design-docs/`). Архитектурные решения —
[`design-docs/rfc-001-emsim.md`](design-docs/rfc-001-emsim.md) и
[`design-docs/adr/`](design-docs/adr); что и почему перенесено из
`orchestration-core` — [`docs/technical-discovery.md`](docs/technical-discovery.md).

## Локальный запуск (demo)

```bash
cp .env.example .env   # при желании поменять логин/пароль администратора
make model             # один раз: веса локальной модели в ./models (раздел «Модель»)
docker compose up --build
```

Без модели (например, для быстрой проверки интерфейса):
`docker compose -f compose.yaml -f compose.no-llm.yaml up --build`.

Поднимает `postgres`, применяет миграции (`migrate`), затем одноразовым
сервисом `bootstrap` создаёт начальную учётную запись администратора
(`BOOTSTRAP_ADMIN_LOGIN`/`BOOTSTRAP_ADMIN_PASSWORD` из `.env`, по умолчанию
`admin` / `local-only-admin-password` — сменить перед чем-либо, кроме
локальной демонстрации), затем одноразовым сервисом `seed` загружает
пилотный каталог служб/классификатора/сценариев и подготовленных голосовых
реплик (`seed/`, включая `pilot-phone-01`) от имени этого администратора, запускает `api` (`:8080` — публичный
API, `:8081` — `/healthz`/`/readyz`/`/metrics`) и один `worker --role=all`
(`:8082` — его собственные `/healthz`/`/readyz`/`/metrics`). `bootstrap` и
`seed` идемпотентны: повторный `docker compose up` не создаёт второго
администратора и не дублирует уже загруженный каталог (`make seed`
перезапускает только сервис `seed`, без остального стека — например, после
добавления файла в `seed/scenarios/`). Сервис `llm` — локальная модель
для ИИ-заявителя и судьи описания 112 (раздел «Модель» ниже); `worker` ждёт,
пока она загрузится. STT/Caddy добавятся вместе с их клиентами.

### Модель (ADR-029)

ИИ-заявитель 112 (`caller.reply`) и LLM-судья описания заявителя
(`DESCRIPTION_CONTENT`) по умолчанию работают через сервис `llm` —
`llama-server` из llama.cpp с моделью `T-lite-it-2.1` (Q5_K_M, GGUF),
[ADR-029](design-docs/adr/029-operator112-local-inference-container.md).
Контейнер без опубликованного порта и без выхода в сеть; веса читаются из
`./models` и не хранятся ни в git, ни в образе `emsim`.

Веса кладёт `make model` (`scripts/fetch-model.sh`) — один раз, на машине
с интернетом, при подготовке офлайн-пакета; дальше каталог `models/`
переносится вместе с поставкой. Источники:

```bash
make model                                # реестр Ollama (по умолчанию)
scripts/fetch-model.sh --from-ollama      # копия из локального Ollama (без скачивания)
scripts/fetch-model.sh --url <URL.gguf>   # любой прямой адрес, нужен LLM_MODEL_SHA256
```

Каждый источник проверяет sha256. Реестр и хранилище Ollama адресуют файлы
по их sha256, поэтому совпадение подтверждает, что в классе те же веса, на
которых качество проверялось через Ollama. Проверенное значение
закрепляется в `PINNED_SHA256` в `scripts/fetch-model.sh`, после чего
скрипт откажется устанавливать другой файл.

Без файла модели `llm` не проходит проверку здоровья и `worker` не
запускается: отсутствие модели видно при установке, а не на занятии.
Режим без модели — `compose.no-llm.yaml`: сервис `llm` выключен, заявитель
отвечает заглушкой из шести фраз (`stub/v1`), судьи нет, новые занятия 112
получают `rubric-v2`. На нём же работают e2e и CI. Для разработки с Ollama
на хосте (например, на Mac с GPU):

```bash
ollama serve
ollama pull t-tech/T-lite-it-2.1:q5_K_M
CALLER_REPLIER=llm ASSESSMENT_JUDGE=llm \
  docker compose -f compose.yaml -f compose.no-llm.yaml up --build
```

Адреса по умолчанию в `compose.no-llm.yaml` уже указывают на Ollama хоста
(`host.docker.internal:11434`).

Параметры (все переопределяются в `.env`; значения — до замера на
целевом сервере):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LLM_PARALLEL` | 4 | слоты `llama-server`: столько запросов обрабатываются одновременно |
| `LLM_CTX_SIZE` | 16384 | контекст на все слоты вместе (по 4096 на диалог при 4 слотах) |
| `LLM_THREADS` | 6 | потоки CPU |
| `LLM_REPACK` | true | переупаковка весов под CPU (`LLAMA_ARG_REPACK`): копия весов (~4,7 ГБ) в анонимной памяти; `false` — для машин, где Docker доступно ~8 ГБ (см. «Память» ниже) |
| `CALLER_CONCURRENCY` | 3 | одновременные ответы заявителя |
| `LLM_CONCURRENCY` | 1 | одновременные запросы судьи; вместе с `CALLER_CONCURRENCY` не больше `LLM_PARALLEL` |
| `CALLER_REPLY_TIMEOUT` | 30s | сколько ждать один ответ модели до повтора/нейтральной реплики |
| `CALLER_WARMUP` | true | прогрев: при ответе на вызов и при первой фразе оператора модель заранее обрабатывает начало разговора (api и worker) |
| `CALLER_OPENING_DELAY` | 0s | задержка вступления заявителя после первой фразы оператора (0–10 с), фора прогреву |
| `LLM_MODEL_FILE`, `LLM_MODEL_ALIAS` | `T-lite-it-2.1-Q5_K_M.gguf`, `t-tech/T-lite-it-2.1:q5_K_M` | файл в `models/` и имя модели в API и в evidence |

Память. При стандартных параметрах `llama-server` держит около 7,2 ГБ
анонимной памяти: веса, переупакованные под CPU (`CPU_REPACK`, ~4,7 ГБ),
и кеш контекста на `LLM_CTX_SIZE=16384` (~2,4 ГБ). Для сервера класса
(32 ГБ) это нормально. В Docker Desktop с 8 ГБ у виртуальной машины
(MacBook Air и т. п.) запас остаётся меньше 100 МБ, и загрузится ли модель,
зависит от того, чем ещё занята VM. Обычно ядро VM убивает `llama-server`
во время загрузки: `Out of memory: Killed process … (llama-server)` в
`dmesg` VM, события `oom`/`die` с кодом 137 в `docker events`, лог
обрывается на `load_model: loading model`, `llm` перезапускается по кругу,
`worker` его ждёт. `docker inspect` при этом показывает
`ExitCode=0`/`OOMKilled=false` — это состояние уже новой попытки после
рестарта, а не убитой. На такой машине задайте в `.env`:

```bash
LLM_REPACK=false
LLM_PARALLEL=1
LLM_CTX_SIZE=4096
CALLER_CONCURRENCY=1
```

Один слот с тем же контекстом на диалог (4096), что и по умолчанию;
анонимной памяти около 0,7 ГБ, веса читаются через mmap. Одного
`LLM_REPACK=false` мало: без переупаковки процесс не падает, но 5,4 ГБ
весов не помещаются в страничный кеш рядом с кешом контекста на 16384, и
генерация падает до ~0,3 токена/с. Скорость на MacBook Air (M-серия, CPU в
Docker) — около 6–9 токенов/с с переупаковкой и без неё одинаково.
Запросы судьи сверх одного слота ждут в очереди сервера.

Сколько одновременных диалогов выдержит сервер класса, заранее не
известно. Это измеряет `bench-llm` (замер W0, [`slice-112-5b-plan.md`](slice-112-5b-plan.md),
этап 2) — на поднятом стеке:

```bash
docker compose run --rm worker bench-llm --concurrency 1,4,8,20 --duration 2m --judge 1
```

Виртуальные операторы ведут многоходовые диалоги по ИИ-сидам через тот же
код и те же настройки, что и `worker`. Для каждого уровня отчёт даёт
ответы в минуту, p50/p95/p99 задержки ответа заявителя, долю ответов
дольше `CALLER_REPLY_TIMEOUT`, ошибки, задержку судьи и, из метрик
`llama-server`, скорость генерации и очередь сервера (`--json -` —
то же в JSON). Колонки `first p50/p95` — задержка первого ответа модели
в диалоге отдельно: он самый медленный, потому что без прогрева модели
приходится обработать весь промпт с нуля. `first new tok` — сколько
токенов промпта первый ответ обработал заново (остальное взято из кэша,
по данным `llama-server`). `warm sys p95`/`warm open p95` — длительность
двух прогревов, `warm ready` — в скольких диалогах оба прогрева успели
закончиться до первого вопроса к модели. Темп диалога: оператор пишет
первую фразу через `--first-line` (3 с) после ответа на вызов,
вступление приходит через `--opening-delay` (по умолчанию
`CALLER_OPENING_DELAY`), дальше — пауза `--think` (5 с) после каждого
ответа. Меняя `LLM_PARALLEL`, перезапускайте `llm`
(`docker compose up -d llm`).

**Прогрев (`CALLER_WARMUP`).** Модель заранее обрабатывает известное
начало промпта с бюджетом в один токен, и `llama-server` кладёт его в кэш.
Задачу `caller.warmup` ставит api, в два момента:

1. при ответе на вызов — правила роли и персонаж (почти весь промпт);
2. при первой фразе оператора — эта фраза и вступление заявителя
   (вступление задано в сценарии и приходит без модели, поэтому известно
   заранее).

Пока обучаемый печатает первую фразу и читает вступление, эта работа уже
сделана, и первому ответу модели остаётся разобрать только новый вопрос и
блок фактов. Генерацию самого ответа прогрев не ускоряет. Устаревший
прогрев (разговор ушёл дальше) пропускается. На данные занятия задача не
влияет: карточка, evidence и журнал не меняются, а при ошибке следующий
ответ просто начинается «с холода».

`CALLER_OPENING_DELAY` (по умолчанию 0) придерживает вступление после
первой фразы оператора и даёт прогреву фору. Выбирается по `bench-llm`:
если `warm ready` заметно меньше числа диалогов, задержка 2–3 с поможет.
Эффект прогрева видно, сравнив прогоны с `CALLER_WARMUP=false` и без него
по колонкам `first p50/p95` и `first new tok`.

Каждый ход модель заново разбирает только новый вопрос и служебный
блок в конце промпта (факты и задача хода). С `caller-prompt/v2` в блок
не попадают уже сообщённые факты, о которых сейчас не спрашивают, и он
в 2–3 раза короче, чем в v1.

Замер ниже — для прежнего варианта (один прогрев после вступления).
Прогрев занимает единственный слот так же, как ответ, и «с холода» длится
столько же, сколько разбор всего начала разговора. В профиле для 8 ГБ
(`LLM_PARALLEL=1`, `LLM_REPACK=false`, MacBook Air M4) модель разбирает
промпт со скоростью около 16 токенов/с, и холодный прогрев (~520 токенов)
длится около 31 с. Вопрос, отправленный раньше, ждёт его окончания в
очереди. Замер 27.09 на только что перезапущенном `llm`:

| пауза оператора | с прогревом | без прогрева |
|---|---|---|
| 20 с | 21,9 с | 39,3 с |
| 5 с | 36,1 с | 41,3 с |

При паузе 5 с выигрыш почти пропадает. Прогрев не мешает, но в таком
профиле помогает только при паузе оператора хотя бы 20–30 с. Если
обучаемые обычно отвечают быстрее, прогрев можно выключить
(`CALLER_WARMUP=false`) — вреда от этого тоже мало.
Сравнивайте `first p50/p95` только при одинаковом состоянии кэша:
перезапускайте `llm` перед каждым прогоном. Правила роли общие для всех
сценариев и остаются в слоте после предыдущего прогона, поэтому второй
прогон начинает «не с нуля».

`blob-data` — общий Docker volume seed/API/worker для content-addressed
голосовых файлов и записей докладов. Не удаляйте его при обновлении, если
нужно сохранить уже принятые записи.

Демо-профиль не ставит перед `api` reverse proxy с TLS, поэтому `api`
запускается с `COOKIE_SECURE=false` — иначе браузер не отправлял бы cookie
сессии обратно по обычному HTTP (ADR-008). Для класса используйте профиль
ниже.

### Класс: доступ по HTTPS (ADR-033)

В демо-профиле `api` слушает только `127.0.0.1`, и другие ПК класса к нему
не подключатся. Профиль класса `compose.class.yaml` ставит перед `api` Caddy:
- Caddy — единственный сервис, опубликованный в локальной сети (порты 443 и 80, с 80 редирект на https);
- сертификат выпускает внутренний CA Caddy;
- cookie сессии получает `Secure`;
- порт `api` больше не публикуется, health и metrics остаются на `127.0.0.1` сервера.

1. В `.env` задайте `EMSIM_HOST`: имя и/или IP, которые будут открывать РМ, например
   `EMSIM_HOST=emsim.local, 192.168.10.5`. Сертификат выпускается ровно на эти имена.
2. `make class-up` — то же, что
   `docker compose -f compose.yaml -f compose.class.yaml up -d --build`.
   Без модели добавьте `-f compose.no-llm.yaml` перед `compose.class.yaml`.
3. `make class-ca` выгружает корневой сертификат CA в `./emsim-root.crt`.
   Установите его один раз на каждый ПК класса как доверенный корневой:
   - Windows: «Доверенные корневые центры сертификации»;
   - Firefox: отдельно, в собственном хранилище браузера.
4. На РМ откройте `https://<EMSIM_HOST>/`.

Сертификат и ключ CA хранятся в томе `caddy-data`. Не удаляйте его при обновлении, иначе
сертификат придётся заново ставить на все ПК. SSE (монитор, обновление
карточек) проксируется без буферизации. Если 443 занят, задайте
`HTTPS_PORT` и открывайте `https://<host>:<port>/` напрямую: редирект с 80
ведёт на стандартный 443.

`docker compose up --build` собирает и веб-клиент (`web/`, стадия
`node:22-alpine` в `Dockerfile`) и встраивает его в бинарник `emsim`
(`web/embed.go`, `//go:embed`) — `api` сам раздаёт SPA на всех путях вне
`/api/`, отдельный веб-сервер не нужен (ADR-009).

Дальше — в браузере на `http://localhost:8080`: вход администратором →
«Рабочие места» (добавить РМ, сохранить) → «Пользователи» (создать
преподавателя и обучаемого со службой из уже загруженного каталога) →
«Выйти» → в другом браузере/профиле вход преподавателя → «Сценарии» —
пилотный каталог (два прохождения карточки «Дерево во дворе», одно с
намеренной ошибкой в округе — эталон, список оповещения и версии видны
без JSON) → «Выйти» → вход обучаемого с номером РМ → ФИО, служба, РМ и
«Ожидайте назначения занятия»; F5 сохраняет вход, «Выйти» отзывает сессию.

### Резервные копии и восстановление (ADR-033)

Worker каждый день в `BACKUP_AT` (по умолчанию 03:00 по `SCHEDULE_TZ`,
Europe/Moscow) делает копию в каталог хоста `BACKUP_HOST_DIR` (по
умолчанию `./backups`). Хранятся последние `BACKUP_KEEP` (14) копий. Копия —
каталог `emsim-YYYYMMDD-HHMMSSZ` (время UTC):
- `db.dump` — `pg_dump` в формате custom;
- `blobs.tar.gz` — голосовые файлы и записи;
- `manifest.json` — sha256 и размеры файлов, версия схемы.

Недописанная копия лежит в `.tmp-*` и копией не считается. Каталог можно
смонтировать на сетевой диск: копия на том же диске не спасёт от его отказа.

```bash
docker compose run --rm --no-deps worker backup     # копия сейчас, например перед обновлением
scripts/restore.sh backups/emsim-20260928-000000Z   # восстановление
```

`scripts/restore.sh` выполняет пять шагов:
1. Спрашивает подтверждение.
2. Останавливает `api` и `worker`.
3. Сверяет контрольные суммы копии и заменяет базу и блобы. Копию от более новой версии EmSim скрипт не восстанавливает.
4. Прогоняет миграции.
5. Поднимает стек.

Для профиля класса передайте overlays:
`COMPOSE="docker compose -f compose.yaml -f compose.class.yaml" scripts/restore.sh …`.

Раз в день в `AUDIT_PRUNE_AT` (04:00) удаляются записи журнала аудита
старше `AUDIT_RETENTION_DAYS` (183 дня).

### Удалённая модель (ADR-033)

Если сервер класса не тянет локальную модель, ИИ-заявитель и судья
подключаются к внешнему OpenAI-совместимому API. Сервис `llm` при этом не
запускается:

```bash
REMOTE_LLM_URL=https://llm.example/v1 REMOTE_LLM_MODEL=<модель> LLM_API_KEY=<ключ> \
  docker compose -f compose.yaml -f compose.remote-llm.yaml up -d --build
```

- Ключ уходит заголовком `Authorization: Bearer` и не пишется в логи и ошибки. Храните его в `.env`, а не в истории команд.
- Разные ключи для заявителя и судьи задаются через `CALLER_LLM_API_KEY` и `JUDGE_LLM_API_KEY`, судье можно дать другую модель — `REMOTE_JUDGE_MODEL`.
- `LLM_DIALECT=openai` (по умолчанию в этом профиле) отправляет только стандартные поля. Для удалённого `llama-server` или Ollama задайте `LLM_DIALECT=llama`.
- Реплики диалога с заявителем и описания заявителя при этом уходят за пределы учебного центра. Включайте режим только там, где это согласовано.

### Рабочее место ДДС: статусы реагирования (ADR-030)

Заказчик уточнил роль диспетчера ДДС 27.09.2026, уточнение совпадает с памяткой ДДС (стр. 21–32). Диспетчер ДДС **не правит** карточку 112. Его работа — статусы реагирования своей службы с комментариями.

**Службы.** Для этой работы в каталоге две службы:
- `dds_district_chertanovo` — ДДС района Чертаново Южное;
- `dds_ambulance_03` — диспетчерская скорой (03).

Обучаемому при создании назначается одна из них.

**Статусы в карточке.** Сначала нужно нажать «Открыть карточку». После этого в блоке своей службы внизу карточки появляется «✎». По нему выбирается статус и пишется комментарий, затем «Сохранить»:
- первичный статус — «Принята» или «Не принята»;
- после «Принята» — «Начало реагирования», «Прибытие», «Проведение работ», «Работы завершены» или «Отказ от выполнения работ»;
- комментарий обязателен для «Не принята» и «Отказ» (причина и куда передана информация);
- у 03 нет «Не принята» и «Отказ», вместо них — «Завершение работ без бригады».

«▾ История статусов» показывает сохранённые статусы с комментариями.

**Закрытие.** Финальный статус («Работы завершены», «Отказ», у 03 — «Завершение без бригады») сам закрывает карточку. Отдельной кнопки «Завершить упражнение» нет. Для этих служб сервер отклоняет `close`, `add_comment` и `set_card_field`.

**Статус карточки.** Очередь, шапка карточки и монитор преподавателя показывают вычисляемый статус карточки: «Зарегистрирована», «Не оповещено» (первичный статус не поставлен за 30 с), «В работе», «Отказ», «Завершена», «Не завершено» (прервана остановкой занятия).

**Сценарии.**
- `dds-district-tree-cycle-01` — дерево на проезде, доклады бригады о выезде, прибытии, работах и завершении;
- `dds-ambulance-cycle-01` — человек без сознания, 03;
- `dds-district-pipe-burst-01` (ДДС-2) — прорыв трубы в подъезде: звонки отдела контроля 112.

Во всех сценариях до «Начала реагирования» нужно позвонить руководителю бригады.

### Связь с бригадой (ДДС-2, ADR-031)

Справа от карточки — панель **«Связь с бригадой»**:
- телефон с контактами по ролям: «Бригада», «Отдел контроля 112», «Заявитель», «Прочие». Если записанной фразы нет, телефон показывает её текст;
- журнал: доклады бригады, входящие и исходящие звонки по времени.

**Доклады после звонка.** Во вторых версиях сценариев (`-v2`) и в новом сценарии доклады бригады привязаны к завершению **первого исходящего звонка** руководителю бригады (`since: call_ended` + `since_contact`), а не к статусам обучаемого. Не позвонил — докладов нет. Первые версии со старыми якорями по статусам работают по-прежнему.

**Входящие звонки.**
- Событие `phone_incoming` звонит 30 с. До ответа виден только звонящий, его слова появляются после «Ответить» (`answer_incoming {event_key}`).
- «Завершить разговор» — это `call_end` без «Кто принял / Суть». Во время разговора исходящий «Вызов» недоступен.
- Не отвеченный за 30 с звонок становится пропущенным.

Отдел контроля в `dds-district-pipe-burst-01` звонит, только если первичный статус не поставлен вовремя (`status_in: [received]`). Обязательный звонок засчитывает только исходящий звонок.

**Для преподавателя.** Монитор показывает колонку «Связь»: последний доклад, давность и фактическую задержку реакции — первый сохранённый статус после доклада или ответа, а также число пропущенных звонков. Разбор карточки показывает хронологию связи с текстами. Оценку этих задержек даёт рубрика `dds/rubric-v2` (ДДС-3, ниже); `expects.comment_facts` оценит ИИ-судья ДДС-4.

**Старые пилоты.** Пилоты срезов 2–7 («Дерево во дворе», правка округа по ADR-017) помечены в файлах флагом `"archived": true`. Каталог их больше не показывает, фильтр «архив» (`status=archived`) — показывает. Их прошлые занятия, оценки и отчёты читаются как раньше.

Приёмочные проверки:
- интеграционные тесты `TestDDSResponseCycleThroughAPIAndWorker` и `TestDDSCrewCommunicationThroughAPIAndWorker` (ДДС-2);
- браузерный `web/e2e/smoke.spec.ts`: цикл «карандашом», доклад после звонка бригаде, ответ на входящий звонок, разбор преподавателя.

### Рубрика ДДС v2 (ДДС-3, ADR-032)

Каждое новое занятие ДДС замораживает `dds/rubric-v2` (`design-docs/contracts/rubric.dds.v2.json`) — детерминированную рубрику под роль диспетчера из ADR-030, без критериев, которые ДДС больше не выполняет (правка карточки, журнал звонка, написание адреса словами). Занятие, уже замороженное на `dds/rubric-v1` до этого среза, продолжает оцениваться по v1 без изменений.

Семь критериев: `T_OPEN`/`T_PRIMARY` (нормативы открытия и первичного статуса, как в v1), `D_PRIMARY` (первичное решение совпадает с эталоном), `T_PROGRESS` (реакция на каждый доклад бригады не позже `expects.within_s`), `S_SEQUENCE` (статус отражает доклад и ожидаемую цепочку — статус, поставленный раньше доклада, штрафуется здесь, а не в `T_PROGRESS`), `D_COMMENT_REQUIRED` (обязательные комментарии на месте) и `C_CALLS` (обязательный исходящий звонок бригаде и ответ на входящие звонки из `reference.required_contacts`). Веса: 10/10/25/20/15/10/10, порог 70, critical_cap 40.

У `dds/rubric-v2` нет ни одного LLM-критерия (это ДДС-4), поэтому карточка без докладов и звонков (например, старый пилотный сценарий) получает `not_applicable` по `T_PROGRESS`/`S_SEQUENCE`/`D_COMMENT_REQUIRED`/`C_CALLS` и `ready` с полным баллом по оставшимся — в отличие от `dds/rubric-v1`, где `G_GRAMMAR` при `ASSESSMENT_JUDGE=off` был безусловно `unavailable` и любая авто-оценка получала `needs_review`. Исходящий звонок на службах с непустым `terminal` (ADR-030) больше не требует «Кто принял»/«Суть сообщения» — диспетчер ДДС не ведёт письменный журнал звонка.

Приёмочная проверка: `test/integration/dds_rubric_v2_test.go` (`TestDDSRubricV2ThroughAPIAndWorker`) — новое занятие получает `dds/rubric-v2` и реальные `met`/`partial` по `T_PROGRESS`/`S_SEQUENCE`/`C_CALLS`; занятие, замороженное на `dds/rubric-v1`, оценивается по v1 без пересчёта.

### Вызов и уточняющий опрос оператора 112

Архивный пилот `pilot-112-medical-01`: заявитель 19 лет звонит
о сильной диарее и обильной рвоте с московского адреса улица Космонавтов,
дом 2, корпус 3, ориентир — метро ВДНХ. АОН `+79161313131`, сценарное
время `02:03 МСК`. Это учебные данные; отправка идёт только в учебную
службу `pilot_ambulance` внутри тренажёра.

Администратор создаёт РМ, преподавателя и обучаемого (для 112 служба в
профиле обучаемого не требуется). Преподаватель в «Занятиях» создаёт
занятие типа «Оператор 112», назначает РМ, обучаемого и активный сценарий,
сохраняет назначения и запускает занятие. Обучаемый входит с номером РМ,
открывает вызов, отвечает, выбирает уточняющие вопросы, заполняет и сохраняет карточку, направляет
сохранённую версию в учебную скорую, завершает разговор и обработку.
Рабочее место располагает телефонные блоки и таймер сверху, поля заявителя
и адреса слева, текстовый разговор справа, а единственную службу «03»
и действия снизу. Ответы появляются только после соответствующих вопросов;
заявитель может дать неполный ответ или сказать, что не знает сведений.
В компактной строке заявителя вводятся ФИО, статус и оператор/канал связи;
новая карточка не подставляет оператора автоматически. Поля возраста и
иностранного языка в учебной форме не показываются. Адрес целиком виден в
своём блоке; на низком экране прокручивается страница. Индикатор учебной
телефонии в карточке можно переключить вручную до её открытия. При открытой
карточке и ещё 10 секунд после закрытия он показывает «Недоступен», затем
возвращается к сохранённому в этом браузере ручному выбору. Это не состояние
реальной телефонной сети.
Разговор можно поставить на удержание и продолжить. Ответы не переносятся
в карточку автоматически. Предоставленный телефон и телефон на место можно
заполнить вручную или скопировать из АОН. «Нет контакта» до ответа и
«Срыв звонка» во время разговора закрывают карточку без направления в 03.
В разговорных назначениях выбор типа и профильная карта пока не используются.
F5 возвращает подтверждённый черновик и состояние вызова; карточку после
перезагрузки нужно открыть из списка заданий. В «Разборе»
преподаватель видит разговор, выясненные факты, сохранения карточки и снимок отправки,
выставляет оценку; результат появляется у обучаемого в «Истории» с
фильтром «Оператор 112».

Три новых назначения 112-3 — «Взрыв газа», «ДТП с пламенем» и их комбинация —
работают без симуляции разговора. После открытия кейса обучаемый сам добавляет
тип происшествия; только тогда появляется карта 104, 101 или обе. В картах
нет заранее выбранных ответов. Неполный черновик можно сохранить, затем
кнопкой «+» открыть окно «Список оповещаемых служб» — предложенные по правилам
каталога службы уже отмечены, добавление или снятие службы вручную требует
причины изменения — и одним действием «оповестить и сохранить карточку»
зафиксировать неизменяемую запись оповещения (адресаты, признак
предложена/добавлена вручную, снимок карточки, время); после этого карточка
закрыта для правок, а «Завершить» становится доступно. Отправка в ДДС в этом
режиме не создаётся.
Определения карт и правила предложений находятся в отдельном версионированном
каталоге, версия которого фиксируется для занятия; кейс хранит собственный
закрытый эталон типов, но не экземпляры карт. Карта 104 на исходном образце
описывает запах газа, поэтому её достаточность для учебного «взрыва газа»
ещё требует профильной приёмки.
API обучаемого выдаёт определения только уже добавленных карт; условия правил
подбора служб и ответы удалённых карт в этой выдаче скрыты.
На одном РМ можно назначить несколько кейсов 112 в заданном порядке: после
завершения текущего появляется следующий. Оператор может вернуться к списку
входящих кейсов, включая только что обработанный; после последнего кейса
список остаётся доступен до ухода с рабочего места.
После добавления кейса форма назначения выбирает следующий доступный сценарий.
Новые кейсы можно также дописать в конец уже сохранённой очереди до запуска
занятия; сохранённые версии при этом остаются теми же.

Архивный кейс среза 112-4 — комбинированный
`pilot-112-full-gas-road-traffic-fire-01`: разговор 112-2 и профильные карты
112-3 в одном задании на той же вёрстке карточки. Обучаемый отвечает на
вызов, выясняет адрес и число пострадавших уточняющими вопросами, добавляет
тип «Взрыв газа и ДТП с пламенем» (карты 104 и 101 появляются сразу),
сохраняет карточку, оповещает предложенные службы тем же окном «Список
оповещаемых служб» и завершает обработку после завершения разговора. Кнопки
«нет контакта»/«срыв звонка» доступны, пока карточка не оповещена, как в
разговорных сценариях 112-1/112-2. Кейсы `card_only`, начатые до этого среза
(без поля `finale` в их состоянии), и разговорные `incoming_call`-сценарии
продолжают прежний маршрут (`review_service_selection`/`complete_profile_case`
и, соответственно, «Направить в 03») без изменений — старые записи и evidence
читаются как раньше. Преподаватель видит запись оповещения (адресаты, признак
предложена/добавлена вручную, причина, время) в мониторе занятия и в «Разборе»
карточки. Профильная приёмка карт 104/101 и правил подбора служб (112-3) ещё
не пройдена; повторное сохранение карточки и повторное оповещение после
первого действия не реализованы — открытый вопрос до уточнения заказчика
(см. [`slice-112-4-plan.md`](slice-112-4-plan.md), раздел «Открытый вопрос»).

Срез 112-5a добавляет для `full_case` со сценарием `intake112.caller_mode:
"free_text"` (архивный технический пилот — `pilot-112-free-text-chat-01`) отдельное плавающее окно
«Чат с заявителем» поверх карточки вместо подготовленных вопросов 112-2:
оператор пишет заявителю своими словами, а ответ формируется асинхронно —
фоновой задачей `caller.reply` в собственном пуле worker, вне транзакции
команды (см. [ADR-024](design-docs/adr/024-operator112-async-caller-reply.md)).
В этом срезе ответ даёт детерминированная заглушка (шесть фиксированных фраз
по кругу, `adapter: "stub/v1"`, не связаны с фактами конкретного сценария) —
настоящая модель подключится в 112-5b той же заменой одного порта
`CallerReplier`. Ответ заявителя не увеличивает `items.seq`, поэтому черновик
карточки переживает асинхронный рефетч. Удержание, завершение разговора или
остановка занятия во время ожидания ответа отменяют ход (`cancelled`) или
оставляют его `pending` на барьере stop — новый ответ на такой ход не
применяется. Преподаватель видит в «Разборе» статус каждого хода (отвечен/нет
ответа по технической причине/отменён/без ответа на момент остановки) вместе
с адаптером, а в мониторе — подпись «Сообщение заявителю» как последнее
действие. Задержка ответа заглушки настраивается `CALLER_STUB_DELAY`
(по умолчанию 1с — `compose.yaml`; e2e снижает её через `run.mjs`, не трогая
продовое значение), очередь ответов — `CALLER_CONCURRENCY`/
`CALLER_REPLY_TIMEOUT`.

Срез 112-5b подключает модель к тому же окну чата, заменяя только
реализацию порта `CallerReplier` — асинхронный протокол ADR-024 не меняется
(см. [ADR-025](design-docs/adr/025-operator112-ai-caller.md)). По умолчанию
(ADR-029) `CALLER_REPLIER=llm` — `aicaller.Replier` поверх сервиса `llm`;
`CALLER_REPLIER=stub` (так в `compose.no-llm.yaml`) возвращает
детерминированную заглушку `stub/v1` без зависимости от модели. В режиме
`llm` regex-классификатор решает, какие факты сценария уже
открыты и раскрыты ли они, модель формулирует ответ. Сценарий без профиля
заявителя (`intake112.dialogue.caller`, например `pilot-112-free-text-chat-01`)
под `CALLER_REPLIER=llm` всё равно отвечает заглушкой — видно по `adapter` хода.

Как запустить с моделью или с Ollama на хосте — раздел «Модель» выше.
Три сида для проверки — `pilot-112-ai-toyota-fire-01`,
`pilot-112-ai-car-in-water-01`, `pilot-112-ai-mobile-shop-01`
([`seed/README.md`](seed/README.md)). В «Разборе» преподавателя у каждого
отвеченного хода видны источник (вступление/фиксированный ответ/модель/
нейтральная реплика при недоступности модели/заглушка) и, для модели и
нейтральной реплики, использованная модель и версия промпта. Ответ на

### Автоматическая оценка оператора 112 (срез 112-6)

Каждая новая версия занятия 112 замораживает рубрику
`operator112/rubric-v2` ([ADR-026](design-docs/adr/026-operator112-assessment-rubric-v2.md)):
6 детерминированных блоков на 100 баллов (адрес — 35, профильные карты — 25,
темы разговора с заявителем — 15, норматив ответа на вызов и норматив
заполнения карточки — по 7,5, описание со слов заявителя — 10) и 4 штрафа
(неверная страна/субъект −10, неверное ФИО заявителя −5, неверный список
служб −5 за каждую расхождение, лишняя профильная карта −5 за карту).
Закрытие карточки ставит ту же `assessment.evaluate`, что и у ДДС (RFC-001
§7.4): `internal/assessment/operator112` сравнивает не сам транскрипт, а
отправленный (или, если оповещения не было, итоговый) снимок карточки с
эталоном сценария — `intake112.reference` в версии сценария. **Если у
кейса ещё нет эталона (сейчас — все сиды), блок или штраф, зависящий от
эталона, получает обычный результат по той же бизнес-логике, что и с
эталоном, просто с нулевым баллом** («эталон не задан» в основании), а не
специальный статус вроде `not_applicable`/`needs_review` — так что
детерминированная `auto rev=1 ready` создаётся всегда, даже без эталона.
`not_applicable` остаётся только за объективной неприменимостью: `card_only`
без разговора, вызов не был принят, сбой сервера. Чтобы добавить эталон к
уже существующему кейсу, готовится **новая версия того же сценария**
(`version+1` при повторном `emsim import scenarios`) с заполненным
`intake112.reference.expected_card`/`.expected_profiles`/`.alternatives`/
`.scoring` — подробный формат в [`seed/README.md`](seed/README.md);
конвейер оценки при этом не меняется, только следующие прохождения этой
версии сразу сравниваются с реальным эталоном. Разбор преподавателя
(`ItemReview.tsx`) показывает блоки и штрафы отдельными таблицами с
раскрываемыми основаниями по каждому полю/карте/службе и позволяет
поправить их численно; отчёт занятия, CSV и PDF показывают ту же разбивку
двумя дополнительными колонками только для строк 112.

**LLM-судья описания заявителя (`operator112/rubric-v3`, ADR-028).** По
умолчанию (ADR-029) `ASSESSMENT_JUDGE=llm` — **и в api, и в worker** — и
новое занятие замораживает `rubric-v3`, где вместо `DESCRIPTION_PRESENT`
(поле непустое = 10 баллов) стоит блок `DESCRIPTION_CONTENT`: контрольные вопросы из
`intake112.reference.description_questions` отправляются модели (только
текст описания и вопросы, без транскрипта и без эталона других полей),
модель отвечает по каждому `yes`/`no`/`needs_review`; баллы (10 поровну
между вопросами) считает бэкенд, не модель. Любой `needs_review` или сбой
модели после исчерпания попыток задачи — весь критерий `unavailable`, вся
оценка `needs_review` без балла, ученику ноль не ставится; преподаватель
довершает вручную, как любой другой критерий. Нет вопросов в эталоне или
незаполненное описание — обычный ноль без обращения к модели (то же
правило «эталон не задан»). Модель вызывается только вне транзакции
записи оценки, тем же принципом ADR-003/025. Промпт и подсчёт перенесены
из архивного прототипа пользователя (94,8% совпадений на 132 описаниях,
`handoff/claude_evaluator_112_20260926.zip`); вопросы добавлены версией 2
только трём существующим ИИ-сидам (`pilot-112-ai-{car-in-water,
mobile-shop,toyota-fire}-01-v2.json`), подробности — [`seed/README.md`](seed/README.md).

`ASSESSMENT_JUDGE=off` (так в `compose.no-llm.yaml`) оставляет `rubric-v2`
без изменений; значение должно совпадать в api и worker. Судья и
ИИ-заявитель по умолчанию обращаются к одной модели в сервисе `llm`
(`JUDGE_LLM_URL`/`JUDGE_LLM_MODEL` и `CALLER_LLM_URL`/`CALLER_LLM_MODEL`),
но включаются и выключаются независимо друг от друга. Температура судьи —
0: ответ на одно и то же описание повторяем. Разбор преподавателя (`ItemReview.tsx`,
`IntakeAutoAssessment.tsx`) показывает ответ по каждому вопросу и модель
судьи (`assessment.model`) без изменений остальной панели; редактор
сценариев — вкладку «Эталон» → «Вопросы к описанию».

### Редактор сценариев 112 (срез 112-7)

Преподаватель создаёт кейс 112 через UI, без правки JSON: «Сценарии» →
«+ Создать сценарий 112» открывает редактор из пяти вкладок (Общее,
Заявитель, Факты, Эталон, Проверка). Редактор ([ADR-027](design-docs/adr/027-operator112-scenario-editor.md))
работает только со сценариями `intake112.mode="full_case"` +
`caller_mode="free_text"` (ИИ-заявитель) — авторинг подготовленного
(`prepared`) диалога и `card_only`-кейсов по-прежнему только файловым
импортом (`seed/README.md`). Каждое сохранение создаёт новую версию
черновика (`base_digest` с прошлого чтения — при несовпадении `409
stale_draft`); черновик виден и правится только автором, утверждённая
версия — всем преподавателям, скопировать чужой утверждённый сценарий в
свой черновик может любой. Вкладка «Проверка» показывает список замечаний
(`error` блокирует предпросмотр/утверждение, `warning` — нет) и тестер фраз
(какие факты сценария классификатор откроет по пробной реплике, без
обращения к модели).

«Пройти самому (предпросмотр)» запускает одноразовое занятие
`mode=preview` без рабочего места, где единственный участник — сам автор;
экран предпросмотра — тот же `Operator112ProfileCase`/чат с заявителем,
что видит обучаемый. Закрытие кейса ставит настоящую автооценку
`operator112/rubric-v2`, видимую автору через разбор карточки, но
предпросмотр не появляется в списке занятий, отчётах, CSV/PDF, истории и
прогрессе (сравнение с трактовкой «эталон не задан» из среза 112-6 выше не
случайно: обе используют один и тот же путь оценки). «Утвердить» переводит
черновик в `approved` (прежняя утверждённая версия — в `superseded`) и
делает сценарий доступным для назначения в обычном конструкторе занятия,
как любой другой утверждённый сценарий 112.

Обновление уже развёрнутой установки (новая миграция добавляет каталог
служб как внешний ключ у `users.service_code`) и диагностика конфликтов при
повторной загрузке каталога — [`seed/README.md`](seed/README.md).

То же через API — curl-пример (`service_code` — код из уже загруженного
каталога, `GET /api/v1/services`; неизвестный код `admin/users` отклоняет
с `422 validation_failed`, срез 2, C5):

```bash
curl -c cookies.txt -s -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"admin","password":"local-only-admin-password"}'

curl -b cookies.txt -s -X PUT http://localhost:8080/api/v1/admin/workstations \
  -H 'Content-Type: application/json' \
  -d '[{"number":5,"label":"РМ-05"}]'

curl -b cookies.txt -s -X POST http://localhost:8080/api/v1/admin/users \
  -H 'Content-Type: application/json' \
  -d '{"login":"trainee-05","password":"correct-horse-battery-staple","full_name":"Иванов Иван","role":"trainee","service_code":"dds_district"}'
```

## Разработка

```bash
make verify              # gofmt, build, go vet, go test, staticcheck (не требует Node)
make test-integration    # очередь/recovery + запуск и crash recovery реального worker (PostgreSQL 16)
make compose-config      # проверить compose.yaml без сборки образов
make seed                # перезапустить только одноразовый сервис seed поверх уже поднятого стека
make verify-web          # web/: npm ci, регенерация типов из openapi.yaml, tsc, vite build
cd web && npm run test:e2e # Chromium: разговорный 112, три профильных кейса, комбинированный full_case и регрессия ДДС в изолированном compose
python3 design-docs/contracts/check.py   # офлайн-проверка контрактов (openapi.yaml, *.schema.json, примеры)
cd web && npm run lint   # oxlint
```

`go build`/`make verify` не требуют Node: `web/dist` несёт закоммиченный
`.gitkeep`-плейсхолдер, так что `//go:embed all:dist` компилируется и без
собранного SPA — `api` в этом случае отвечает на любой путь вне `/api/`
тем же закрытым конвертом ошибок с понятным сообщением про
`make web-build`. Разработка самого клиента — см. [`web/README.md`](web/README.md)
(`npm run dev` на `:5173` с прокси `/api` на запущенный отдельно `emsim api`).

`make test-integration` использует Docker (testcontainers). Без Docker —
поднять локальный PostgreSQL 16 и передать `TEST_DATABASE_URL` (отдельная
пустая тестовая БД, схема на время теста пересоздаётся):

```bash
TEST_DATABASE_URL="postgres://user@localhost:5432/emsim_test?sslmode=disable" \
  go test -tags=integration -count=1 ./test/integration/...
```


Операции очереди используют часы PostgreSQL; проверка lease выполняется после
получения блокировки строки. Для атомарной записи доменного эффекта используйте
`EnqueueTx`, `CancelTx` и `Terminal` с общей `pgx.Tx`: вызывающий код отвечает
за commit/rollback. Повтор `Terminal` сравнивает статус, код ошибки и JSONB-результат
(порядок ключей несущественен); изменение результата возвращает конфликт.

Интеграционный process-тест собирает `cmd/emsim`, проверяет реальные роли
`worker/maintenance/all`, graceful shutdown и SIGKILL во время фиксации noop.
Для ускорения теста expiry оставшегося lease меняется в тестовой БД; reaping и
повторное выполнение выполняют настоящие процессы приложения.

Второй process-тест (`test/integration/api_process_test.go`) собирает тот же
бинарник и проходит срез 1 целиком через настоящий HTTP: `migrate up` →
`bootstrap-admin` (дважды — второй запуск должен остаться no-op) → `api` →
вход администратора → создание РМ/преподавателя/обучаемого → выход
администратора и отказ по старой cookie → вход обучаемого с РМ → `GET /me`
после «перезагрузки страницы» → 403 у обучаемого на административный API →
выход обучаемого → отказ по неверному паролю.

Тот же файл добавляет сквозной каталожный тест среза 2: `migrate up` →
`bootstrap-admin` → `emsim import seed` → `api` — преподаватель видит
каталог и просмотр карточки без утечки закрытых полей (`pilot_goal` не
покидает `reference`), администратор доходит до `/services`, но получает 403
на `/scenarios`, неаутентифицированный запрос — 401, а создание обучаемого с
неизвестным `service_code` — настоящий 422 от работающего процесса `api`.

Срез 4 (групповые занятия, очереди, hard, монитор, stop, SSE, restart
recovery) проверяется на трёх уровнях: unit — Hub epoch/cursor/resync
(`internal/platform/realtime/hub_test.go`); `training.Service` напрямую
против настоящего PostgreSQL (`test/integration/training_service_test.go`) —
независимые очереди нескольких участников на одной и на разных версиях
сценария, конкурентные команды на одной карточке, hard-очередь (валидация
`spawn_every_s`, ровно одна выдача за tick даже после часового простоя
планировщика — RFC-001 §7.2 «пропущенные интервалы не воспроизводятся
пачкой»), stop как барьер с durable `lesson.close`, восстановление после
рестарта (идемпотентные маркеры interruption, дедлайны и `due_at` карточек/
событий не сдвигаются, просроченное событие доставляется с `late=true`),
`control_report` — реплей, устаревший `expected_seq`, доказанная неизменность
evidence — и живой `RunListener` поверх настоящего `LISTEN`/`NOTIFY`
(`test/integration/realtime_test.go`); и, наконец, HTTP end-to-end через
настоящий процесс `api` (`test/integration/training_realtime_e2e_test.go`,
`TestAPIProcessSSEStreamSnapshotReplayResyncAndFiltering`) — RFC-001 §7.7
целиком: `stream.ready` раньше любого другого события, переподключение по
`Last-Event-ID` и по запасному `?cursor` (для нового `EventSource`
без заголовков) реплеит пропущенное, неизвестный cursor даёт `resync`, а
поток преподавателя и поток каждого обучаемого не видят чужих событий.

Срез 5 добавляет браузерный телефон: `pilot-phone-01` (с ADR-030 в архиве каталога) требует до статуса
`accepted` завершить звонок руководителю бригады (4152), сообщив адрес,
тип происшествия и принятые меры. Новые сценарии ДДС требуют того же звонка до «Начала реагирования». В seed включены записанные greeting/ack
в PCM WAV, mono, 16-bit, 16 kHz. Тест
`TestTrainingPhoneCallRecordingAndEvidenceEndToEnd` проходит звонок,
manifest/upload/replay, закрытие/evidence и доступ к записи преподавателя.

Для ручной приёмки в Chrome, Edge и актуальном Яндекс Браузере разрешите
микрофон на странице рабочего места, завершите звонок и убедитесь, что
состояние записи стало `ready`. Отдельно проверьте отказ в разрешении
(звонок завершается с `recording=null`) и повтор загрузки после временного
разрыва сети; незагруженные байты после перезагрузки вкладки восстановить
нельзя, и после deadline состояние отображается как `missing`.
Автоматический Chromium-e2e запускается через `cd web && npm run test:e2e`:
он поднимает отдельный Docker Compose project на свободных localhost-портах
(с `compose.no-llm.yaml`: заглушка заявителя, без судьи и без модели),
использует seed WAV как fake microphone и после завершения удаляет только свои
контейнеры и volumes. В CI этому соответствует job `web-e2e`.

Срез 6 добавляет разбор оценки преподавателем. При закрытии training-карточки
worker сначала запечатывает `assessment_inputs`, затем создаёт одну
детерминированную `auto`-ревизию. Пока LLM-проверки не подключены, такая
ревизия имеет `needs_review` и пустой итоговый балл — это ожидаемое состояние,
а не ошибка очереди. Преподаватель открывает завершённое или остановленное
занятие → «Разбор», видит доказательства правил, журнал и записи звонков, и
сохраняет экспертную ревизию как итоговую. Для этого в Compose должен работать
worker с `LLM_CONCURRENCY>=1` (стандартный `.env.example` уже задаёт это).

Приёмочный тест `TestAssessmentPipelineThroughAPIAndWorker` проходит реальный
API и отдельный процесс worker: закрытие → auto `needs_review` → список
разбора → экспертная ревизия. Дополнительно `assessment_pipeline_test.go`
проверяет finalizer, потерю lease, ручную оценку без auto и гонки ревизий.

Срез 7 добавляет отчёт по завершённому занятию: преподаватель открывает
«Отчёт» из карточки занятия, получает текущую JSON-сводку и CSV, а PDF
запрашивается как отдельный неизменяемый снимок. Пока файл строится, интерфейс
показывает его состояние; готовый файл скачивается по ссылке из списка
артефактов. Построение выполняется в отдельном пуле `report`
(`REPORT_CONCURRENCY=1` в demo Compose), поэтому не задерживает закрытие
занятий. Обучаемый видит «Историю» только со своими карточками, статусами
оценки и безопасной обратной связью; эталоны, evidence и причины экспертной
проверки туда не попадают.

Приёмочный тест `TestReportingThroughAPIAndWorker` проходит законченное
занятие через реальный API и worker: экспертная оценка → JSON/CSV → очередь
PDF → скачивание blob, затем проверяет личные `/my/results` и `/my/progress`
без закрытых полей.
