# EmSim — design docs

Пакет по методике «продуктовая задача → discovery → RFC → ADR → диаграммы для решений → контракты». Актуальный скоуп задают согласованный контекст УМЦ ГО ЧС и RFC; ссылки на `docs/` ниже — исторические материалы, не действующее ТЗ.

| Шаг | Артефакт | Где |
|---|---|---|
| 1 | Продуктовая задача | [`../docs/product-task.md`](../docs/product-task.md) |
| 2 | Technical discovery (что берём из orchestration-core) | [`../docs/technical-discovery.md`](../docs/technical-discovery.md) |
| 3 | **RFC-001: EmSim** — problem, goals/non-goals, use cases, архитектура, API, модель данных, критические потоки, consistency/failure, security, observability, capacity, alternatives, rollout | [`rfc-001-emsim.md`](rfc-001-emsim.md) |
| 3 | ADR — по одному решению на файл | [`adr/`](adr/) |
| 4 | Диаграммы, которые помогли принять решения: контекст/компоненты, последовательности критических сценариев, ER | [`diagrams/`](diagrams/) |
| 4 | Контракты: OpenAPI, DDL, JSON-схемы сценария / evidence / входа оценки / SSE-событий / задач | [`contracts/`](contracts/) |

## Как читать

1. `rfc-001-emsim.md` целиком — 30 минут. Это документ для обсуждения; после реализации становится архивом решений.
2. Не согласен с решением — открой соответствующий ADR: там контекст, варианты и последствия. Изменение решения = новый ADR, старый помечается «superseded».
3. Контракты — то, что дорого менять после начала кода: пути и тела API, таблицы, формат сценария и событий. Правки в них проходят через обновление RFC.

## Статус

Черновик после согласованных исправлений design review от 18 сентября 2026. Принятые пункты и отложенные вопросы — [ADR-014](adr/014-accepted-design-review-corrections.md); основной текст — RFC. Реализация ещё должна пройти конкурентные acceptance-проверки.

Последующее уточнение — [ADR-015](adr/015-dds-first-operator112-extension.md): сначала реализуется ДДС, затем оператор 112 со своей рубрикой; сейчас заложены только минимальные точки расширения. Порядок разработки бэкенда и фронтенда — RFC §13.

## Проверка

```bash
python3 design-docs/contracts/check.py
```

Нужны Python-пакеты `PyYAML` и `jsonschema`. Проверяются JSON-схемы, примеры, локальные ссылки OpenAPI и отрицательные примеры согласованных контрактов.

При заданном `DATABASE_URL` дополнительно применяются `schema.sql` и `check-invariants.sql`: единственная автооценка, приоритет экспертной ревизии, неизменяемость артефактов, исторический отчёт и ограничения состояний. Использовать только отдельную пустую тестовую БД; проверка создаёт схему, а тестовые данные откатывает. Для этого шага нужен `psql`. Без `DATABASE_URL` SQL-проверка явно пропускается. Конкурентное исполнение будущего приложения этими проверками не покрывается.

Последнее согласованное ревью — [ADR-016](adr/016-review-fixes-and-mvp-simplifications.md). Оно упрощает восстановление и хранение оценки; ограничения сохранности аудио и таймингов явно отражены в RFC и контрактах.
