## 1. Problem statement

УМЦ ГО ЧС обучает диспетчеров ДДС, которые в АРМ-112 получают карточки происшествий от системы-112 и отрабатывают их: принимают/отклоняют, докладывают руководству по телефону, ведут статусы реагирования, пишут комментарии. Сейчас нет тренажёра: обучение идёт по бумажным билетам без интерфейса, без нормативов времени и без объективной оценки.

Нужен локальный веб-тренажёр: группа из 20–30 курсантов одновременно отрабатывает карточки в копии интерфейса АРМ-112; преподаватель готовит задания (в том числе с помощью локальной LLM), наблюдает занятие в реальном времени, получает автоматическую оценку с правом исправить её и отчёты по прогрессу.

## 2. Goals / Non-goals

**Goals (MVP к защите)**

- G1. Обучаемый отрабатывает карточку в интерфейсе, который эксперт УМЦ узнаёт как АРМ-112: список карточек, карточка, список оповещения, статусы по правилам памятки, комментарии, кнопка «в отдел контроля».
- G2. Симулятор телефона: набор номера → фраза → запись доклада → фраза; без реальной телефонии.
- G3. События сценария по таймлайну (сообщения бригады, новые карточки) и серверные нормативы 30 с / 3 мин.
- G4. Преподаватель: сценарии (ручные, из билетов, сгенерированные LLM с утверждением), занятие с назначением по РМ, live-монитор, стоп.
- G5. Автооценка после карточки: детерминированные критерии + LLM по комментарию/докладу; преподаватель правит, правка — итоговая.
- G6. Результаты обучаемого, отчёты (таблицы, графики, CSV и PDF) и рекомендация уровня для преподавателя; краткий совет «над чем работать», сформированный LLM по статистике ошибок.
- G7. 30 РМ одновременно на одном сервере без GPU; полностью офлайн; docker compose.
- G8. Надёжность: подтверждённые действия сохранены на сервере; одна неподтверждённая команда на карточку переживает перезагрузку через localStorage. Незагруженное аудио хранится в памяти и при закрытии вкладки может потеряться; отсутствие записи явно показывается. После сбоя сервера временные критерии затронутых карточек не оцениваются (ADR-016).

**Non-goals**

- N1. Режим оператора 112 с приёмом обращения и заполнением карточки входит в общий объём, но реализуется после ДДС. В первом этапе закладываются только точки расширения (§4.5, ADR-015); подробный процесс 112 обсуждается отдельно.
- N2. SIP/WebRTC/Asterisk, VoIP-задержки, аппаратные телефоны.
- N3. Интерактивный голосовой диалог с ветвлением; LLM в реальном времени в цикле обучаемого.
- N4. Интеграция с боевой системой-112, доменная аутентификация, MFA.
- N5. Горизонтальное масштабирование за пределы одного сервера (описано как профиль, не реализуется).
- N6. Мобильная версия.
- N7. Fine-tune модели на правках преподавателя (накапливаем данные, не обучаем).

## 4. Архитектура

### 4.1 Обзор

Модульный монолит на Go (ADR-001): один бинарник `emsim` с подкомандами `api`, `worker`, `migrate`, `import`. Одна база PostgreSQL 16 — данные, очередь задач и шина уведомлений (ADR-002). Фронтенд — SPA на TypeScript/React, отдаётся тем же процессом (ADR-009). Локальные модели — отдельные контейнеры `llama.cpp` и `whisper.cpp` с HTTP, вызываются только worker'ом (ADR-003). Reverse proxy Caddy — TLS и единая точка входа.

```
                    браузеры РМ-01…РМ-30, ПК преподавателя, админ
                                        │ HTTPS
                                   ┌────▼────┐
                                   │  caddy  │
                                   └────┬────┘
                      ┌─────────────────┼──────────────────┐
                      │        emsim api (Go, :8080)        │
                      │  auth · content · training ·        │
                      │  assessment · reporting · platform  │
                      │  REST/JSON + SSE + статика SPA      │
                      └───────┬──────────────────▲──────────┘
                              │ pgx              │ NOTIFY
                        ┌─────▼──────────────────┴─────┐
                        │      PostgreSQL 16            │
                        │  данные · tasks · audit       │
                        └─────▲────────────────────────-┘
                              │ claim / heartbeat / done
                      ┌───────┴──────────────────────────┐
                      │       emsim worker (Go)          │
                      │  scenario.generate · voice.render │
                      │  assessment.evaluate · stt · …    │
                      └───┬──────────┬──────────┬────────┘
                          │ HTTP     │ HTTP     │ exec
                     ┌────▼───┐ ┌────▼────┐ ┌───▼───┐
                     │llama.cpp│ │whisper  │ │ piper │
                     │ LLM     │ │ STT     │ │ TTS   │
                     └─────────┘ └─────────┘ └───────┘
                          файлы: записи звонков, озвучка → volume /data/blobs
```

Полная схема компонентов и границ — [`diagrams/01-context-components.md`](diagrams/01-context-components.md).

### 4.2 Модули (Go-пакеты внутри `internal/`)

| Модуль | Отвечает | Владеет таблицами | Зависит от |
|---|---|---|---|
| `auth` | пользователи, сессии по cookie, роли, рабочие места, RBAC-middleware | `users`, `sessions`, `workstations` | — |
| `content` | справочник служб и их workflow, классификатор, билеты, сценарии и их неизменяемые версии, озвучка | `services`, `classifier_types`, `tickets`, `scenarios`, `scenario_versions`, `voice_assets` | `platform` (задачи, blobs) |
| `training` | занятие, назначения, прогон обучаемого, карточка, действия, события по таймлайну, звонки, stop, монитор | `lessons`, `assignments`, `runs`, `items`, `actions`, `item_events`, `calls`, `evidence`, `control_reports` | `content` (версии сценариев, только чтение), `platform` |
| `assessment` | рубрика по умолчанию + поправки из эталона кейса (§7.4), детерминированные критерии, LLM-judge, STT, ревизии, рекомендация уровня, LLM-совет «над чем работать», примеры для дообучения | `assessment_inputs`, `assessments`, `trainee_assessment_state`, `recommendations`, `training_examples`, `advice` | `training` (evidence, только чтение), `platform` |
| `reporting` | агрегаты по занятию/группе/обучаемому, графики, экспорт CSV и PDF (обязательно) | `report_files`, представления (views) над `assessments`/`items`/`runs` | `assessment`, `training` (чтение) |
| `platform` | очередь задач (из orchestration-core), SSE-шина, blobs, audit, health/metrics, конфигурация | `tasks`, `blobs`, `audit_log` | — |

Правила: модуль пишет только в свои таблицы; чтение чужих — через Go-интерфейс, объявленный у потребителя; никаких циклов (`training` не знает про `assessment`, `assessment` — про `reporting`).

### 4.3 Процессы и топология

«Процесс» здесь — операционная единица развёртывания: отдельный контейнер в docker compose со своим логом, перезапуском и healthcheck. Модули из §4.2 — это код; процессы — то, где этот код исполняется. Отчёты и досье обучаемого не являются процессом: их считает `emsim api` синхронно SQL-запросами по представлениям (`lesson_report_rows`), а тяжёлый PDF собирает `emsim worker` задачей `report.build`.

| Процесс | Что делает | Экземпляров |
|---|---|---|
| `emsim api` | HTTP-запросы всех модулей (в том числе отчёты и ЛК — чтение из БД), SSE-потоки, планировщик событий сценария (tick 500 мс), раздача статики SPA | 1 во всех профилях первого этапа; несколько API требуют отдельного решения о восстановлении |
| `emsim worker` | claim задач всех kind'ов по приоритету, coordinator зависимостей/советов каждые 2 с, reaper просроченных lease | 1 процесс; отдельные пулы: короткие задачи, LLM, STT. `LLM_CONCURRENCY` выбирается замерами 1/2/4, не числом карточек |
| `postgres` | — | 1 |
| `llm` | `llama-server` с моделью Q4 (T-Lite 2.1 8B, запасной Qwen3-4B), OpenAI-совместимый `/v1/chat/completions` | 1 |
| `stt` | `whisper.cpp server`, модель small/medium, `/inference` | 1 |
| `caddy` | TLS (самоподписанный или свой), `/` → api | 1 |

Piper TTS запускается worker'ом как процесс внутри его контейнера (нет постоянного сервера). Профили compose: `demo` (ноутбук, всё в одном), `class` (сервер УМЦ), `gpu` (тот же compose с `--n-gpu-layers`).

### 4.4 Фронтенд

React + TypeScript + Vite, `TanStack Query` для данных, `EventSource` для SSE, без UI-кита — стили копируют АРМ-112 по скриншотам памятки и инструкции оператора 112 v2.1 (121 снимок реального интерфейса, разбор — [`../docs/reference-ui/README.md`](../docs/reference-ui/README.md)) (ADR-009). Три набора экранов по роли в одном SPA:

- обучаемый: список карточек, карточка + список оповещения + панель телефона, ЛК (история, ошибки, уровень), ознакомительный режим (те же экраны + слой подсказок);
- преподаватель: сценарии (список, редактор, предпросмотр, генерация), занятия (создание, назначение по РМ, монитор, стоп), оценки (просмотр, ревизия), отчёты;
- администратор: пользователи, РМ, импорт, состояние (задачи, health), backup.

Типы API генерируются из `openapi.yaml` (`openapi-typescript`), чтобы фронт и бэк не расходились.

### 4.5 Два типа упражнения: сначала ДДС, затем оператор 112

`exercise_type` отличает `dds_processing` от будущего `operator112_intake`. Это не роль доступа и не `mode`: роли остаются прежними, `intro/training` обозначают ознакомление/тренировку. Тип фиксируется в версии сценария, занятии и прогоне, попадает в evidence и вход оценки. На назначении и старте проверяется совпадение типов сценария и занятия; после старта тип не меняется. Текущие исполняемые контракты разрешают только `dds_processing`; поддержку 112 включит отдельное расширение схем после согласования его процесса.

Общая часть `training` ведёт занятия, очередь карточек, команды/квитанции, журнал, часы и фиксацию evidence. Правила команд, переходов, завершения и содержимое снимка ДДС размещаются в отдельном компоненте `training/dds` за интерфейсом процесса упражнения. Будущий `training/operator112` подключается через ту же границу. Транзакции, авторизация и идемпотентность остаются общими; универсальный конструктор процессов не требуется. Нынешние обязательные поля готовой карточки и цепочка реагирования относятся к контракту ДДС, а не являются обязательными для будущего черновика 112.

У каждого типа своя базовая версионированная рубрика: текущая `rubric.default.json` относится к ДДС, у 112 будет другой набор критериев. Выбор — по `(exercise_type, rubric_version)`; поправки `reference.scoring`, нормировка и сохранение `rubric_effective` остаются общими. Тип учитывается при выборке истории для рекомендаций и агрегатов ошибок: результаты разных упражнений не смешиваются автоматически. Раздельные уровни, конкретные критерии 112 и совместная передача карточки между обучаемыми пока не проектируются. Добавление 112 само по себе не вводит SIP или голосового бота.

## 5. API

Полный контракт — [`contracts/openapi.yaml`](contracts/openapi.yaml). Принципы:

- REST/JSON, префикс `/api/v1`; cookie-сессия; SSE — `GET /api/v1/lessons/{id}/stream` (преподаватель) и `GET /api/v1/my/stream` (обучаемый).
- Каждый ответ — `X-Request-ID`, `Cache-Control: no-store`; ошибки — `{ "error": { "code", "message", "details"? }, "request_id" }` с закрытым списком кодов.
- Команды обучаемого — **один** эндпоинт `POST /api/v1/items/{item_id}/actions` с телом `{command_id, expected_seq, type, payload, client_at}`; ответ — квитанция `{outcome: applied|rejected, replayed, action_id, log_seq, seq, reaction, item_state, server_at, error_code?}` (ADR-004).
- Запись звонка — `PUT /api/v1/items/{item_id}/calls/{call_id}/recording` (multipart, ≤ 10 МБ, webm/opus или wav).
- Долгие операции (генерация, импорт, отчёт) возвращают `202 {task_id}`; статус — `GET /api/v1/tasks/{id}`; готовность приходит и по SSE.

Ключевые группы:

| Группа | Пути | Роль |
|---|---|---|
| auth | `POST /auth/login`, `POST /auth/logout`, `GET /me` | все |
| admin | `/admin/users`, `/admin/workstations`, `/admin/import/{classifier,tickets}`, `/admin/tasks`, `/admin/backup` | admin |
| content | `/services`, `/scenarios`, `/scenarios/{id}`, `/scenarios/{id}/versions`, `/scenarios/{id}/approve`, `/scenarios/generate`, `/scenarios/{id}/regenerate` | instructor |
| lessons | `/lessons`, `/lessons/{id}`, `/lessons/{id}/assignments`, `/lessons/{id}/start`, `/lessons/{id}/stop`, `/lessons/{id}/monitor`, `/lessons/{id}/stream` | instructor |
| trainee | `/my/run`, `/my/items`, `/items/{id}`, `/items/{id}/actions`, `/items/{id}/calls/{call_id}/recording`, `/my/stream`, `/my/results`, `/my/progress` | trainee |
| assessment | `/items/{id}/assessment`, `/items/{id}/assessment/revisions`, `/users/{id}/recommendation` | instructor (+ trainee чтение своего) |
| reports | `/lessons/{id}/report`, `/lessons/{id}/report.csv`, `/groups/progress`, `/users/{id}/progress` | instructor |

## 6. Модель данных

DDL — [`contracts/schema.sql`](contracts/schema.sql); ER — [`diagrams/03-er.md`](diagrams/03-er.md). 28 таблиц и 2 представления, одна схема `public`, имена по модулям в комментариях.

Главные инварианты:

- **Версия сценария неизменяема:** body, digest и difficulty закрепляются при создании версии. Старое прохождение не читает текущую сложность из `scenarios`.
- **Журнал команд append-only:** `command_id` глобально уникален, `request_digest` связывает его с автором, карточкой и телом. `items.seq` — версия состояния для optimistic lock; `log_seq` нумерует все авторизованные попытки под блокировкой карточки, включая отклонённые. Evidence и ссылки оценщика используют `action_id`, порядок — `log_seq`. `actions.effect` (срез 3, ADR-017) хранит серверный факт изменения поля карточки (`set_card_field`) отдельно от клиентского `payload`, участвующего в `request_digest`.
- **Состояние карточки** меняют только доменные транзакции под блокировками занятия и карточки. Планировщик, stop и загрузка записи соблюдают тот же протокол; внешние вызовы под блокировками запрещены.
- **Evidence закрытия неизменяем:** включает журнал до `cutoff_log_seq`, доставленные/отменённые события, манифест ожидаемых записей, effective timing, дедлайны, маркеры interruption и финальное состояние. Поздние отклонённые команды остаются в журнале вне этого снимка.
- **Производные входы оценки тоже фиксируются:** `assessment_inputs` хранит правила, рубрику, точные тексты STT с происхождением и JSON входа judge. До фиксации этого снимка STT находится в защищённом от очистки `tasks.result`; отдельных таблиц правил и транскриптов нет.
- **Одна автооценка на карточку:** `kind=auto, revision=1`; технический retry завершает ту же задачу и не создаёт новую ревизию. Экспертная оценка — ручная правка преподавателя с причиной. Итоговая — последняя экспертная, а при её отсутствии автооценка. Повторный автопересчёт исключён из MVP.
- **Rubric effective фиксируется один раз:** дефолтная рубрика + только поправки `reference.scoring`; результат сохраняется в assessment_inputs и каждой ревизии. Ранее согласованная схема рубрики не заменяется набором самостоятельных рубрик на кейс.
- **Задачи исполняются at-least-once, доменный результат фиксируется один раз:** `dedup_key` защищает постановку; fencing и общая транзакция эффекта + `tasks.done` защищают исполнение (§8). Ожидание зависимостей — `waiting`, не ошибка модели.
- **История не зависит от текущего профиля:** `runs.level_at_start`, `scenario_versions.difficulty`; отчёт берёт длительности из evidence. `users.level` в ЛК — текущий уровень, не уровень прошлых занятий.
- **Рекомендации и советы имеют версию основания:** `trainee_assessment_state.version` по `(user_id, exercise_type)` меняется при новой итоговой оценке или применении уровня; ключ задачи и `basis_version` включают эту версию. Старые результаты не выдаются за актуальные.
- **Отчётность — SQL по доменным таблицам.** Производные артефакты — PDF/CSV и текст совета; отдельного аналитического хранилища нет. Audit каждого эффекта пишется в его транзакции.

## 7. Критические потоки

Диаграммы — [`diagrams/02-sequences.md`](diagrams/02-sequences.md).

### 7.1 Команда обучаемого (горячий путь)

```
Авторизация → проверка принадлежности item пользователю (до любой выдачи receipt)
BEGIN
  lessons FOR SHARE → items FOR UPDATE
  поиск actions по command_id, повторный после получения блокировки
  найдено: сравнить actor_id, item_id, request_digest
    совпало → исходные receipt и HTTP-статус + replayed=true; новых эффектов нет
    не совпало → 409 command_id_conflict, исходную квитанцию не раскрывать
  не найдено: проверить running, закрытие item, expected_seq и workflow
  взять clock_timestamp() после блокировок; log_seq := log_seq+1
  INSERT actions с action_id, log_seq, request_digest и полной квитанцией
    отказ → accepted=false, items.seq не растёт; отказ и audit коммитятся
    успех → items.seq+1, изменение состояния/дедлайнов; планирование по since
  pg_notify('emsim_events', идентификаторы изменённых ресурсов)
COMMIT → HTTP receipt
```

Исходный `outcome=applied|rejected` и HTTP-статус сохраняются и при replay; отдельный флаг `replayed` не маскирует отказ. Повтор успешно применённой команды работает и после stop/close. `request_digest` — sha256 канонического `{actor_id,item_id,type,payload,expected_seq,client_at}`; клиент хранит исходное тело без изменений. Повтор после `stale_seq` с новым намерением получает новый command_id, старую команду автоматически не переписывают.

`server_at` — время решения сервера после получения блокировок (`clock_timestamp()`), а не начало ожидавшей транзакции. Порядок определяется `log_seq`, не часами и не UUID. Evidence хранит `action_id`; ссылки имеют вид `action:<uuid>`.

### 7.2 Таймлайн и часы упражнения

`since` и `status_in` имеют разные функции. При **первом** достижении `since` создаётся событие с `anchor_at` и `due_at = anchor_at + at_s`. `status_in` проверяется при доставке. Например, `since=accepted, at_s=90, status_in=[responding]` планируется в момент принятия, а не через 90 секунд после responding. UNIQUE(item_id,event_key) исключает повторное планирование при возвращении к статусу. Для ДДС ADR-031 добавляет якорь `since=call_ended` + `since_contact`: завершение первого исходящего звонка этому контакту; якоря по статусам остаются для уже утверждённых версий.

Планировщик каждые 500 мс сначала читает кандидатов без row-lock, затем обрабатывает каждого отдельной короткой транзакцией: `lessons FOR SHARE → items FOR UPDATE → item_events FOR UPDATE SKIP LOCKED`. Повторно проверяет due_at, running, открытость и статус; атомарно сохраняет delivered/skipped и NOTIFY. Закрытие сначала отменяет оставшиеся scheduled-события, затем делает evidence. Событие после снимка не доставляется. Если транзакция создаёт следующую карточку, она заранее берёт `runs FOR UPDATE` до блокировок items.

**Сбой сервера (упрощение MVP):** один API-процесс выполняет начальное восстановление до readiness. В транзакции под барьером занятия все незакрытые карточки running-занятий получают идемпотентный маркер `interruptions[{recovery_id,cause:server_restart,detected_at}]`. Никакого heartbeat на lessons, вычисления длительности паузы или сдвига due_at/deadlines нет. Новые команды принимаются после фиксации маркеров; далее их приём не зависит от фонового heartbeat. Все timing-критерии затронутой карточки получают `not_applicable`; числовые интервалы остаются фактическими и в отчёте помечены прерыванием. Такие карточки не входят в рекомендацию уровня. Уже закрытые карточки не меняются. Падение scheduler внутри живого API делает процесс unhealthy и приводит к перезапуску, а не к отдельному запрету команд по таймеру heartbeat.

Просроченные сообщения восстанавливаются в порядке due_at с `late=true`. Если status_in пока не выполнен, событие затронутой восстановлением карточки остаётся scheduled до подходящего статуса либо до close/stop; оно не выбрасывается из-за действий, которых нельзя было выполнить при простое. Задержка вызванных сбоем сообщений не считается ошибкой обучаемого; порядок фактических действий по-прежнему проверяется. Подробный расчёт компенсированных часов исключён из MVP.

**Выдача карточек:** start выдаёт первую назначенную карточку каждого run. Без spawn_every_s очередная выдаётся в транзакции close предыдущей. В hard планировщик выдаёт следующую по `runs.next_offer_at`, независимо от открытых карточек; после выдачи next_offer_at = фактическое offered_at + spawn_every_s. Лимита «две открытые» не вводим. После задержки или рестарта за tick выдаётся не более одной карточки на run, пропущенные интервалы не воспроизводятся пачкой. Close в этом режиме не ускоряет очередь. Порядок блокировок: lessons SHARE → runs UPDATE → items по id; queue_cursor и UNIQUE(run,ordinal) защищают от двойной выдачи. Событие spawn_card использует тот же механизм выдачи, потребляет следующий элемент назначенной очереди только при совпадении стабильной пары `(scenario_key, version)` с этим элементом; UUID версии в body события не хранится. Несовместимый план отклоняется до start. В hard такая выдача переносит next_offer_at на offered_at + интервал. Законченная очередь + отсутствие открытых items завершают run; все finished runs завершают lesson. Intro следует тем же правилам выдачи без оценок.

**Единая timing policy ДДС:** open_s=30, primary_s=30 от offered_at, complete_s=180 от первого primary_at. Политика фиксируется при старте; кейс её не переопределяет. Повтор статуса не перезапускает таймер. Пока решения нет, complete_at=null. Превышение срока фиксируется как ошибка, но карточку не закрывает; close_reason=timeout не используется. Отчёт различает open_seconds, primary_seconds, work_seconds и total_seconds; при interruption это фактические интервалы с явной отметкой «время не оценивается».

### 7.3 Звонок и поздняя запись

Набор → `call_start` → готовая greeting-фраза → MediaRecorder → завершение → ack-фраза → «Кто принял»/«Суть сообщения». Аудиочанки находятся только в памяти вкладки. Перед `call_end` браузер собирает файл в памяти; команда содержит поля отработки и манифест записи `{sha256,size,mime}` либо `recording=null`, если записи нет. Сервер фиксирует ожидаемый hash до закрытия; после call_end этот манифест не меняется.

`PUT recording` передаёт только ранее заявленный файл; сервер сверяет фактический hash/размер/формат. Повтор того же файла возвращает успех; другой файл — `409 recording_conflict`. При закрытии фиксируется `recording_upload_deadline_at = closed_at + recording_grace_s` (по умолчанию 120 с, конфигурация фиксируется на старте). После срока новый файл отклоняется; повтор уже принятого файла остаётся идемпотентным. До закрытия ожидаемая загрузка не просрочена. Загрузка не меняет evidence: в нём уже сохранён манифест ожидаемого файла. Stop не разрешает новый call_end, но разрешает дозагрузить ранее объявленный файл до его срока.

STT запускается только после закрытия карточки и при наличии проверенного файла. `stt.transcribe` сохраняет текст, digest, hash записи, модель и параметры в tasks.result атомарно с done. Done-результат не заменяется. Зависимая задача оценки содержит dependency_task_ids; эти задачи нельзя очищать до фиксации assessment_inputs или отмены оценки. В assessment_inputs копируется сам текст с происхождением, поэтому после фиксации входа история не зависит от хранения очереди. Незагруженное аудио после закрытия вкладки не восстанавливается; после upload deadline отсутствие отражается как missing. Это unavailable для проверки устного доклада, а не доказательство отсутствия звонка. Письменная отработка оценивается независимо. При stop активный звонок без call_end сохраняет лишь факт начала.

### 7.4 Закрытие, оценивание и ручная оценка без автоматики

`set_status` изменяет реакцию, но сам не закрывает карточку. `close` разрешён после not_accepted, refused, completed или completed_without_team, при выполненных обязательных комментариях и без активного звонка. Причина — refused для первых двух статусов, completed для остальных. Иное состояние → transition_not_allowed. После close реакции не меняются; исправления сообщаются через control_report. Evidence включает саму команду close; её серверное время завершает норматив отработки.

**Пилотное исключение (ADR-017, срез 3):** для версии сценария с `reference.pilot_goal=accept_card` (снимок — `items.pilot_goal`) `close` дополнительно разрешён из `accepted`; реакция не меняется, `close_reason=pilot_completed`. Правило не распространяется на сценарии без этого поля и не заменяет обычную семантику `completed`/`refused`. Команда `set_card_field {path,value}` (срез 3, ADR-017) меняет один разрешённый путь карточки (`/card/address/okrug`) в состояниях `received`/`not_accepted`; серверный факт `{path,old,new}` пишется в `actions.effect`, отдельно от `payload`, и копируется в evidence.

```
Close: lessons SHARE → runs UPDATE → items UPDATE
  closed_at; отменить scheduled; evidence/digest и сроки дозагрузки
  training → assessment.evaluate в waiting (attempts=0)
  STT уже загруженных записей; задачи-зависимости привязать к evaluate
  выдать следующую карточку по §7.2; audit + NOTIFY; COMMIT
  intro → без оценки/STT/рекомендаций/советов

Worker dependency coordinator (отдельный короткий цикл, каждые 2 с):
  выбрать waiting; проверить файлы/терминальные состояния STT
  готовы → правила + rubric_effective + тексты STT → assessment_inputs
  assessment_inputs + evaluate.input_id + waiting→pending атомарно
  ошибка подготовки → failed/input_preparation_failed, без фиктивной auto

Assessment.evaluate (LLM-пул):
  claim только с input_id; читать неизменяемый вход
  правила уже в снимке; semantic проверки — вне транзакции
  одна auto rev=1 + task done + audit + NOTIFY в fenced-транзакции
```

Координатор ждёт только зависимости включённых критериев. При JUDGE=off STT для оценки не ставится и не ожидается; llm-критерии получают unavailable, правила считаются всегда. Критерии звонка not_applicable, если звонок не требовался.

Координатор — цикл внутри worker, не отдельный kind/сервис и не LISTEN-подписчик. `tasks.wait_until` — время следующей проверки зависимостей, не крайний срок оценивания. NOTIFY предназначен UI; polling гарантирует работу и без него. Повтор coordinator безопасен под items/tasks locks. Пока зависимости не готовы, attempts не расходуются. Ошибка подготовки терминальна и видна преподавателю; административный retry возвращает такую задачу без input_id в waiting, а задачу с sealed input — в pending. Отдельного assessment.prepare и отдельных предварительных результатов правил нет.

**Ожидание STT:** файл, не объявленный либо не загруженный до upload deadline, даёт missing. Для загруженного файла ждём done/failed/dead_letter задачи STT; ожидание места в очереди не считается отказом распознавания. Таймаут одной попытки STT ограничивает зависший вызов и определяется замерами W0, затем работает ограниченный retry. Автоматического отсечения всей очереди через 180 секунд нет. Длительное ожидание показывается в UI, преподаватель может оценить вручную в любой момент после закрытия. STT до закрытия не переносим.

**Один вход оценки:** assessment_inputs.body содержит evidence_digest, exercise_type, rubric_version/effective, результаты правил, полные транскрипты и их digest/hash/модель/параметры либо причины отсутствия, версии judge-промптов и точный semantic_input. Retry использует тот же body. Текст комментария и отработки не подменяет устный доклад. Отсутствие обязательного заполнения — 0 соответствующего критерия; отсутствие технического источника — unavailable.

**Рубрика:** contracts/rubric.schema.json определяет kind=deterministic|llm, строковую version и устойчивые id критериев. Базовая рубрика своя на exercise_type; reference.scoring содержит только weights/critical/disabled. Сначала исключаются disabled и not_applicable, затем оставшиеся веса нормируются к 100; unavailable не исключается для получения искусственно полного балла. При любом неразрешённом unavailable: needs_review, score=NULL, passed=NULL. Итоговые средние/лидеры и рекомендации используют только ready; незавершённые оценки показаны отдельным количеством. Преподаватель разрешает недоступные критерии и получает ready. Для interruption timing-критерии not_applicable; нормировка остальных явная, отметка interruption сохраняется, рекомендация такую карточку не использует. Новых шкал частичного балла нет.

**Исчерпание попыток:** handler финальной ошибки и reaper используют общий assessment-finalizer. Если input уже есть и expert отсутствует, failed/dead_letter задачи и auto rev=1 needs_review (правила из input, семантика unavailable, score/passed NULL) сохраняются атомарно. Это итог автоматической попытки, не повод автоматически считать заново; retry задачи после появления auto запрещён. Если подготовка входа упала и auto отсутствует, API показывает failed и разрешает ручную оценку по evidence. Сбой LLM не делает карточку недоступной преподавателю.

**Ручная оценка:** base_revision — текущая итоговая ревизия либо 0, если её ещё нет. Номер 1 зарезервирован за auto; первая expert без auto получает revision=2, base_revision=0, input_id=NULL. Если auto есть, expert получает base_revision+1 и может ссылаться на его input. При первой ручной оценке преподаватель заполняет все применимые критерии по rubric_version/scoring/evidence; частичная правка разрешена только при существующей ревизии. reason обязателен. Под блокировкой item проверяется base_revision; stale → 409. В той же транзакции незавершённая evaluate отменяется (cancelled), готовая auto остаётся. Worker перед фиксацией проверяет отмену/отсутствие expert; поздняя auto не появляется. Следующие expert продолжают нумерацию. Итог — последняя expert, иначе auto. Пара ИИ/эксперт сохраняется только если auto действительно существовала. Ручная оценка не требует успешной подготовки входа или работающей модели.

**Рекомендации и совет:** assessment владеет trainee_assessment_state(user_id,exercise_type,version,advice_due_at). Новая итоговая оценка увеличивает version в той же транзакции и ставит задачу детерминированной рекомендации. Основание сохраняет конкретные assessment_id/revision, исторический уровень и тип; только ready без interruption. Применение уровня — application use case, который через порты auth и assessment меняет users.level и версию основания в общей транзакции; прямой записи assessment в users нет. Устаревшие рекомендации отклоняются по basis_version.

Совет не ставится на каждую правку: изменение основания переносит advice_due_at на now+5 с. Цикл worker после периода без новых изменений ставит одну задачу по user_id/exercise_type для текущей версии; версии остаются в dedup_key. Совет относится к агрегатам истории этого типа (advice.lesson_id=NULL), его можно показать в ЛК и отчёте занятия как текущую рекомендацию по обучаемому. Старые queued-задачи проверяют актуальность до LLM и отменяются без вызова модели; перед публикацией версия проверяется снова. Устаревший текст скрывается. Приоритет LLM-очереди: оценка 100, генерация сценариев 50, совет 10; уже выполняющийся вызов не прерывается. На принятом входе совет использует только агрегаты ошибок. SQL-отчёт отражает текущую итоговую ревизию; PDF/CSV сохраняют основание и дату формирования.

### 7.5 Stop и действия после закрытия

`POST stop`: под `lessons FOR UPDATE` записать `state=stopped`, `stopped_at=clock_timestamp()`, epoch+1, `items.stop_cutoff_log_seq = items.log_seq` для незакрытых карточек на барьере, задачу lesson.close, audit и NOTIFY. Повтор stop возвращает то же stopped_at и не меняет epoch. Новые учебные команды после барьера отклоняются; старые command_id возвращают исходные квитанции (§7.1).

`lesson.close` исполняется в коротком пуле, не ожидает свободного LLM-слота. Для training создаёт waiting evaluate; для intro задач оценки нет. Незакрытые items → interrupted; `closed_at=lessons.stopped_at`, а время фактического создания evidence отдельно. Это время, а не задержка worker, участвует в нормативах. Ещё не наступившие к stop события и этапы помечаются прерванными, а не ошибками обучаемого. Evidence содержит причину и cutoff из items.stop_cutoff_log_seq; команды, отклонённые после барьера до прихода worker, остаются только в журнале. Для intro нет автооценки; interrupted не участвует в автоматической рекомендации уровня. Повтор закрытия докрывает оставшиеся карточки без дублирования снимков/задач.

`control_report` — отдельное постфактум-сообщение обучаемого по своей закрытой карточке, допустимо и после завершения занятия. Через тот же командный endpoint оно проходит отдельную ветку до проверки running/закрытости, сохраняется в `control_reports` и actions с уникальным command_id, увеличивает seq/log_seq, но не меняет reaction, closed_at или evidence. Оценка не пересчитывается; преподаватель видит сообщение при ручном разборе. Поздние отклонённые попытки также остаются вне зафиксированного evidence.

### 7.6 Генерация сценария

`POST /scenarios/generate {service, categories, difficulty, count, ticket_ids?}` ставит `count` задач, по одной на сценарий, → `202 {task_ids}`. Worker выбирает типы классификатора, где целевая служба в списке оповещения; промпт с билетом и JSON-схемой сценария; валидирует ответ по схеме и по справочникам (адрес, служба, статусы); пишет `scenarios(status=draft)` + `scenario_versions(version=1, source_task_id)` и `tasks.done` в общей fenced-транзакции; SSE `scenario.ready`. Преподаватель правит через `PUT /scenarios/{id}` (создаёт версию 2 как черновик) или `POST regenerate {comment}`. `POST approve` → версия `approved`, задача `voice.render` → Piper → `voice_assets`.

### 7.7 Переподключение обучаемого

SSE — уведомление об изменении, источник состояния — PostgreSQL. После загрузки/перезапуска/потери LISTEN: сначала открыть поток в режиме буферизации; получить `stream.ready` с cursor `<stream_epoch>:<counter>`; затем перечитать snapshot (`/my/run`, **весь** `/my/items` и открытые карточки, либо monitor); затем применить накопленные инвалидирующие события. Дубликаты безопасны: клиент перечитывает состояние, старый seq не затирает новый. Изменение, попавшее одновременно в snapshot и SSE, не применяется повторно как команда. При переполнении буфера во время snapshot цикл начинается заново.

При reconnect внутри жизни EventSource используется Last-Event-ID. При новой вкладке cursor можно передать через query `cursor` (нативный EventSource не принимает произвольные заголовки); сервер проверяет epoch и наличие cursor в буфере. На неизвестный cursor, смену процесса или восстановление LISTEN всегда отправляется `resync` и выполняется описанная процедура. NOTIFY исполняется **внутри** транзакции доменного изменения, подписка LISTEN открывается до обслуживания браузеров; после разрыва её восстановление обязательно инвалидирует все подписки. Буфер — ускорение, а не durable-журнал доставки.

Клиент до отправки сохраняет в localStorage неизменяемое тело одной неподтверждённой команды на item, с ключом user_id/item_id. Пока нет квитанции, следующая команда этой карточки не отправляется. После восстановления повторяется исходный command_id; stale_seq не меняет старое тело. Квитанция позволяет удалить сохранённую команду; отклонённый пользовательский текст остаётся доступен для копирования. Данные другой учётки UI не восстанавливает. При недоступном localStorage интерфейс сообщает, что восстановление команды после закрытия вкладки не гарантируется. Аудио только в памяти; при живой вкладке можно повторить upload после сетевого обрыва, после закрытия незагруженные байты теряются. Серверное время остаётся источником нормативов; клиентское время не применяется задним числом.

## 8. Consistency и failure semantics

| Ситуация | Поведение |
|---|---|
| Двойная команда, включая повтор после stop/close | После авторизации поиск command_id раньше проверки изменившегося состояния; исходный outcome/HTTP, replayed=true |
| Тот же command_id, другое тело или ресурс | 409 command_id_conflict; чужой receipt не раскрывается |
| Две вкладки | expected_seq; отказ stale_seq сохраняется отдельным action_id/log_seq |
| Обрыв до HTTP-ответа / перезагрузка | Исходная команда в localStorage; replay без повторного эффекта. Незагруженное аудио после закрытия вкладки теряется и отмечается missing |
| Stop vs команда/событие | Общий барьер lessons; эффект либо до stop и в evidence, либо отклонён/отменён после |
| Сбой до commit | Транзакция откатывается; retry безопасен |
| Commit прошёл, процесс упал до публикации | NOTIFY уже входит в commit; при потере слушателя — resync и чтение БД |
| Worker потерял lease во время вызова модели | Результат не фиксируется без совпадения worker/token и действующего lease; старый worker не пишет доменный результат |
| Worker упал при фиксации результата | Доменный эффект, audit, NOTIFY и tasks.done в одной транзакции: всё либо ничего; уникальный source_task_id — дополнительная защита |
| Ожидание записи/STT | waiting до готовности/дедлайна, без расходования attempts и вычислительного слота |
| LLM/STT недоступны | needs_review с NULL-баллом; правила в sealed input; ручная оценка доступна даже без auto/input |
| Перезапуск API | Маркер interruption на открытых карточках, timing not_applicable, overdue события late; дедлайны не сдвигаются |
| Правка сценария/рубрики | Новая версия для новых прохождений; существующие снимки/оценки неизменны |
| Правка преподавателя | Последняя expert становится итоговой; инвалидация рекомендации/совета по новой версии основания |
| Поздняя запись или сообщение в контроль | Только объявленный hash до upload deadline; control_report отдельно от evidence; автоматического пересчёта нет |

Изоляция — READ COMMITTED. Порядок доменных блокировок: `users` (только если меняется профиль) → `trainee_assessment_state` (при изменении основания) → `lessons` → `runs` (если меняется очередь) → `items` (по id) → `item_events/calls` → `tasks`. Claim берёт только tasks и сразу коммитит. Reaper сначала читает кандидатов без locks; для финального отказа оценки вызывает доменный finalizer в том же порядке locks, без предварительного удержания task lock; inference — вне транзакции. Finalize заново берёт необходимые доменные блокировки в указанном порядке, затем tasks FOR UPDATE, проверяет worker/token/lease по clock_timestamp и атомарно пишет результат + done. Перед finalize auto проверяется отсутствие expert; ручная оценка отменяет незавершённую evaluate. Для одной auto дополнительно UNIQUE(item_id) WHERE kind='auto'; для генерации — UNIQUE(source_task_id). Терминальная задача возвращает уже сохранённый result. Административный retry ошибочной задачи сохраняет task id/dedup и монотонный lease_token; увеличивает бюджет попыток, не обнуляет token и не разрешает повтор оценки, уже имеющей auto или expert.

## 9. Security

- Аутентификация: логин + пароль (`argon2id`), cookie `Secure; HttpOnly; SameSite=Strict`, сессия в БД, TTL 12 ч, logout инвалидирует. Без 2FA по решению заказчика (ADR-008).
- Авторизация: три роли; middleware проверяет роль по маршруту, обработчик — принадлежность (обучаемый видит только свои `runs/items`; преподаватель — свои занятия и любые сценарии; администратор не имеет доступа к содержимому занятий и оценкам).
- TLS терминирует caddy (самоподписанный сертификат в пакете; можно подменить).
- Ограничения ввода: JSON ≤ 64 КБ, запись звонка ≤ 10 МБ, rate-limit на `/auth/login` (5/мин на логин).
- Audit: каждый эффект — строка в `audit_log` в той же транзакции; журналы хранятся 6 месяцев (ротация задачей `audit.prune`).
- Логи и метрики никогда не содержат паролей, текстов комментариев, транскриптов, ФИО; только идентификаторы и коды.
- Модели работают в изолированной docker-сети без выхода наружу; `api` — единственный сервис с публикуемым портом (через caddy).
- Персональные данные: ФИО и логин курсантов; билеты обезличены заказчиком.
- Backup БД и blobs — автоматически **не реже одного раза в сутки**, также доступен ручной запуск. Расширенные вопросы backup/restore из ревью отложены.

## 10. Observability

- Логи: `slog` JSON в stdout, поля `process, request_id, user_id?, operation, outcome, code`; уровень по env.
- Метрики Prometheus на admin-порту `:8081/metrics`: HTTP (route, method, class, duration histogram), `sse_connections`, `commands_total{type,outcome}`, `scheduler_events_delivered_total`, `scheduler_lag_seconds`, `tasks{kind,status}` gauge, `task_duration_seconds{kind}`, `llm_request_duration_seconds`, `assessment_queue_wait_seconds`, `assessment_end_to_end_seconds`, `oldest_pending_assessment_seconds`, `assessments_total{status}`.
- `/healthz` — процесс жив; `/readyz` — PostgreSQL доступна, схема нужной версии; модели в readiness не входят (их недоступность — деградация, не отказ).
- Экран администратора «Состояние»: очередь задач по kind/status, dead-letter с кнопкой «повторить», версии моделей, место на диске, последний backup.
- Нагрузочный прогон в CI-профиле `load`: 30 виртуальных обучаемых × карточка с реальными паузами + 1 монитор; отчёт p50/p95 команд и задержки SSE.

## 11. Capacity и план замеров

| Параметр | Предположение / проверка |
|---|---|
| Класс / сервер | 20–30 РМ; 6 CPU-ядер, 32 ГБ, без GPU; 100 клиентов — отдельный прогон |
| Интерактивные команды | Среднее 30 × 1/15 с ≈ 2 rps, синхронный пик 30 rps; цель p95 ≤ 100 мс, приёмочный предел 2 с |
| SSE | Около 32 соединений; состояние восстанавливается snapshot, не только replay |
| Обычная карточка | До 30 с на первичное решение + 180 с на отработку после решения; 210 с — пример максимального цикла, не измеренный средний темп |
| Поток оценок | При 30 обучаемых и цикле 210 с — около 8,6 карточки/мин; hard с выдачей раз в 150 с может дать около 12 карточек/мин |
| Размер БД / файлов | 100 пользователей × 50 карточек × 50 КБ ≈ 250 МБ; записи по 300 КБ ≈ 1,5 ГБ; это оценка объёма, не benchmark |
| LLM / STT / RAM | Скорость, память и полезный параллелизм **не измерены**; устанавливаются W0 на целевом CPU с реальными входами |

**Одна минута на комментарий — только расчётный пример.** Если одна проверка занимает 60 с, то 150 карточек (30 × 5) требуют 150 минут при одном исполнителе или 75 минут при идеальном двукратном ускорении. При 10 с и таком же идеальном ускорении — 12,5 минуты. Это суммарная обработка готового набора, не время ожидания одной карточки и не гарантированная задержка продукта. 5 операторов × 3 карточки — 15 задач, поступающих по мере закрытия, а не требование запускать 15 inference-запросов одновременно. Оценивание предыдущих карточек идёт параллельно дальнейшему занятию.

**Цель — достаточная пропускная способность и приемлемое ожидание, не максимум одновременных запросов.** На одном CPU запросы делят ресурсы. Для каждого уровня параллелизма измеряется фактическая производительность μ; устойчивый поток требует μ выше фактической скорости поступления λ. `LLM_CONCURRENCY` не равен числу обучаемых или размеру очереди.

W0: типичные короткие/длинные комментарии + эталоны; один компактный структурированный ответ; сравнить concurrency 1, 2, 4 по карточкам/мин, p50/p95 задержки и качеству. Отдельно измерить STT и совместную нагрузку. W4: 5×3 и 30×5 карточек с реальными паузами, hard, одновременно живой API и модели; фиксировать время ожидания в очереди и от закрытия до результата. Слот коротких задач (координатор зависимостей, `lesson.close`, рекомендации) резервируется независимо от LLM; CPU-потребление моделей ограничивается по замеру. Все semantic-критерии карточки по возможности объединяются в один запрос. Срок полного отчёта объявляется после измерения; обещания «все оценки к концу занятия» до него нет. UI показывает прогресс готовности, а не ложную фиксированную длительность.

| Альтернатива | Почему нет | ADR |
|---|---|---|
| Микросервисы (training / assessment / content отдельно) | один сервер, одна команда, 3 rps; сеть между сервисами добавляет только точки отказа | 001 |
| Redis/RabbitMQ/Kafka для очереди и pub/sub | дополнительный сервис при достаточной для этого класса PostgreSQL-очереди; PostgreSQL с SKIP LOCKED + NOTIFY закрывает и очередь, и шину; код очереди уже есть | 002 |
| WebSocket вместо SSE | двунаправленность не нужна; SSE — обычный HTTP, авто-reconnect, `Last-Event-ID`, проходит через caddy без настроек | 007 |
| gRPC между api и worker | они не общаются напрямую, только через таблицу `tasks`; браузер gRPC не умеет | 001 |
| LLM в реальном времени (подсказки, диалог) | CPU-сервер, 30 одновременных — не укладываемся; заказчик прямо просил «до и после» | 003 |
| Оценка по живым таблицам вместо snapshot | оценка нестабильна при повторах и правках; snapshot с digest даёт воспроизводимость и защиту от «оценили не то» | 006 |
| Реальный SIP (Asterisk) + WebRTC | заказчик снял; +2 сервиса, +NAT/кодеки, ноль пользы для оценки | 005 |

| Vue/Svelte/Angular | React — самый доступный для команды; UI-кит не нужен, копируем АРМ-112 | 009 |
| Хранить записи звонков в PostgreSQL (bytea) | раздувает БД и backup; файлы + `blobs` с sha256 проще | 002 |
| Zitadel/Keycloak для auth | 3 роли и логин/пароль; внешний IdP — лишний сервис и лишняя настройка в классе | 008 |
| Прямой перенос `runs/run_items` из core | другая семантика (пассивный item vs живой человек), FK-граф мешает | 010 |

## 13. Rollout

Вертикальные срезы первого этапа — ДДС; режим 112 следует после него (ADR-015). Бэкенд идёт впереди, но первый сквозной сценарий «поступление → решение → звонок → закрытие → оценка» проверяется на простом рабочем фронтенде в W2–W3; полная визуальная проработка АРМ-112 завершается после основного бэкенда, до приёмки W4.

| Неделя | Срез | Выход |
|---|---|---|
| W0 | Скелет: репозиторий, `emsim migrate/api/worker`, очередь из core с тестами, auth, compose `demo`, SPA-заглушка, CI | логин работает; задача `noop` проходит очередь; замер качества и throughput LLM/STT, concurrency 1/2/4 на целевом CPU → выбор модели и лимитов |
| W1 | Контент: импорт классификатора и билетов, справочник служб, ручной сценарий, генерация LLM, утверждение, озвучка | преподаватель получает утверждённый сценарий с голосом |
| W2 | Карточка: занятие, назначение по РМ, старт, список карточек, карточка АРМ-112, команды, события, телефон, stop, монитор | 3 обучаемых одновременно проходят карточку; монитор показывает |
| W3 | Оценка и отчёты: evidence, рубрика + поправки кейса, детерминированные критерии, STT, LLM-judge, ревизии, ЛК, отчёт (таблицы, графики, CSV, PDF), LLM-совет, рекомендация, ознакомительный режим | полный цикл UC2–UC12 |
| W4 | Приёмка: нагрузочный прогон 5×3, 30×5 и 100 клиентов при работающих моделях; failure-проверки ADR-014/016, offline-пакет, инструкция установки, демо-видео ≤ 5 мин, презентация | сдача |

Feature flags не нужны — поставка одноразовая. Миграции только вперёд (goose up); откат — восстановление из backup. Данные для демо — синтетические сценарии + 96 билетов.

## 14. Открытые вопросы и граница этой правки

1. Приоритетные службы и конкретные исключения workflow 103/104 — подтвердить по памятке.
2. Модель и полезный CPU-параллелизм — по замерам §11, включая качество комментариев.
3. Голоса Piper или готовые записи — по качеству на слух.

Оператор 112 входит в общий объём следующим этапом после ДДС; сейчас закреплены только точки расширения и отдельная рубрика (ADR-015). Подробности приёма обращения и необходимость совместного занятия 112 → ДДС обсудить отдельно. PDF обязателен. В ADR-014 перечислены принятые исправления предыдущего ревью. Расширенная математика частичных оценок (кроме согласованного NULL для needs_review), развитие дублей и дополнительный список замечаний по security/экспортам/backup из ревью этой правкой не проектируются. Существующие интерфейсы этих функций не означают завершённую реализацию. Backup выполняется не реже раза в сутки.
