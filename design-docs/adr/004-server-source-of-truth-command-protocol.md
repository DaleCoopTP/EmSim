# ADR-004. Сервер — источник правды; идемпотентный командный протокол

Статус: accepted · 2026-09-17 · уточнён ADR-016 от 2026-09-18

## Контекст
Нормативы и оценка зависят от серверного времени и порядка действий. Ответ может потеряться, вкладка закрыться, преподаватель — остановить занятие до повторного запроса.

## Решение
- Команды: POST /items/{id}/actions {command_id,expected_seq,type,payload,client_at}. До отправки неизменяемое тело сохраняется в localStorage. Одновременно — не более одной неподтверждённой команды на item.
- После авторизации и принадлежности: lessons FOR SHARE → items FOR UPDATE → поиск command_id. Исходная квитанция возвращается **до** проверки running/closed; повторно сверяется request_digest с actor_id/item_id/телом.
- Replay сохраняет outcome=applied|rejected, HTTP-статус и server_at; признак replayed=true отдельный. Другое тело под тем же id — 409 command_id_conflict без выдачи чужого receipt.
- Новая команда проверяет expected_seq, состояние и workflow. Все авторизованные структурно корректные попытки коммитятся в actions, включая отказ; items.seq растёт только при applied. log_seq растёт для каждой попытки под блокировкой item.
- server_at=clock_timestamp() берётся после блокировок. Порядок — log_seq; ссылки в оценках — action:<action_id>. Stop фиксирует items.stop_cutoff_log_seq под барьером занятия; evidence использует соответствующий cutoff_log_seq; поздние действия его не меняют.
- Эффект + actions + audit + pg_notify — одна транзакция, внешних вызовов внутри нет.
- control_report по закрытой карточке имеет отдельную ветку, допустим после stop, не меняет evidence и не запускает оценку заново.
- Timing фиксируется при старте: 30 с от offered_at на открытие/первичное решение и 180 с от первого primary_at на отработку. Повтор статуса не сбрасывает срок; после server_restart timing-критерии затронутых карточек not_applicable без сдвига сроков.

## Варианты
- Клиентское время для нормативов — недоверенное; только справочно.
- Последний писатель выигрывает — две вкладки молча портят состояние; отвергнуто.
- Проверять running до replay — потерянный успешный ответ превращается в отказ после stop; отвергнуто.

## Последствия
Клиент хранит одну неподтверждённую команду на item в localStorage; аудио — только в памяти вкладки, незагруженные байты после её закрытия могут потеряться. Это транспортное восстановление; доменное состояние остаётся серверным. После stale_seq клиент перечитывает состояние; новое намерение имеет новый command_id, старое не переписывается автоматически.
