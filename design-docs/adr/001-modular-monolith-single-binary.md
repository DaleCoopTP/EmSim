# ADR-001. Модульный монолит на Go, один бинарник с ролями

Статус: accepted · 2026-09-17

## Контекст
Один сервер без GPU, 20–30 РМ, ~3 запроса/с, одна команда разработки на 4 недели. ТЗ говорит о «сервисах», «масштабировании», «отказоустойчивости узлов»; заказчик на Q&A — «в классе 20–30 должно работать», «сложная модель с кучей параметров — плохо».

## Решение
Один Go-модуль `emsim`, один бинарник с подкомандами `api | worker | migrate | import`. Модули (`auth, content, training, assessment, reporting, platform`) — Go-пакеты с явными интерфейсами, каждый владеет своими таблицами. Между модулями — вызовы функций, не сеть. `api` и `worker` — один образ, разные команды запуска.

## Варианты
- **Микросервисы** по модулям — сеть между сервисами при 3 rps добавляет только точки отказа и время; отвергнуто.
- **Python (FastAPI)** — модели всё равно отдельные HTTP-сервисы; Go даёт статический бинарник, горутины под SSE, и уже написанную очередь; отвергнуто.
- **Монолит без модульных границ** — быстрее на первой неделе, дороже на третьей; отвергнуто.

## Последствия
- Развёртывание — 6 контейнеров, из них наших 2 (api, worker).
- Горизонтальное масштабирование остаётся возможным (api stateless, worker'ов несколько) и описано как профиль, но не реализуется.
- Дисциплина границ держится только код-ревью и `go vet`-правилом на импорты (`internal/<module>` не импортирует соседа напрямую, только через интерфейсы потребителя).
