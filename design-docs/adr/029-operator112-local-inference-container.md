# ADR-029. Локальная модель в составе compose, ИИ-заявитель и судья по умолчанию

Статус: accepted · 2026-09-27 · дополняет ADR-025 и ADR-028 (значения по умолчанию, движок), этап 2 `slice-112-5b-plan.md`

## Контекст

ADR-025 (ИИ-заявитель, `caller.reply`) и ADR-028 (судья описания,
`DESCRIPTION_CONTENT`) подключили модель через OpenAI-совместимый
`internal/platform/llm`, но оставили её явным опт-ином:
`CALLER_REPLIER=stub` и `ASSESSMENT_JUDGE=off` по умолчанию. Сама модель в
поставку не входила. При разработке это Ollama на хосте
(`host.docker.internal:11434`), контейнер `llama-server` с GGUF был
отложен на этап 2 112-5b вместе с замером W0.

В результате `docker compose up` на сервере класса даёт заглушку из шести
фраз вместо заявителя и рубрику v2 без судьи. Автономной поставки с ИИ нет,
хотя RFC-001 §4.3 и ТЗ требуют офлайн-контур с локальной моделью.
Пользователь 27.09.2026 решил выполнить этап 2 так, как он задумывался:
модель — отдельный контейнер в compose, ИИ включён по умолчанию. Выбор
движка оставлен разработчику.

## Решение

- **Движок — `llama-server` (llama.cpp).** Скорость генерации на CPU у
  Ollama и `llama-server` одинакова (Ollama запускает тот же llama.cpp).
  Решают управляемость и наблюдаемость под десятки одновременных диалогов
  на 6 CPU без GPU:
  - `--parallel N` задаёт число слотов, запросы в слотах пакетируются в
    один проход декодера (continuous batching);
  - кеш префикса на слот (промпт `aicaller` уже упорядочен под него,
    `slice-112-5b-plan.md`, решение 4);
  - `--metrics` отдаёт Prometheus-метрики (`requests_processing`,
    `requests_deferred`, tokens/s), они нужны замеру W0;
  - модель не выгружается при простое (у Ollama `keep_alive` по
    умолчанию 5 минут, после чего первый запрос даёт холодный старт);
  - поставка — один GGUF-файл и образ без реестра моделей.

  Код адаптеров не меняется: оба движка отдают `/v1/chat/completions`.
  Ollama на хосте остаётся вариантом для разработки.
- **Сервис `llm` в `compose.yaml`.** Образ
  `ghcr.io/ggml-org/llama.cpp:server-<сборка>`, закреплённый по digest.
  Веса монтируются только для чтения из `./models`. Порт наружу не
  публикуется, контейнер подключён только к внутренней сети compose без
  выхода наружу (RFC-001 §9). `worker` ждёт `service_healthy` у `llm`.
- **Одна модель на заявителя и судью.** Оба обращаются к `llm` с одним
  алиасом модели (по умолчанию `t-tech/T-lite-it-2.1:q5_K_M`, та же строка,
  что в Ollama при разработке, поэтому `generation.model` в evidence
  одинаков в обоих окружениях). Слоты общие: `CALLER_CONCURRENCY` +
  `LLM_CONCURRENCY` не превышают `LLM_PARALLEL`, иначе лишние запросы
  ждут в очереди сервера. По умолчанию 3 + 1 = 4 слота.
- **По умолчанию `llm`.** В конфигурации процессов (`config.Worker`,
  `config.API`) пустые `CALLER_REPLIER` и `ASSESSMENT_JUDGE` означают
  `llm`. Без адреса и имени модели процесс не стартует с сообщением о том,
  какую переменную задать, а не переходит молча на заглушку. Заглушка
  (`stub`/`off`) остаётся только явной настройкой: автотесты, CI,
  разработка без модели.
- **`compose.no-llm.yaml`.** Переопределение, которое выключает сервис
  `llm`. Используется либо вместе с `CALLER_REPLIER=stub
  ASSESSMENT_JUDGE=off` (e2e, CI), либо с адресами Ollama на хосте
  (разработка на Mac).
- **Веса не в git.** `models/` исключён из git и из контекста сборки
  образа. `make model` скачивает GGUF и проверяет закреплённый sha256 (при
  подготовке офлайн-пакета на машине с интернетом). Второй источник —
  копия blob-а из локального Ollama: имя blob-а и есть его sha256, поэтому
  совпадение доказывает, что в классе стоят те же веса, на которых
  проверялось качество.
- **Детерминированность судьи.** `llm.Request.Temperature` отправляется
  всегда, в том числе ноль. Раньше `omitempty` выбрасывал
  `temperature: 0`, и сервер подставлял своё значение по умолчанию (0.8 у
  обоих движков), хотя в `assessment_inputs.judge` записан 0.
- **Рассуждения модели.** Сервер запускается с `--reasoning-budget 0`. На
  стороне клиента `llm.StripThinking` удаляет и закрытый
  `<think>…</think>`, и незакрытый `<think>…` до конца текста (обрыв
  генерации), и рассуждение до одиночного `</think>`.
- **Таймаут ответа заявителя.** `CALLER_REPLY_TIMEOUT` по умолчанию 30 с
  вместо 15 с: 15 с подбирались на Mac с GPU, а генерация 8B-модели на CPU
  медленнее. Окончательное значение задаёт замер W0.
- **Прогрев кэша промпта (`CALLER_WARMUP`, по умолчанию включён,
  27.09.2026).** Первый ответ модели в диалоге разбирает весь промпт с
  нуля (правила роли и персонаж — сотни токенов), поэтому он заметно
  медленнее последующих. Вступление заявителя приходит без модели, и в
  той же транзакции worker ставит техническую задачу `caller.warmup`
  (пул `caller`, приоритет ниже `caller.reply`, одна попытка). Она
  отправляет модели `aicaller.WarmupMessages` — системное сообщение и
  историю в точности как у следующего ответа — с `max_tokens: 1` и
  выбрасывает результат. Задача не меняет item, evidence и журнал и
  всегда завершается `done` (в `result` — прогрета ли модель). Если
  оператор уже отправил следующий вопрос, прогрев пропускается, чтобы не
  конкурировать с настоящим ответом. Ускоряется только разбор промпта,
  генерация ответа — нет. Потоковый показ ответа по словам отложен до
  конца MVP (решение пользователя).
- **Замер W0 — `emsim bench-llm`.** Подкоманда воспроизводит реальную
  нагрузку: многоходовые диалоги по ИИ-сидам через тот же
  `aicaller.Replier` и, опционально, параллельные запросы судьи через
  `descjudge.Handler`. Отчёт по каждому уровню параллелизма: p50/p95/p99
  задержки (и отдельно — первого ответа модели в диалоге), доля ответов
  дольше таймаута, ошибки, скорость генерации и очередь сервера из
  `/metrics`. Прогрев воспроизводится так же, как в worker, по
  `CALLER_WARMUP`.

## Варианты

- **Ollama в контейнере.** Отвергнуто: нет слотов с явным контекстом и
  Prometheus-метрик, модель выгружается при простое, поставка через
  реестр моделей Ollama, а не один файл.
- **Оставить `stub`/`off` по умолчанию и включать ИИ переменными.**
  Отвергнуто пользователем: поставка для класса должна работать с ИИ без
  ручной настройки; режим без модели — исключение для тестов.
- **Отдельные контейнеры для заявителя и судьи.** Отвергнуто: две копии
  весов в памяти и два конкурента за одни и те же 6 ядер. Разделение
  трафика задаётся размерами пулов worker, а не отдельными серверами.

## Последствия

- ADR-003 не меняется: модель по-прежнему вызывает только worker, и только
  в двух случаях, разрешённых ADR-025 и ADR-028.
- ADR-025 («`CALLER_REPLIER=stub` по умолчанию») и ADR-028 («судья
  выключен по умолчанию») в части значений по умолчанию заменены этим
  ADR. Всё остальное в них, включая резервную реплику при сбое модели и
  `needs_review` при недоступном судье, без изменений.
- `docker compose up` без скачанной модели не поднимает `worker`:
  контейнер `llm` не проходит проверку здоровья. Это намеренно: отсутствие
  модели видно при установке, а не во время занятия. Без модели систему
  запускают с `compose.no-llm.yaml`.
- Новые занятия 112 при стандартной поставке закрепляют
  `operator112/rubric-v3`. Уже созданные занятия сохраняют свою рубрику.
- Память (дополнение 27.09.2026). Переупаковка весов llama.cpp
  (`CPU_REPACK`, по умолчанию включена) держит копию весов (~4,7 ГБ) в
  анонимной памяти, кеш контекста при `--ctx-size 16384` — ещё ~2,4 ГБ;
  RSS `llama-server` около 7,2 ГБ. Сервер класса (32 ГБ) это вмещает,
  поэтому умолчания не меняются. На машине разработчика с ~8 ГБ у Docker VM
  ядро VM убивает процесс при загрузке; там задаются `LLM_REPACK=false`
  (`LLAMA_ARG_REPACK`), `LLM_PARALLEL=1`, `LLM_CTX_SIZE=4096` — контекст
  на диалог прежний, анонимной памяти ~0,7 ГБ. Влияние выключения
  переупаковки на скорость на целевом x86-64 не замерялось; если
  понадобится, это решает замер `bench-llm`.
- Ёмкость класса этим ADR не заявляется. `LLM_PARALLEL`,
  `CALLER_CONCURRENCY`, `CALLER_REPLY_TIMEOUT` и решение «весь класс /
  часть РМ» принимаются по результатам `bench-llm` на целевом сервере
  (`slice-112-5b-plan.md`, этап 2). Двадцать одновременных генераций
  8B-модели на 6 CPU могут не уложиться в приемлемую задержку; замер
  должен показать это до занятия.
