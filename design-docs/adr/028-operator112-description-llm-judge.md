# ADR-028. Оператор 112: LLM-судья описания заявителя (`operator112/rubric-v3`)

Статус: accepted · 2026-09-26 · уточняет ADR-026 §«LLM-критерии — будущая v3» и порядок `slice-planning-112.md` §3

## Контекст

ADR-026 (112-6, детерминированный этап) оставил блок `DESCRIPTION_PRESENT`
заглушкой «поле `complaint` непустое = 10 баллов» и явно отложил
качественную проверку описания на `operator112/rubric-v3`, после этапа 2
112-5b (замер W0, `llama-server`/GGUF в compose). Пользователь передал
готовый прототип оценщика (`handoff/claude_evaluator_112_20260926.zip`):
модель отвечает `yes`/`no`/`needs_review` на положительно сформулированные
контрольные вопросы по тексту описания, получая **только** сам текст и
вопросы — без транскрипта разговора, без эталона, без весов. Локальный
прогон на 22 сценариях/132 описаниях (`t-tech/T-lite-it-2.1:q5_K_M` через
Ollama) дал 94,8% совпадений с подготовленной разметкой; два расхождения —
ошибка JSON без сохранённого сырого ответа.

Решением пользователя от 26.09.2026 срез начинается **до** этапа 2 112-5b
(замер W0 остаётся отдельной задачей, как и в ADR-026): 112-5b уже
подключило `internal/platform/llm` и один разрешённый вызов модели на
интерактивном пути (`caller.reply`, ADR-025); этот ADR подключает **второй**
разрешённый вызов — `assessment.evaluate`, всегда после закрытия карточки,
никогда на интерактивном пути. ADR-003 не меняется.

## Решения пользователя (26.09.2026)

1. 10 баллов блока делятся **поровну** между вопросами сценария.
2. Любой вопрос с ответом `needs_review` (или отсутствие ответа модели)
   переводит весь блок в `unavailable` → вся оценка карточки —
   `needs_review`, `score=NULL`; итог выставляет преподаватель.
3. У сценария нет вопросов к описанию → обычный `0` по правилу ADR-026
   «эталон отсутствует» (не `not_applicable`, не отдельный статус); модель
   не вызывается.
4. Вопросы добавляются только трём уже существующим ИИ-сидам
   (`pilot-112-ai-car-in-water-01`, `-mobile-shop-01`, `-toyota-fire-01`).
   Расширение библиотеки остальными 19 сценариями прототипа — отдельная,
   не входящая в этот срез задача.
5. Правка преподавателя — баллами за весь критерий (существующая форма
   `ItemReview.tsx`), без правки по отдельным вопросам.
6. Новое занятие/предпросмотр закрепляют `rubric-v3` только когда судья
   включён конфигурацией (`ASSESSMENT_JUDGE=llm`); иначе — `rubric-v2`
   без изменений.
7. Живая проверка на локальной Ollama — в рамках этой же работы, сервер
   останавливается после проверки.

## Решение

### Рубрика `operator112/rubric-v3`

Новый файл `rubric.operator112.v3.json`: девять критериев `rubric-v2`
без изменений (id/веса/params) плюс один заменяющий `DESCRIPTION_PRESENT`:

| id | вес | kind | что |
|---|---|---|---|
| `DESCRIPTION_CONTENT` | 10 | `llm` | вопросы к `complaint` (эталон — `intake112.reference.description_questions`), модель отвечает `yes/no/needs_review` |

`rubric.operator112.json` (`operator112/rubric-v2`) не переименовывается и
не меняется — уже идущие/старые занятия на нём читаются как раньше
(ADR-013's freeze). Обе версии остаются в `contracts.Files`;
`operator112RubricCriterionIDs` (`internal/content/rubric.go`) — теперь
объединение id всех трёх файлов (v1/v2/v3), чтобы сценарий с
`scoring.disabled: ["DESCRIPTION_PRESENT"]` (v2) и сценарий, ссылающийся
на `DESCRIPTION_CONTENT` (v3), одинаково проходили валидацию независимо
от того, на какой рубрике их фактически оценят.

### Выбор версии — по конфигурации, не «текущий файл»

`content.RubricVersionFor(operator112_intake)` не меняется (продолжает
возвращать `operator112/rubric-v2` — консервативное значение по
умолчанию). Новая функция `content.Operator112RubricVersion(judgeEnabled
bool)`: `false` → делегирует в `RubricVersionFor` (v2, без изменений);
`true` → версия `rubric.operator112.v3.json`. `training.Service` и
`training.Service.StartPreview` вызывают именно её, с флагом из
конфигурации процесса (`ASSESSMENT_JUDGE`), а не из «какая рубрика
сейчас последняя». `ASSESSMENT_JUDGE` присутствует **в конфигурации api и
worker одинаково** (default `off`): api решает, какую версию заморозить
в новом занятии; worker решает, может ли он на самом деле ответить на
судейский запрос. Рассинхронизация (api думает, что судья включён, а
worker — нет, или наоборот) не приводит к нулю ученику: `DESCRIPTION_
CONTENT` в этом случае получает `unavailable` с объясняющим текстом
(«судья не настроен» на стороне рубрики v2, либо реальная ошибка вызова
на стороне worker), и весь блок уходит на ручную проверку — то же
правило §2 выше, без специального кода на рассинхронизацию.

### Поток оценки: модель вызывается вне транзакции, один раз за попытку задачи

`assessment.evaluate` остаётся одной задачей одного пула `llm` — новый
пул/новая задача (по образцу `caller.reply`, ADR-024/025) не заводится:
и подготовка входа (`sealInputForItem`, coordinator), и запись `auto rev=1`
(`recordAutoTx`) остаются на своих местах. Меняется только `Handle`:

1. Coordinator (без изменений в транзакционной модели) вызывает
   `evaluator.Evaluate(evidence, body, effective, semantic=nil)` —
   `RuleEvaluator.Evaluate` получает четвёртый параметр
   (`SemanticAnswers`, отсутствующий на этом шаге, судья ещё не звал).
   Если оператор112-оценщик реализует новый необязательный интерфейс
   `SemanticPreparer` **и** судья сконфигурирован
   (`Service.judge != nil`), он дополнительно готовит
   `assessment_inputs.semantic_input["DESCRIPTION_CONTENT"]`
   (`{description, questions:[{id,question}]}`) и `judge.model`/
   `judge.prompt_versions["DESCRIPTION_CONTENT"]="description-questions-v1"`.
   Пустое описание или отсутствие вопросов — обычный путь без судьи;
   `PrepareSemantic` в этом случае просто не добавляет запись, и
   `Evaluate`'s собственное правило «эталон отсутствует»/«описание
   пусто» отрабатывает как раньше, без единого обращения к модели.
2. `Handle` (пул `llm`, вызывается воркером на каждую попытку задачи):
   читает уже запечатанный вход (`InputByID`, отдельная короткая
   транзакция только на чтение — как `PeekPayload` уже делает для
   технической части задачи); если `semantic_input` непусто — вызывает
   зарегистрированного по `prompt_version` `SemanticJudge`
   **вне какой-либо транзакции** (тот же принцип ADR-003/025), с
   ограничением по времени (`JUDGE_TIMEOUT`, аналог
   `CALLER_REPLY_TIMEOUT`). Сбой сети/HTTP/JSON/схемы/`finish_reason=
   length` → `tasks.NewHandlerFailure(Retryable, "judge_unavailable")`
   — те же ограниченные повторы задачи (`MaxAttempts: 3`, уже
   зарегистрированные для `assessment.evaluate`), без выделенного
   fallback-текста (в отличие от `caller.reply` — тут нет реплики,
   которую нужно показать обучаемому; исчерпание попыток просто оставляет
   критерий `unavailable`).
3. Полученные ответы модели передаются **в памяти того же вызова**
   в `recordAutoTx`/`computeAndInsertAuto`, которые запускают
   `Evaluate` второй раз — теперь с реальными ответами — и пишут
   единственную `auto rev=1`. Ответы судьи не сохраняются как отдельный
   долговечный артефакт: `assessment_inputs` остаётся запечатанным один
   раз при подготовке (ADR-006, тот же digest что и раньше, поле
   `semantic_input` содержит только запрос, не ответ); ответ живёт ровно
   один такт обработки задачи и уходит в `assessments.criteria` того же
   коммита. Повторный вызов модели возможен только если сам коммит не
   прошёл (redis-редкий случай сбоя БД между вызовом модели и записью) —
   в отличие от детерминированных правил, `Evaluate` не обязан
   воспроизводить byte-identical ответ модели между отдельными вызовами
   этой не-детерминированной части (тот же принцип, что уже принят для
   `caller.reply`).
4. Исчерпание попыток задачи (`FinalizeExpired`) вызывает
   `computeAndInsertAuto` без каких-либо ответов судьи — `DESCRIPTION_
   CONTENT` получает `unavailable`, вся оценка `needs_review`, ученику
   ноль не ставится (RFC-001 §7.4, без изменений).

Никакой новой durable-таблицы/поля не заводится: судейский ответ — это
входные данные для одного вызова `Evaluate` внутри уже существующей
транзакции записи `auto`, не отдельный шаг конвейера с собственным
состоянием ожидания.

### Подсчёт `DESCRIPTION_CONTENT`

- Нет `description_questions` в эталоне → `not_met`, `score=0`,
  `explanation="эталон не задан"` (то же правило ADR-026, модель не
  вызывается).
- Есть вопросы, но `complaint` не заполнен (`state != known`) → `not_met`,
  `score=0`, все вопросы `no` без вызова модели (то же правило, что уже
  действует у прототипа для пустого описания).
- Есть вопросы и текст → судья вызывается один раз (все вопросы в одном
  запросе, прототип); `details[]` — по вопросу, `points = 10/n`,
  `max_points = 10/n`; доля `yes` от общего числа вопросов → `met`
  (все `yes`) / `partial` / `not_met` (все `no`); **любой** `needs_review`
  или отсутствие ответа модели на конкретный вопрос → у критерия статус
  `unavailable`, `score=nil` (решение №2 выше) — доля `yes`/`no` в этом
  случае не считается, поскольку итог всё равно уходит на ручную
  проверку.
- Вопросы — часть закрытого эталона; `assessment.StripExpected` уже
  чистит `Expected` из `Details` для обучаемого — здесь текст вопроса
  идёт в `Label`, а не `Expected`, поэтому дополнительно скрывается сам
  вопрос от обучаемого через существующий механизм видимости эталона
  (`intake112.reference` целиком недоступен trainee API — без изменений).

### Модель и протокол вызова

Промпт и правило разбора ответа перенесены из прототипа **дословно**
(система: «Ты проверяешь поле «Описание со слов очевидца» …», формат —
JSON-объект `{id: yes|no|needs_review}`); версия — `description-questions
-v1`. Структурированный ответ запрашивается через новое поле
`llm.Request.ResponseFormat` (JSON Schema с `enum` по id вопросов и
`additionalProperties: false`) — тот же параметр, который понимают и
Ollama (`/v1/chat/completions`, `format`/`response_format`), и
`llama-server`; `temperature=0`, `max_tokens` — по умолчанию 1024
(прототип), настраивается `JUDGE_MAX_TOKENS`. Обрезанный ответ
(`finish_reason=length`) — ошибка вызова (`judge_unavailable`), не
частичный результат: прототип уже поднимает это как исключение, не
подменяет ответ на `no`. Логи никогда не содержат текст описания,
вопросов или ответа модели (RFC-001 §9) — только коды ошибок.

### Границы

Судья получает только `{description, questions}` — без транскрипта,
эталона, весов и баллов; баллы считает бэкенд (`ApplyJudge`, не модель) —
то же требование, что и в прототипе. Расширение той же инфраструктуры на
`CALLER_TOPICS` (оценка содержательности свободного разговора) не входит
в этот ADR — это следующий отдельный критерий будущей версии рубрики,
если понадобится.

## Варианты

- Отдельная задача/пул для судьи (по образцу `caller.reply`) — отвергнут:
  единственный вызов на попытку задачи `assessment.evaluate`, без
  промежуточного ожидания между «спросить» и «оценить», не даёт
  преимуществ второй задачи (нет реплики, которую нужно показать сразу
  после ответа) и удваивает число мест, которые нужно мониторить/
  восстанавливать после сбоя.
- Сохранять ответ судьи как отдельное поле `assessment_inputs` (по
  аналогии с транскриптами STT) — отвергнут: `assessment_inputs`
  запечатывается один раз (ADR-006) и не предназначен для двухфазной
  записи; поскольку модель вызывается и результат коммитится в одном
  такте задачи, отдельного durable-шага между «запрос» и «ответ» не
  требуется.
- Отдельный статус для «эталон описания ещё не заполнен» — отвергнут по
  той же причине, что и в ADR-026: это обычный `0` через ту же бизнес-
  логику.

## Последствия

- `internal/assessment`: `RuleEvaluator.Evaluate` получает четвёртый
  параметр (`SemanticAnswers`); новые необязательные интерфейсы
  `SemanticPreparer`/`SemanticJudge`/`SemanticJudgeRegistry`; `Service`
  получает `judge *JudgeConfig` (nil в api-процессе — судья зовётся
  только воркером); `Handle` разбит на вызов модели вне транзакции и
  запись внутри неё.
- `internal/assessment/operator112`: реализует `SemanticPreparer`;
  новый подпакет `descjudge` — промпт, схема ответа, разбор, адаптер
  `SemanticJudge` поверх `internal/platform/llm`.
- `internal/platform/llm`: `Request.ResponseFormat`.
- `internal/platform/config`: `ASSESSMENT_JUDGE` (api и worker),
  `JUDGE_LLM_URL`/`JUDGE_LLM_MODEL`/`JUDGE_TIMEOUT`/`JUDGE_MAX_TOKENS`
  (worker).
- `internal/content`: `Intake112Reference.DescriptionQuestions`.
- `internal/reporting`: `DESCRIPTION_CONTENT` — та же колонка отчёта, что
  `DESCRIPTION_PRESENT` (общая метка «Описание со слов заявителя»).
- Три сида (`pilot-112-ai-{car-in-water,mobile-shop,toyota-fire}-01`)
  получают версию 2 с вопросами из прототипа; остальные сценарии не
  меняются.
- Коммит-план реализации — `slice-112-6-llm-plan.md`.
