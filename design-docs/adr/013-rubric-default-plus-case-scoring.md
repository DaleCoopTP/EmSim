# ADR-013. Рубрика по умолчанию + поправки в эталоне кейса; два оценщика

Статус: accepted · 2026-09-17 · уточняет ADR-006; обновлён ADR-015/016

## Контекст
Цена одной и той же ошибки зависит от кейса: опечатка в улице при затоплении без пострадавших — мелочь, при ДТП с пострадавшими — критическая ошибка. Где-то комментарий обязателен и его содержание надо проверять LLM, где-то комментария быть не должно. Одновременно отчёт прогресса и рекомендация уровня сравнивают баллы разных кейсов — нужна общая шкала. Полная своя рубрика на каждый кейс даёт гибкость, но требует генерировать/заполнять веса для каждого из ~100 кейсов и ломает сопоставимость.

## Решение
Два слоя:
1. **Рубрика по умолчанию** — одна на тип упражнения, версионируется (`dds/rubric-v1`): критерии с `kind` (`deterministic` | `llm`), весом, признаком критичности, порогом зачёта и `critical_cap`. По ADR-015 текущая рубрика относится к `dds_processing`; для `operator112_intake` будет отдельная рубрика. Выбор — по `(exercise_type, rubric_version)`.
2. **`reference.scoring` в эталоне кейса** — необязательный блок *только с отличиями*: `weights` (переопределение), `critical` (что критично в этом кейсе), `disabled` (что не применяется). Пустой блок = дефолт.

Контракт — `contracts/rubric.schema.json`; поле kind выбирает компонент, rule/prompt определяет проверку. Письменная отработка проверяется отдельно от устного доклада; адрес сравнивается по нормализованным компонентам (улица/дом/корпус/квартира), неоднозначное извлечение → unavailable, общей строковой похожести недостаточно.

Оценщик один раз считает `rubric_effective = merge(default, scoring)`, нормирует веса после disabled/not_applicable к 100; unavailable не исключается для получения полного балла и сохраняет `rubric_effective` в ревизии оценки.

В коде два оценщика за интерфейсами: `DeterministicEvaluator` (правила) и `SemanticJudge` (LLM). Диспетчер критериев выбирает по `kind`. `JUDGE=off` переводит llm-критерии в `unavailable` → `needs_review`, score=NULL, passed=NULL. Кейс не ссылается на LLM/промпты — только на идентификаторы критериев.

Наличие/отсутствие комментария — детерминированный критерий (`D_COMMENT_REQUIRED` по `reference.primary_decision.comment_required`); содержание — llm-критерий (`D_COMMENT_CONTENT` по `comment_must_mention`), автоматически `not_applicable`, если `must_mention` пуст.

## Варианты
- Одна жёсткая рубрика без поправок — не отражает разную цену ошибок; отвергнуто.
- Полная рубрика на каждый кейс — генерация весов LLM непредсказуема, преподаватель не объяснит балл, шкала несопоставима; отвергнуто.
- Рубрика на уровень сложности — строгость лучше выражать сложностью сценария и таймингом занятия; отвергнуто.

## Последствия
- Схема сценария получает блок `scoring`; генератор обязан выставлять `critical: [G_ADDRESS]` при пострадавших/угрозе (правило в промпте), преподаватель видит и правит при утверждении.
- `assessments.rubric_effective` — воспроизводимость балла независимо от последующих правок дефолта.
- Функция слияния — ~15 строк; тесты: пустой scoring = дефолт, нормировка после `disabled`, критичность из кейса.
