# ADR-031. ДДС: связь с бригадой, входящие звонки, роли контактов

Статус: accepted · 2026-09-28 · дополняет ADR-030 и RFC-001 §7.2 (якоря событий); не меняет режим оператора 112

## Контекст

Срез ДДС-1 (ADR-030) дал цикл статусов реагирования через «карандаш». Статусы хода работ по памятке ДДС (стр. 22, 26) ставятся «по факту получения информации» от бригады. На момент ДДС-1 эта информация была устроена по-пилотному:

- События `notice` якорились на **статусы самого обучаемого** (`since: accepted`). Бригада «выезжала» через 20 с после «Принята», даже если диспетчер ей не звонил.
- `phone_incoming` был в схеме сценария, но доставлялся так же, как `notice`. Входящего звонка не было.
- У контакта не было роли. Бригаду, отдел контроля 112 и заявителя нельзя было различить ни в интерфейсе, ни в оценке. Ключ `control_112` к тому же не проходит `^[a-z_]{2,32}$`.
- Обязательный звонок (`reference.call`) засчитывался по любому завершённому звонку контакту. Входящий звонок бригады засчитался бы как «диспетчер позвонил».

Памятка (стр. 26–28, 31–33):
- отдел контроля 112 звонит диспетчеру при нарушениях: нет статуса, неправомерный отказ;
- диспетчер сам звонит в отдел контроля, чтобы что-то уточнить;
- нарушение №7 — «не отвечают на звонки».

## Решение

1. **Якорь «после звонка контакту».** Новое значение `event.since = "call_ended"` с обязательным `event.since_contact = <contact.key>`.
   - Момент якоря — завершение первого **исходящего** звонка этому контакту (серверное время команды `call_end`).
   - Повторный звонок якорь не сдвигает: `UNIQUE(item_id, event_key)` и правило «первое достижение» из RFC-001 §7.2.
   - Если бригаде не позвонили, доклады не приходят. В evidence такие события остаются незапланированными, штраф назначает рубрика ДДС-3.
   - Якоря по статусам (`accepted`, `responding`, …) остаются допустимыми и работают для уже утверждённых версий. Новые сценарии ДДС их не используют: доклады привязаны ко времени происшествия, а не к действиям обучаемого.
2. **Роль контакта.** Необязательное `contact.role ∈ {crew, control_112, applicant, other}`, по умолчанию `other`.
   - Ключ контакта остаётся произвольным (`control`, `crew_leader`).
   - Роль не секретна и отдаётся обучаемому для группировки контактов.
   - Тексты подготовленных фраз `greeting`/`ack` тоже отдаются обучаемому: они не эталон. Интерфейс показывает текст, если WAV нет.
3. **Входящий звонок** (`delivery = phone_incoming`).
   - После доставки событие **звонит** `dds.IncomingRingS = 30` с. Состояние «звонит / пропущен» вычисляется из серверного времени, фоновых переходов нет.
   - `answer_incoming {event_key}` — тот же тип команды, что у 112, со своим телом для `dds_processing`. Команда создаёт строку `calls` с `direction = incoming` и `event_key`. На одно событие — не больше одного звонка.
   - Ответ после окончания звонка отклоняется новым кодом `call_missed`.
   - Ответить можно только на открытой карточке и без активного разговора (`call_in_progress`).
   - Завершается звонок обычным `call_end`. Для входящего `accepted_by`/`summary` могут быть пустыми строками (поля в теле остаются; общая необязательность — ДДС-3), запись разговора не ведётся: манифест отклоняется.
   - Пока звонок не принят, обучаемый видит только «кто звонит». Текст события (реплика звонящего) открывается после ответа. Пропущенный звонок текст не раскрывает.
   - Непринятый звонок не мешает сохранить финальный статус. Активный разговор мешает, как в ADR-030.
4. **Обязательный звонок** (`CallPolicy`/`reference.call`, критерии `C_CALL*` рубрики `dds/rubric-v1`) засчитывается только исходящим звонком. Evidence без `direction` читается как `outgoing`.
5. **Эталон реакции на доклад.** `event.expects.comment_facts: string[]` — факты, которые должны попасть в комментарий к статусу, поставленному в ответ на событие.
   - Поле не проецируется обучаемому: `expects` не проецируется целиком.
   - Оценивает его ИИ-судья среза ДДС-4. В ДДС-2 есть только схема и проверка импорта.
6. **Монитор преподавателя.** Для доставленных `notice`/`phone_incoming` активных карточек монитор показывает:
   - время доставки;
   - время ответа (для входящего);
   - время первой реакции — первого применённого `set_status` после доставки, а для входящего — после ответа.

   Эталон `expects` здесь не используется: монитор показывает фактическую задержку, а её оценка — дело рубрики.

`calls` получает столбцы `direction text NOT NULL DEFAULT 'outgoing'` и `event_key text` с частичным уникальным индексом `(item_id, event_key)`. Evidence `calls[]` получает необязательные `direction`/`event_key`. Схема evidence остаётся `emsim/evidence/v1`, старые снимки валидны.

## Отложено

- Баллы: `T_PROGRESS` (реакция на доклад не позже `expects.within_s`), `S_SEQUENCE` по докладам, `C_CALLS` (бригада, отдел контроля, пропущенные входящие) — ДДС-3.
- Оценка `comment_facts` — ДДС-4.
- Озвучка текста событий (TTS), повторный звонок после пропуска, очередь входящих — вне ДДС-2.

## Последствия

- Доклады бригады и входящие звонки отдела контроля становятся частью упражнения. Статусы хода работ проверяемы относительно фактических докладов.
- Пилотные сценарии и версии v1 работают по-прежнему. Новые версии сценариев (`-v2`) используют `call_ended`.
- Рабочее место ДДС с финальными статусами получает панель «Связь с бригадой» вместо списка «Сообщения». Старые карточки сохраняют прежний экран.
