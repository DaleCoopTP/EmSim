# ADR-023. Оповещение служб «Сохранить → оповестить и сохранить карточку»

Статус: accepted · 2026-09-24 · дополняет ADR-021

## Контекст

ADR-021 зафиксировал первый разговорный маршрут 112: `dispatch_intake`
отправляет карточку одной вручную выбранной службе, повтор команды не создаёт
вторую отправку. Срез 112-3 добавил параллельный маршрут `card_only`, который
заканчивается `review_service_selection` → `complete_profile_case` и вовсе не
отправляет карточку. Ни один из двух маршрутов не совпадает с инструкцией
оператора 112: по ней список служб для оповещения формируется автоматически
по типу происшествия, оператор может его дополнить, а «Сохранить» открывает
окно «Список оповещаемых служб» (Рис. 45), где одно действие «оповестить и
сохранить карточку» (либо «вернуться к заполнению») оповещает весь список
разом. Отдельного выбора адресата и отдельной отправки/снимка на каждую
службу в инструкции нет.

Срез 112-4 объединяет разговор (112-2) и профильные карты (112-3) в одном
кейсе; двум разным финалам («одна служба» и «список без оповещения») предстояло
бы либо разойтись ещё сильнее, либо один из них пришлось бы подгонять под
другой без основания в референсе.

## Решение

- Финал 112 для новых прохождений — единая команда `notify_services
  {services[], reason}`. Она доступна после сохранённого черновика,
  оповещает весь переданный список служб одним действием и необратимо
  закрывает черновик для правок. Одна неизменяемая запись на карточку
  (`intake_notifications`) содержит итоговый список, отметку
  предложенных/добавленных вручную служб, причину отклонения от
  предложенного списка (если она была), один снимок карточки и время.
  Отдельных снимков на каждую службу нет — инструкция не разделяет
  отправку по адресатам.
- `dispatch_intake` (одна служба, снимок в `intake_dispatches`) сохраняется
  только для уже одобренных версий `incoming_call` с ровно одной
  `recipient_services`. Он не расширяется на новые кейсы и не описывает
  оповещение по инструкции.
- Новый режим сценария `full_case` объединяет разговор и профильные карты в
  одном кейсе и использует `notify_services`; существующий `card_only`
  переходит на тот же финал для новых прохождений, уже начатые `card_only`
  без флага довершаются прежним маршрутом.
- Повторное сохранение карточки и повторное оповещение служб после первого
  `notify_services` инструкцией не описаны. До уточнения заказчика карточка
  после оповещения закрыта для правок; это ограничение зафиксировано как
  открытый вопрос, а не как постоянное архитектурное решение.

## Последствия

`dispatch_intake` и `intake_dispatches` остаются только историческим путём
для старых `incoming_call`; они не удаляются и не переинтерпретируются.
Evidence 112 получает второе, взаимоисключающее с `dispatch` поле
`notification`; ни один существующий снимок не меняется. Критерии оценки 112
(срез 112-6), которые ссылаются на «что было отправлено», должны читать оба
поля evidence в зависимости от того, каким маршрутом прошла карточка.
