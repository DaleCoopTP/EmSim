# ADR-007. SSE для уведомлений с восстановлением snapshot

Статус: accepted · 2026-09-17 · уточнён ADR-014 от 2026-09-18

## Контекст
Нужны обновления карточек, событий, оценок и монитора. Источник состояния — PostgreSQL; уведомление может пропасть при перезапуске процесса/слушателя.

## Решение
- Потоки /my/stream и /lessons/{id}/stream. Heartbeat 15 с; Caddy flush_interval -1.
- pg_notify с идентификаторами ресурсов пишется в транзакции эффекта; LISTEN открывается до обслуживания браузеров. Потеря LISTEN инвалидирует текущие потоки даже если HTTP-соединение не разорвалось.
- Cursor = <stream_epoch>:<counter>; epoch меняется при рестарте/восстановлении LISTEN. Буфер последних 1000 событий — оптимизация. Неизвестный cursor/epoch/переполнение → resync, а не молчаливое продолжение.
- Начальное соединение: открыть поток, получить stream.ready и буферизовать; перечитать snapshot (включая весь my/items на hard); применить накопленные инвалидирования с повторным чтением актуального состояния. Старый seq не затирает новый; дубликаты не повторяют команду. Переполнение во время snapshot повторяет цикл.
- EventSource передаёт Last-Event-ID при собственном reconnect; новая вкладка передаёт сохранённый cursor query-параметром, поскольку произвольного заголовка у нативного конструктора нет. При наличии заголовка он имеет приоритет.
- Resync не является HTTP 204: это SSE-событие, запускающее повторную синхронизацию.

## Варианты
- WebSocket — обратный канал закрывают POST-команды, не требуется.
- Считать память/NOTIFY durable-журналом — нельзя гарантировать восстановление после потери слушателя; отвергнуто.

## Последствия
API может восстановить UI без долговечного SSE-журнала. Кольцевой буфер и идентификаторы не обещают exactly-once доставки; доменные эффекты защищены командами. По ADR-016 первый этап имеет один API; несколько API требуют отдельного протокола recovery. Смена stream epoch приводит к resync.
