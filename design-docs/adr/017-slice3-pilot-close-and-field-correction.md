# ADR-017. Срез 3: пилотное завершение по `pilot_goal` и исправление поля карточки

Статус: accepted · 2026-09-20 · уточняет ADR-004/011/015 для двух пилотных сценариев slice-2-plan.md; не меняет общие правила завершения ДДС; с 2026-09-27 действует только для служб без `workflow.terminal` (ADR-030)

## Контекст

Первый сквозной прогон (slice-planning.md §4) реализуется на двух уже загруженных пилотных сценариях (`pilot-tree-01`, `pilot-tree-02`, ADR из slice-2-plan.md §3). Их workflow (`seed/services.json`) — только `added→received→{accepted|not_accepted}`, `not_accepted→accepted`, без дальнейшей цепочки бригады. `accepted` не входит в список статусов, после которых ADR-011/RFC §7.4 разрешают `close` (`not_accepted|refused|completed|completed_without_team`). Обоим пилотам нужен способ явно завершить упражнение после `accepted`, не вводя вымышленный `completed` и не меняя общее правило для будущих неупрощённых сценариев. Второй пилот дополнительно требует от обучаемого исправить `card.address.okrug` до принятия — сейчас нет команды, которая меняет поле карточки.

## Решение

**Пилотное закрытие.** Если `scenario_versions.body.reference.pilot_goal = "accept_card"`, `close` дополнительно разрешён из `reaction=accepted`. `reaction` при этом не меняется (остаётся `accepted`); `items.close_reason = 'pilot_completed'` — отдельное значение, не `completed`. `pilot_completed` не означает, что обучаемый прошёл карточку правильно: неисправленный `ЮАР` в пилоте 2 всё равно позволяет закрыть, ошибка остаётся видна в evidence и разрешается вручную в срезе 6. Для сценариев без `pilot_goal=accept_card` правила close не меняются: `accepted` по-прежнему не терминальный статус для завершения.

`pilot_goal` фиксируется на `items` при старте (`items.pilot_goal`) как снимок значения версии сценария на момент выдачи карточки — так же, как `timing_effective` и `workflow`; последующая правка сценария не может задним числом изменить правило закрытия уже выданной карточки.

**Исправление поля карточки.** Новая команда `set_card_field` с телом `{path, value}`:
- `path` — ровно `"/card/address/okrug"` (JSON Pointer из `reference.field_corrections[].path`); любой другой путь — `invalid_payload`. Это описание одного конкретного разрешённого действия, а не API произвольного JSON Patch; расширение на другие пути — отдельное решение при появлении сценариев, которым это нужно.
- `value` — непустая строка после `strings.TrimSpace`.
- Разрешена, когда `item.reaction ∈ {received, not_accepted}` (карточка открыта, первичное решение ещё не принято или отклонено и может быть пересмотрено); после `accepted` — `transition_not_allowed`.
- Правильность значения не проверяется и не сравнивается с `reference.field_corrections[].expected_value` — эталон остаётся скрытым от обучаемого и от команды; обучаемый может исправить на неверное значение или не исправлять вовсе, и всё равно дойти до `accepted`/`close`.
- Эффект — серверный факт `{path, old, new}`, записывается в `actions.effect` (новая колонка), отдельно от `payload` (клиентское тело команды, входящее в `request_digest` для идемпотентности). Evidence копирует `effect` при сборке действия и обновлённое поле — в `final_card`.
- После применения `items.card.address.okrug` меняется, и вместе с ним пересобирается зависимая отображаемая строка `card.address.text` тем же способом, каким её строит `seed/scenarios/*.json` (`"Россия, Москва, (<округ>, <район>), <улица>, <дом>, к. <корпус>, под. <подъезд>"`), чтобы UI не показывал рассинхронизированные округ и итоговую строку.

**Режимы.** `intro` и `training` оба принимаются занятием в срезе 3. Оба сохраняют журнал действий и evidence при закрытии. Ни один не ставит задачу оценки и не может изменить `users.level` — оценка появляется в срезе 6, а intro по RFC §7.4 никогда не получает автооценку. Различие двух режимов в UI (слой подсказок) откладывается до среза 8.

## Отложено

- Общий процесс ДДС (согласование с организатором) и полноценный workflow с цепочкой бригады, статусами `responding/arrived/working`, звонком — не входят в объём. `set_card_field` не становится общим механизмом произвольных исправлений; следующие сценарии могут потребовать нового явного решения.
- События сценария, звонки, `control_report`, stop, SSE, восстановление после рестарта сервера, несколько назначений на одно занятие — следующие срезы (4–5).
- `Assignment.user_id` становится обязательным полем контракта в этом срезе (slice-planning.md §4: «вариант "кто залогинится на РМ" в MVP не поддерживается»); `NULL` как «любой, кто войдёт на РМ» — не реализуется здесь и требует отдельного решения, если понадобится позже.

## Последствия

Пилотные допущения из slice-2-plan.md (сокращённая цель, разрешённое исправление одного поля) получают явное серверное правило и место в evidence, не подменяя обычную семантику `close`/`accepted` для будущих полных сценариев ДДС. `pilot_goal`/`set_card_field` являются точечным, документированным расширением, а не прецедентом для произвольного редактирования карточки обучаемым.
