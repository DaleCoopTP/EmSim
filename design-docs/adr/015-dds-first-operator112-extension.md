# ADR-015. Сначала ДДС, затем оператор 112: минимальные точки расширения

Статус: accepted · 2026-09-18 · уточняет область действия ADR-013/014

## Контекст
Общий объём снова включает два тренажёра. Сначала реализуется ДДС. Сейчас согласована только подготовка архитектуры к следующему этапу; процесс оператора 112 и его подробные требования будут обсуждаться отдельно. У оператора 112 будет другая рубрика.

## Решение
- Сохранить модульный монолит и общие механизмы занятий, команд, очереди, evidence, оценивания и отчётности.
- Ввести `exercise_type` в версии сценариев, занятия, прогоны и снимки оценки. Первый этап поддерживает только `dds_processing`; `operator112_intake` — имя будущего типа, пока не доступного для запуска. Не смешивать тип с ролями доступа и `intro/training`.
- Изолировать правила ДДС в `training/dds`: команды, статусы, завершение, специфические поля evidence. Общий исполнитель отвечает за транзакции, авторизацию, квитанции и журнал. Следующий процесс подключается отдельным компонентом, без универсального движка workflow.
- Выбирать базовую рубрику по типу упражнения и версии. Для 112 — самостоятельный набор критериев; механизм поправок кейса и фиксации итоговой рубрики сохраняется. Агрегаты ошибок и основания рекомендаций фильтровать по типу.
- Проверять совместимость типов при назначении/старте; фиксировать тип при старте. Схемы готовой карточки ДДС не навязывать будущему черновику 112. Его команды и состояние будут отдельным вариантом контрактов.

## Граница
Сейчас не разрабатываются диалог, телефония, критерии 112, раздельные уровни профиля или совместное занятие с передачей карточки между обучаемыми. Текущие CHECK/const допускают только ДДС; следующий этап расширит их миграцией и новыми вариантами JSON/API. Это осознанная точка расширения, а не готовая поддержка 112. Формулировка ADR-014 об исключении 112 из объёма заменена этим решением; остальные принятые исправления сохраняются.

## Порядок реализации
Сначала ДДС. Бэкенд может опережать фронтенд, но ранний сквозной сценарий проверяется через простой рабочий интерфейс. Полная визуальная проработка выполняется после основного бэкенда и до приёмки; срок и план реализации 112 определяются отдельно.
