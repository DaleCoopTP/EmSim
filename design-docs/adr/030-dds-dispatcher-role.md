# ADR-030. Роль диспетчера ДДС: цикл статусов реагирования, закрытие финальным статусом

Статус: accepted · 2026-09-27 · уточняет ADR-011 и ADR-017 по разъяснениям заказчика; не меняет режим оператора 112

## Контекст

Заказчик в чате хакатона 27.09.2026 уточнил роль диспетчера ДДС. Уточнение совпадает с памяткой «Работа на АРМ-112. Памятка для дежурно-диспетчерских служб» (ОКР Службы 112, 2025; стр. 21–32):

- ДДС — промежуточное звено между оператором 112 и реагирующей бригадой. Гормост, Мосводоканал, ДДС района, диспетчерская скорой помощи — всё это ДДС.
- Диспетчер ДДС **не редактирует** карточку 112 и не контролирует правильность её заполнения: это задача оператора 112 и отдела контроля 112. Если диспетчер видит неточность, он звонит в отдел контроля 112, и карточку там дополняют.
- Работа диспетчера в АРМ-112 — **статусы реагирования своей службы с комментариями**. Их ставят через «карандаш» в блоке оповещения службы. Выбор последовательный:
  - сначала «Принята» / «Не принята»;
  - после «Принята» — «Начало реагирования», «Прибытие», «Проведение работ», «Работы завершены», «Отказ от выполнения работ»;
  - из «Не принята» можно перейти только в «Принята».

  «Статусы меняются автоматически» у заказчика означает две вещи: выпадающий список сам предлагает следующие статусы, а статус *карточки* вычисляется системой. Статусы реагирования система сама не ставит.
- Комментарий пишется к статусу. Для «Не принята» и «Отказ от выполнения работ» он обязателен: в нём указывают причину и куда передана информация. Сохранение «Работы завершены» или «Отказ от выполнения работ» закрывает карточку для редактирования. Служба 103 вместо «Не принята» и «Отказ» ставит «Работы завершены: завершение работ без бригады».
- С бригадой и с заявителем диспетчер связывается по телефону или другим каналам, минуя 112.

Реализация срезов 3–7 держалась на пилотных допущениях ADR-017:
- workflow `received→accepted|not_accepted` без цепочки бригады;
- `close` из `accepted` по `pilot_goal`;
- исправление `card.address.okrug` командой `set_card_field`.

Правка карточки противоречит уточнению. Отсутствие цикла статусов не даёт тренировать основной навык.

## Решение

**Режим финальных статусов.** Поведение ДДС выбирается по снимку workflow службы на карточке (`items.workflow`), а не по эталону сценария.

Если `workflow.terminal` непуст (новые службы ДДС):
- `set_status` в статус из `terminal` сразу закрывает карточку в той же транзакции, с теми же последствиями, что и `close`: evidence, отмена запланированных событий, выдача следующей карточки, постановка оценки. Причина закрытия: `refused` для `refused`, `completed` для `completed` и `completed_without_team`.
- Если идёт звонок или не завершён обязательный звонок, переход в финальный статус отклоняется так же, как `close`.
- Команды `close`, `add_comment`, `set_card_field` отклоняются как `transition_not_allowed`: закрывает финальный статус, комментарий входит в `set_status`, карточку ДДС не правит.

Если `workflow.terminal` пуст (пилотные службы срезов 2–7), всё работает как раньше, включая ADR-017. Уже выданные карточки и их evidence не меняются.

Признак берётся из снимка workflow, поэтому обучаемый может его видеть. Клиент получает `Item.terminal_statuses`, а эталонных полей (`pilot_goal`, `field_corrections`) по-прежнему не видит.

**Службы.** Workflow существующего кода службы не меняется: `ImportServices` отклоняет переопределение. Поэтому заводятся новые коды со схемой из памятки:
- `dds_district_chertanovo` — ДДС района: `comment_required = [not_accepted, refused]`, `terminal = [completed, refused]`.
- `dds_ambulance_03` — диспетчерская скорой (03): нет `not_accepted` и `refused`, вместо них `completed_without_team`; `comment_required = [completed_without_team]`, `terminal = [completed, completed_without_team]`.

После «Принята» доступны все статусы хода работ. Пропуск этапа не запрещается правилами, он фиксируется оценкой: в памятке это нарушение №6, а не блокировка интерфейса. Импорт служб проверяет workflow: у финального статуса нет исходящих переходов, финальные статусы достижимы из `received`.

**Статус карточки.** Для ДДС сервер вычисляет `card_status` по памятке, стр. 27–28 (чистая функция, не хранится):

| `card_status` | Условие |
|---|---|
| `registered` | Первичного статуса ещё нет, срок не истёк |
| `not_notified` | Нет «Принята» / «Не принята», а норматив первичного статуса истёк |
| `in_progress` | Принята, идут работы |
| `refused` | `not_accepted` или `refused` |
| `completed` | `completed` или `completed_without_team` |
| `not_completed` | Карточка прервана (stop) без завершения |

Статус «Не завершено» (48 часов без «Работы завершены») в сжатом времени тренажёра означает «прервана без завершения». «Отработана» и «Проверена» относятся к стороне 112 и не моделируются.

**Архивирование подготовленных сценариев.** Файл сценария получает необязательный флаг `archived`. Импорт ставит по нему `scenarios.status = archived | approved` идемпотентно в обе стороны, тела и версии не меняет. Каталог без явного фильтра статуса архивные сценарии не показывает. Архивация миграцией не подходит: на чистой базе сид выполняется после миграций. Пилоты срезов 2–7 архивируются. Их прошлые прогоны, оценки и отчёты читаются как раньше. Назначение через API проверяет статус версии, а не каталожный статус сценария, поэтому здесь ничего не меняется.

## Отложено

- Доклады бригады в отдельной панели, входящие звонки, контакты «отдел контроля 112» и «заявитель», эталон реакции на доклад (`expects`, `comment_facts`) — срез ДДС-2.
- Рубрика ДДС v2 без `D_FIELD_CORRECTIONS` и отработки звонка (`C_CALL_LOG*`), ИИ-судья комментариев и грамотности — срезы ДДС-3 и ДДС-4. До них новые карточки оцениваются рубрикой `dds/rubric-v1`, где неприменимые критерии получают `not_applicable`.
- Необязательность `accepted_by` / `summary` в `call_end` — срез ДДС-3.

## Последствия

- Основной навык ДДС (своевременные и корректные статусы с комментариями) становится выполнимым и проверяемым. Пилотные допущения ADR-017 остаются только для старых служб и не служат прецедентом редактирования карточки обучаемым.
- UI обучаемого ДДС показывает блок своей службы с «карандашом». Кнопки «Принять», «Не принять», «Добавить комментарий», «Завершить упражнение» и форма округа остаются только для карточек старых служб.
- Порядок срезов 8–12 из `slice-planning.md` для ДДС заменяется `slice-planning-dds.md`.
