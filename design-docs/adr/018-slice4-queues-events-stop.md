# ADR-018. Очереди, события, stop и монитор среза 4

Статус: accepted · 2026-09-20

## Решение

- Назначение — это упорядоченная непустая очередь `scenario_version_ids` для одной пары РМ и обучаемого. Одна версия может состоять в очередях любого числа участников; один пользователь и одно РМ уникальны только внутри занятия.
- `start` атомарно создаёт run и первую карточку каждой очереди. В обычном уровне следующая карточка выдаётся при close текущей; в `hard` — планировщиком по `next_offer_at`. После задержки один tick выдаёт не больше одной карточки на run.
- Событие `spawn_card` не хранит случайный UUID. Для `kind=scenario` оно содержит `{scenario_key, version}`; на import/start эта пара разрешается в утверждённую совместимую версию. Событие может потребить только следующий элемент назначенной очереди. Для `duplicate` следующим элементом должна быть та же версия; `variation` добавляется к описанию экземпляра новой карточки.
- Для однозначной очереди допускается не более одного `spawn_card` в версии. Его целевая версия обязана совпасть со следующим элементом очереди, иначе start отклоняется. Это исключает карточки вне конфигурации преподавателя и недетерминированный расход очереди.
- Монитор возвращает `active_items[]`, а не один `current_item`: hard не скрывает параллельно открытые карточки. Presence — best-effort память единственного API-процесса.
- Stop под барьером lessons сохраняет `stopped_at`, `stop_reason`, новый epoch и cutoff всех незакрытых items, затем атомарно ставит `lesson.close`. Повторный stop ничего не меняет. Worker фиксирует interrupted evidence по cutoff; его фактическая задержка не влияет на `closed_at`.
- При запуске одного API до readiness все открытые items running-занятий получают общий idempotent marker `server_restart`; сроки не сдвигаются. Просроченные события после recovery доставляются с `late=true`.
- SSE — invalidation поверх PostgreSQL. `NOTIFY` содержит только идентификаторы, stream имеет epoch/cursor, буфер 1000 сообщений, heartbeat 15 с и `resync` при неизвестном cursor, переполнении или восстановлении LISTEN.
- `control_report` выполняется после close через общий endpoint: создаёт action и отдельную строку, увеличивает seq/log_seq, но никогда не меняет evidence.

## Границы

`phone_incoming` в срезе 4 показывается как событие; телефония остаётся срезом 5. `lesson.close` пока не ставит assessment-задачи: assessment начинается в срезе 6.
