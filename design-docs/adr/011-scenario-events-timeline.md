# ADR-011. Таймлайн и выдача карточек

Статус: accepted · уточнён ADR-016 от 2026-09-18

## Решение
- Первое достижение since фиксирует anchor_at; due_at=anchor_at+at_s. status_in — фильтр доставки, не точка запуска. UNIQUE(item,event_key) исключает повторное планирование.
- Scheduler внутри одного API, tick 500 мс. Порядок locks: lessons SHARE → runs UPDATE при выдаче → items UPDATE → events. Эффект/NOTIFY атомарны; close отменяет scheduled до evidence; stop использует общий барьер.
- После перезапуска до readiness все открытые карточки running-занятий получают interruption с recovery_id. Нет runtime heartbeat, clock_pauses, расчёта длины паузы и сдвига сроков. Timing этих карточек not_applicable, в рекомендацию они не входят.
- Overdue сообщения идут по due_at с late=true; если status_in пока не подходит на затронутой сбоем карточке, ждём подходящего статуса или close/stop, не теряем сообщение из-за простоя. Серверная задержка не является ошибкой обучаемого.
- Start выдаёт первую карточку. Без spawn_every_s следующая выдаётся в close. Hard выдаёт по runs.next_offer_at; после выдачи новый срок = фактическое offered_at + interval. За tick максимум одна выдача на run, без воспроизведения пропущенных интервалов пачкой. Лимита двух открытых нет.
- spawn_card потребляет следующий совместимый сценарий назначенной очереди через тот же механизм и в hard сдвигает next_offer_at. Совместимость проверяется до start. queue_cursor и UNIQUE(run,ordinal) защищены run lock.
- set_status не закрывает карточку. close разрешён после not_accepted/refused/completed/completed_without_team при обязательных комментариях и без активного звонка; reason refused/completed соответственно. Превышение норматива не закрывает; timeout отсутствует.

## Последствия
Сложность восстановления ограничена маркером interruption. Оценка порядка действий сохраняется; неопределённые тайминги не оцениваются. Изменение видимо в UI/отчёте. Конкретные workflows 103/104 должны соответствовать памятке. Отдельный алгоритм дублей не добавляется.
