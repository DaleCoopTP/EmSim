# ADR-026. Оператор 112: детерминированная рубрика v2 (срез 112-6, этап 1)

Статус: accepted · 2026-09-25 · уточняет ADR-013/019 для `operator112_intake`; RFC-001 §7.4

## Контекст

Срез 112-6 начинается по решению пользователя до завершения этапа 2
среза 112-5b (замер W0 остаётся отдельной, более поздней задачей).
Пользователь согласовал 100-балльную рубрику из пяти блоков и четырёх
штрафов, полностью детерминированную — LLM-критерии (полнота описания,
содержательность свободного разговора) откладываются на v3, после
этапа 2 112-5b.

Сейчас код не поддерживает эту рубрику вообще:

- `training.Service.enqueueEvaluateWaiting` безусловно пропускает
  `operator112_intake` — закрытие 112-карточки не ставит
  `assessment.evaluate`;
- `lessons.rubric_version` для новых 112-занятий зашит как
  `operator112/rubric-v1` — ручная рубрика из 112-1 (три критерия
  `manual`);
- `assessment.Service.sealInputForItem`/`recordAutoTx` читают evidence
  через `EvidenceReader.EvidenceByItem`, типизированный на
  `training.EvidenceBody` (форма ДДС) — для 112 он сегодня отдаёт
  только identity-поля (item/run/lesson/trainee id, версия сценария,
  digest, exercise_type), остальное — нулевые значения;
- `assessment.Registry` (`cmd/emsim/assessment_composition.go`)
  регистрирует только `internal/assessment/dds`;
- `intake112.reference` (`scenario.schema.json`) сегодня почти пуст:
  `expected_card`/`expected_types`/`expected_services`/
  `case_description`, без структурированных полей адреса за пределами
  city/street/house/building/landmark и без эталона профильных карт,
  ФИО заявителя или самой рубрики (`scoring`).

Ключевое новое решение пользователя: **эталон в кейсах пока не
заполняется** — все текущие `seed/scenarios/pilot-112-*.json` останутся
с почти пустым `reference`. Но инфраструктура должна уже сейчас
поддерживать полный эталон, чтобы добавление его к конкретному кейсу
было последующей версией файла сценария, а не изменением конвейера
оценки. Второе решение: **отсутствие эталона у блока/штрафа — это
обычный ноль**, та же бизнес-логика, что и при эталоне, а не отдельный
статус `not_applicable`/`unavailable`/`needs_review`.

## Решение

### Рубрика v2 (`operator112/rubric-v2`)

Шесть блоков-критериев (`kind: deterministic`, статус `met`/`partial`/
`not_met`, `Score` — доля 0..1 для `partial`) и четыре штрафа
(`kind: penalty`, новое значение `rubric.schema.json`'s `kind`,
исключаются из нормировки `Score` и вычитаются из итога после неё):

| id | вес | что |
|---|---|---|
| `ADDRESS_FIELDS` | 35 | поля адреса против эталона, по полям, кроме `object`/`landmark` |
| `PROFILE_CARDS` | 25 | ожидаемые профильные карты, поровну между картами, доля верных ответов внутри карты |
| `CALLER_TOPICS` | 15 | темы, затронутые оператором в разговоре (словарь по ключевым словам/RE2) |
| `T_ANSWER` | 7.5 | норматив ответа на вызов (15 с) |
| `T_FILL` | 7.5 | норматив заполнения карточки (90 с), за вычетом ожидания ответа ИИ-заявителя |
| `DESCRIPTION_PRESENT` | 10 | описание со слов заявителя непусто |

| id | штраф | условие |
|---|---|---|
| `P_ADDRESS_REGION` | −10, один раз | страна ИЛИ субъект (регион/округ) не совпали с эталоном |
| `P_APPLICANT_NAME` | −5, один раз | ФИО заявителя раскрыто в разговоре, но не совпадает с эталоном |
| `P_SERVICES` | −5 за каждую | служба выбрана лишняя или пропущена относительно эталонного списка |
| `P_EXTRA_PROFILE` | −5 за каждую | создана профильная карта, которой нет в эталоне |

Веса блоков и точные нормативы/баллы полей лежат в `params` каждого
критерия (`rubric.operator112.json`), не зашиты в коде оценщика —
правки в будущем (например, после профильной приёмки) остаются
правкой контракта, а не пересборкой `internal/assessment/operator112`.
Прежняя ручная рубрика v1 (`INTAKE_COMPLETENESS`/`INTAKE_ACCURACY`/
`INTAKE_DISPATCH`, `kind: manual`) сохраняется как
`rubric.operator112.v1.json` — уже идущие/старые занятия на ней не
переоцениваются задним числом (ADR-013's rubric-version freeze).

### Сравнение с эталоном, не с транскриптом

Отвергнут первоначальный вариант (подстрочный поиск заполненного
значения по тексту разговора): он не различает верный и ошибочный
ответ, если хоть какое-то упоминание есть, и не имеет решения для
`card_only`/`incoming_call`, где разговора может не быть вовсе. Вместо
этого каждый блок сравнивает фактически отправленный снимок карточки
(`notification.card_snapshot`, а до оповещения — `final_card`, §"Что
проверяется" ниже) со закрытым эталоном сценария
(`intake112.reference`), расширенным этим ADR структурированными
полями адреса, ФИО заявителя, ожидаемыми ответами профильных карт и
альтернативными верными значениями.

### Правило «эталон отсутствует»

Эталон блока считается заданным, если в `intake112.reference` есть
хотя бы одно оцениваемое значение этого блока. Иначе — и это
центральное решение этого ADR — блок или штраф получает **обычный
ноль по той же бизнес-логике**, как если бы эталон был и обучаемый
все значения указал неверно:

| Блок / штраф | Эталон не задан | Эталон задан частично |
|---|---|---|
| `ADDRESS_FIELDS` | `not_met`, `score=0`, `explanation="эталон не задан"`; вес блока остаётся в нормировке | поле без своего значения в эталоне — `not_applicable` только внутри блока (не влияет на остальные поля этого же блока) |
| `PROFILE_CARDS` | нет `expected_types`/`expected_profiles` → `not_met`, `score=0` | ожидаемая карта без `expected_profiles[id]` → её доля блока — 0, не пропуск |
| `P_ADDRESS_REGION`, `P_APPLICANT_NAME`, `P_SERVICES`, `P_EXTRA_PROFILE` | штраф не начисляется (0 штрафных баллов), `explanation="эталон не задан"` | правила §"Штрафы" применяются к тому, что в эталоне есть |
| `CALLER_TOPICS`, `T_ANSWER`, `T_FILL`, `DESCRIPTION_PRESENT` | эталон не нужен — эти критерии эталон не используют вовсе, считаются как обычно |

`not_applicable` целого критерия остаётся зарезервирован за объективной
неприменимостью, не связанной с отсутствием эталона: `card_only` без
разговора (тема разговора неприменима), маркер `interruptions`/stop до
этапа (тайминг), закрытие до `notify_services` без снимка (профильные
карты/адрес всё равно оцениваются по `final_card` — см. ниже, они не
становятся `not_applicable` из-за этого). Смешивать «эталона нет» и
«критерий неприменим» запрещено: первое всегда даёт числовой 0 и
входит в нормировку, второе исключает критерий из неё.

Сиды `seed/scenarios/pilot-112-*.json` не меняются этим ADR. Там, где
у них уже есть `expected_types`/`expected_services` (`full_case`/
`card_only` кейсы) — это существующий частичный эталон и он
используется как есть; `ADDRESS_FIELDS`/`P_APPLICANT_NAME` там дадут 0
до отдельной работы по наполнению `expected_card`/`applicant_name`
(вне объёма этого среза — новая версия конкретного файла сценария).

### Что проверяется

Оцениваемый снимок карточки — `notification.card_snapshot`, если
`оповестить и сохранить` состоялось (ADR-023); если карточка закрыта
раньше (stop, `interrupted`) — `final_card`, последний известный
черновик. Это соответствует RFC-001 §10: сравнивать с тем, что реально
ушло службам, а не только с финальным черновиком, но не наказывать
обучаемого повторно, если оповещения не произошло вовсе — тогда
`final_card` уже отражает всё, что было сделано.

Legacy-маршрут (`intake_state.finale == ""` — items, созданные до
ADR-023, у которых нет `notify_services` вовсе, только старые
`dispatch_intake`/`complete_profile_case`) не может быть осмысленно
оценён этой рубрикой: снимка отправки в новом формате нет. Такие items
получают отдельный терминальный код отказа задачи —
`operator112_legacy_route` — вместо `auto rev=1`; ручная оценка
преподавателем остаётся доступна как обычно (RFC-001: «сбой LLM не
делает карточку недоступной преподавателю» — тот же принцип
распространяется на структурную невозможность посчитать правило).

### Рубрика выбирается по версии

`assessment.LoadRubric(exerciseType, version)` заменяет жёстко
зашитый `LoadDefault()`/`loaded112()` парой единственных версий:
занятие фиксирует `rubric_version` при создании (как ДДС уже делает),
`sealInputForItem`/`recordAutoTx`/`Get`/`CreateExpertRevision` грузят
рубрику именно этой версии, а не «текущую v2» — существующее занятие
на `operator112/rubric-v1` продолжает получать только ручную оценку
без автоматической постановки задачи (см. §"Постановка оценки").

### LLM-критерии — будущая v3

Эта рубрика не содержит ни одного критерия `kind: llm`. Проверка
полноты описания через LLM и содержательности свободного разговора —
следующая версия рубрики (`operator112/rubric-v3`), которая
добавляется после этапа 2 112-5b (замер W0, `llama-server`) — она
переиспользует ту же инфраструктуру `internal/platform/llm`, что уже
подключена для `caller.reply` (ADR-025), но как отдельный вызов из
`assessment.evaluate`, строго после закрытия карточки (ADR-003, без
изменений).

## Варианты

- Подстрочный поиск заполненного значения в транскрипте — отвергнут
  пользователем и автором плана совместно: не различает верный и
  ошибочный ответ, не работает без разговора, поощряет заполнение
  «наугад» полей, которые заявитель не называл.
- Особый статус `not_applicable`/`needs_review` для «эталон ещё не
  добавлен» — отвергнут пользователем явно («просто 0, бизнес логика
  как мы описали»): отдельный статус скрывал бы от преподавателя, что
  реального прогресса по кейсам без эталона в принципе не измерить,
  и требовал бы отдельной перенормировки веса блока, которую позже
  пришлось бы убирать при добавлении эталона — переусложнение ради
  переходного состояния.
- Отдельная рубрика на каждый кейс вместо общей v2 с параметрами в
  `params` — отвергнут: полностью ломает версионирование ADR-013
  («базовая рубрика по exercise_type, поправки — только через
  `reference.scoring`»), не даёт единообразно сравнивать разных
  обучаемых одного занятия.

## Последствия

- `internal/assessment/operator112` — новый пакет, пятое место, где
  реализуется `RuleEvaluator` (после `internal/assessment/dds`);
  подключается через `cmd/emsim/assessment_composition.go`'s
  `Registry`.
- `internal/content` расширяет `Intake112Reference`/
  `Intake112ExpectedCard` и валидацию импорта — уже сейчас, даже
  притом что реальные сиды остаются с пустым эталоном; это и есть
  «инфраструктура, готовая принять эталон позже» из требования
  пользователя.
- `internal/assessment`'s `RuleEvaluator.Evaluate` меняет сигнатуру на
  сырое evidence (`json.RawMessage`) + `content.ScenarioBody` вместо
  типизированного `training.EvidenceBody` — ДДС продолжает читать свою
  типизированную форму, декодируя её сама внутри `assessment/dds`,
  поведение не меняется.
- Отчётность (`internal/reporting`) получает колонки по блокам/сумме
  штрафов 112, независимые от колонок ДДС.
- Коммит-план реализации — `slice-112-6-plan.md`.
