# ADR-002. PostgreSQL как БД, очередь задач и шина; файлы на диске

Статус: accepted · 2026-09-17 · уточнён ADR-014 от 2026-09-18

## Контекст
Нужны: durable-очередь для LLM/STT/TTS/отчётов (поток по мере закрытия карточек; пропускная способность проверяется по RFC §11), pub/sub для SSE между процессами, хранение записей звонков и озвучки. Сервер один, интернета нет, администратор — техник УМЦ.

## Решение
- Таблица `tasks` с `FOR UPDATE SKIP LOCKED`, lease/heartbeat/fencing/retry/dead-letter (ADR-010). Постановка задачи — в той же транзакции, что и доменный эффект (transactional outbox бесплатно).
- `pg NOTIFY` канал `emsim_events` для уведомлений между `api`-экземплярами и от `worker` к `api`; внутри процесса — Go-канал. Payload NOTIFY — только идентификаторы; вызов в транзакции доменного эффекта. Получатель перечитывает данные; потеря LISTEN требует resync (ADR-007/014).
- Бинарники — файлы в `/data/blobs/<sha256[:2]>/<sha256>` + таблица `blobs (id, sha256, mime, size)`. Backup = `pg_dump` + rsync директории; автоматический запуск не реже раза в сутки.

## Варианты
- Redis (очередь + pub/sub) — ещё один сервис, ещё одна точка отказа и backup'а при достаточной для класса PostgreSQL-очереди; отвергнуто.
- Kafka/RabbitMQ — несоразмерно; отвергнуто.
- `bytea` в PostgreSQL для записей — раздувает БД и dump (1,5 ГБ/год), усложняет стриминг в браузер; отвергнуто.

## Последствия
- Единый backup и единая точка восстановления.
- Очередь опрашивается (poll 250 мс) — задержка старта задачи до 250 мс, приемлемо.
- При >1 `api` SSE-события проходят через NOTIFY (лимит payload 8 КБ — поэтому только id).
