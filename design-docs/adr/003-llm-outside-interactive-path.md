# ADR-003. Модели только до занятия и после карточки

Статус: accepted · 2026-09-17 · уточнён ADR-014 от 2026-09-18 · для 112
`caller.reply` уточнён [ADR-025](025-operator112-ai-caller.md) от 2026-09-25

## Контекст
Сервер: 6 ядер, 32 ГБ, без GPU. Скорость модели на целевом CPU пока не измерена; оценки tok/s и секунд не являются результатом benchmark. Заказчик [60:20–64:30]: «генерируйте заранее, не онлайн; обучаемые выбирают действия, модель потом оценивает; real-time не взлетит».

## Решение
LLM, STT и TTS вызываются **только** из `worker` в рамках задач: `scenario.generate`, `scenario.regenerate`, `voice.render` (до занятия), `stt.transcribe`, `assessment.evaluate` (после закрытия карточки). Во время работы обучаемого с карточкой ни один запрос не идёт к моделям. Фразы телефона и события — заранее отрендеренные файлы.

Все вызовы — через один порт `LLMClient.CompleteJSON(prompt, schema)`; ответ валидируется по JSON-схеме; невалидный — retryable failure.

## Варианты
- Онлайн-подсказки/диалог на LLM — не помещаемся по CPU при 30 РМ; отвергнуто.
- Маленькая модель (1–3B) для real-time — качество русского недостаточно для оценки; отвергнуто.

## Последствия
- Задержка оценки и время полного отчёта определяются замером, гарантия «к концу занятия» не установлена. UI показывает прогресс готовности и результаты правил.
- Отдельные пулы для коротких задач, LLM и STT; concurrency 1/2/4 сравниваются по throughput, качеству и отклику API. 15 задач в очереди не означают 15 inference одновременно (ADR-014).
- Задержка/недоступность моделей — деградация (needs_review), никогда не отказ занятия.
- Появление GPU ускоряет, ничего не меняя в архитектуре (профиль compose).
