# ADR-033. Поставка, часть 1: профиль класса с HTTPS, резервные копии, «Состояние», очистка аудита, удалённая модель, демо-стенд

Статус: accepted · 2026-09-28 · реализует часть ДДС-10 (`slice-planning-dds.md`), общую для ДДС и 112; уточняет RFC-001 §4.3, §9, §10 и ADR-008, ADR-029

## Контекст

ДДС-4, ДДС-5 и ДДС-8 ждут от заказчика структуру протокола классификации происшествий. На время ожидания берём часть ДДС-10, которая от неё не зависит и нужна к сдаче в любом случае. Сверка с кодом на 28.09.2026:

- api и worker публикуют порты только на `127.0.0.1` (`compose.yaml`), `COOKIE_SECURE=false`, Caddy нет. С других ПК класса к тренажёру не подключиться.
- `/admin/status`, `/admin/backup`, `/admin/tasks/{id}/retry` описаны в `openapi.yaml`, но не реализованы.
- Нет планировщика задач по времени и нет очистки `audit_log` (RFC-001 §9: хранение 6 месяцев). У `audit_log` нет отдельного индекса по `at`. В runtime-образе нет `pg_dump`.
- `internal/platform/llm.Client` не передаёт API-ключ.
- В `seed/` нет пользователей и рабочих мест.

Решения пользователя 28.09.2026:
- резервные копии в каталог хоста, хранить 14 копий;
- сертификат HTTPS выпускает внутренний CA Caddy;
- удалённая модель — OpenAI-совместимый API с `Authorization: Bearer`;
- нагрузочный прогон и W0 на целевом сервере, офлайн-пакет, документация и видео, импорт через админку (`/admin/import/*`) — в техдолг.

## Решение

### Профиль класса (`compose.class.yaml`)

- Overlay поверх `compose.yaml` добавляет сервис `caddy` (образ закреплён по digest, конфигурация `deploy/caddy/Caddyfile`): `tls internal` с `skip_install_trust`, `reverse_proxy api:8080`, редирект с 80 на 443. Имя или IP сервера задаёт `EMSIM_HOST`.
- В этом профиле для api: `COOKIE_SECURE=true`, опубликованные порты снимаются (`ports: !reset []`). Наружу открыт только Caddy.
- Базовый `compose.yaml` (демо на одной машине), e2e и CI не меняются: http на localhost, `COOKIE_SECURE=false`.
- Корневой сертификат CA хранится в томе `caddy-data`. `make class-ca` выгружает его, администратор один раз ставит его на ПК класса.
- `RequireSameOrigin` сверяет `Origin` с `Host`, Caddy передаёт Host без изменений, поэтому код проверки не меняется. SSE Caddy отдаёт без буферизации.

### Планировщик задач по времени

- `tasks.Scheduler` — Supervisor в роли `maintenance`, рядом с reaper и sampler. Раз в минуту проверяет расписания и после наступления слота ставит задачу с `DedupKey = "<kind>:daily:<YYYY-MM-DD>"`. Уникальность `dedup_key` исключает дубли при рестарте и при нескольких процессах maintenance.
- Время слота задаётся в часовом поясе `SCHEDULE_TZ` (по умолчанию `Europe/Moscow`, база поясов встроена через `time/tzdata`). Если процесс не работал весь день, пропущенный слот не догоняется.
- Ошибка тика логируется и не останавливает процесс, как у sampler.

### Очистка аудита (`audit.prune`)

- Пул `short`, ежедневно в `AUDIT_PRUNE_AT`. Удаляет строки старше `AUDIT_RETENTION_DAYS` (по умолчанию 183) пачками по 5000, каждая пачка в своей транзакции.
- Сама очистка пишет запись аудита (`actor_role: system`, число удалённых строк).
- Миграция добавляет BRIN-индекс `audit_log (at)`.

### Резервные копии (`backup.run`)

- Пул `report` (1 слот): бэкап долгий и не должен занимать короткий пул, в котором идёт `lesson.close`. Во время бэкапа сборка PDF ждёт.
- Состав копии: `pg_dump -Fc` (`db.dump`), архив блобов без `.staging` (`blobs.tar.gz`), `manifest.json` (sha256 и размеры файлов, версия схемы, время создания).
- Копия собирается в `.tmp-*` и атомарно переименовывается в `emsim-YYYYMMDD-HHMMSS/`. Недописанный каталог копией не считается. Хранятся последние `BACKUP_KEEP=14` успешных копий.
- Пароль БД передаётся `pg_dump` через `PG*`-переменные окружения, а не аргументом командной строки.
- В runtime-образ добавляется клиент PostgreSQL той же major-версии, что сервер (16).
- Каталог хоста — `BACKUP_HOST_DIR` (по умолчанию `./backups`), монтируется в worker. Одноразовый сервис с правами root выставляет владельца каталога (uid 65532).
- Расписание — `BACKUP_AT` (по умолчанию 03:00). Ручной запуск — `POST /admin/backup` и команда `emsim backup`.
- Восстановление — `scripts/restore.sh <каталог>`: сверка manifest, `pg_restore --clean`, распаковка блобов при остановленных api и worker. Процедура описана в README и проверяется интеграционным тестом «бэкап → восстановление в чистую БД».
- Отдельное хранилище в локальной сети (AR-04 в `docs/architecture/03-requirements.md`) остаётся за администратором: каталог хоста можно смонтировать на сетевой диск.

### Отметки живости и экран «Состояние»

- Таблица `platform_heartbeats (component, status, detail, checked_at)`. Через неё api узнаёт то, что видит только worker: api не подключён к сети `inference`, поэтому доступность модели (`/health` раз в 30 с) и свободное место в каталоге копий проверяет worker.
- `GET /admin/status` (пакет `internal/platform/status`, только `GroupAdmin`) показывает:
  - версию схемы;
  - задачи по видам и статусам;
  - модели;
  - свободное место под блобами и копиями;
  - `last_backup_at` и последние копии;
  - неудачные задачи (`failed`/`dead_letter`): id, вид, код ошибки, время.

  Полезная нагрузка и результаты задач не отдаются: администратор не имеет доступа к содержимому занятий (RFC-001 §9). Контракт расширяется полями `workers`, `backups`, `failed_tasks`.

### Повтор задачи администратором (`POST /admin/tasks/{id}/retry`)

- Общий `tasks.Store.Retry` разрешён только для `failed`/`dead_letter`. Увеличивает бюджет попыток, сохраняет id, `dedup_key` и монотонный lease-токен, возвращает задачу в `pending`.
- Вид задачи может задать свою проверку (`RetryGuard`):
  - `assessment.evaluate` — повтор запрещён, если у карточки уже есть auto или expert; без входа задача возвращается в `waiting` (RFC-001 §7.4);
  - `caller.reply` — повтор запрещён: ход уже закрыт finalizer'ом.
- Доступ — `GroupAdmin`. Черновая группа `GroupTasks` снимается.

### Удалённая модель

- `llm.Client` получает API-ключ и отправляет `Authorization: Bearer`. Ключ не попадает в логи, ошибки и ответы API.
- Переменные `CALLER_LLM_API_KEY` и `JUDGE_LLM_API_KEY`, запасная — общая `LLM_API_KEY`.
- `LLM_DIALECT=llama|openai`: в режиме `openai` не отправляются параметры, которые понимает только llama.cpp (`repeat_penalty`).
- Overlay `compose.remote-llm.yaml` отключает сервис `llm`. `bench-llm` работает без `/metrics` и `timings` llama-server.
- При удалённой модели реплики диалога с заявителем и описания заявителя уходят за периметр учебного центра. Поэтому режим включается только явно; по умолчанию модель локальная (ADR-029), RFC-001 §9 для базового профиля не меняется.

### Демо-стенд

- `emsim demo-setup` через `auth.Service`, идемпотентно, создаёт:
  - рабочие места `РМ-01…РМ-N`;
  - преподавателя;
  - обучаемых ДДС района, 03 и 112.

  Пароль берётся из `DEMO_PASSWORD`, значения по умолчанию нет. Существующим пользователям пароль не меняется.
- Запуск — сервис compose в профиле `demo` и `make demo`. Сценарий показа описан в README.

## Отложено (техдолг)

- Нагрузочный прогон (30 виртуальных обучаемых + монитор) и замер W0 на целевом сервере.
- Офлайн-пакет (`docker save`, модель, установка на чистую машину), документация `.docx`/`.pdf`, демо-видео.
- Импорт классификатора и билетов через админку (`/admin/import/*`); импорт остаётся командой `emsim import`.
- Модели STT/TTS в экране «Состояние» (поля остаются `null`, пока этих клиентов нет).

## Последствия

- Класс подключается к серверу по HTTPS; cookie сессии в профиле класса передаётся только по TLS. Голосу (112-8) это тоже нужно: браузер даёт доступ к микрофону только на защищённой странице.
- Администратор видит состояние системы, делает и восстанавливает копии без командной строки на ПК класса и может повторить упавшую задачу, не видя содержимого занятий.
- В runtime-образе появляется клиент PostgreSQL, что увеличивает размер образа.
- Пул `report` делят сборка PDF и бэкап.
