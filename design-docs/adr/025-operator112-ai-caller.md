# ADR-025. ИИ-заявитель 112 на интерактивном пути

Статус: accepted · 2026-09-25 · уточняет ADR-003 для `caller.reply` 112

## Контекст

ADR-003 запрещает вызывать LLM/STT/TTS во время работы обучаемого с
карточкой; модели вызываются только `worker`-ом до занятия
(`scenario.generate`, `voice.render`) и после закрытия карточки
(`stt.transcribe`, `assessment.evaluate`). 112-5a (ADR-024) уже вынес
ответ заявителя за пределы транзакции команды в отдельную асинхронную
задачу `caller.reply` (пул `caller`, вне интерактивного пути в смысле
ADR-004: обучаемый не ждёт эту задачу внутри HTTP-транзакции своей
команды), но реализовал порт `CallerReplier` детерминированной
заглушкой — вызова модели там не было.

Локальный прогон пользователя (`t-tech/T-lite-it-2.1:q5_K_M` через
Ollama, 20 сценариев, 280 ходов, `handoff/README.md` от 2026-09-25)
показал рабочую схему: regex-правила решают, какие факты можно
раскрыть, модель формулирует фразу. 112-5b подключает эту схему,
заменяя только реализацию `CallerReplier`; протокол ADR-024 (отмена,
барьер stop, поздний ответ, finalizer, попытки) не меняется.

ADR-003 в текущей форме не различает «вызов внутри транзакции команды»
и «вызов из воркера в ответ на команду, но до следующего действия
обучаемого» — оператор 112, отправив сообщение, ждёт ответа заявителя,
прежде чем содержательно продолжать разговор, хотя технически ждёт вне
HTTP-транзакции своей команды. Это не режим «генерируем заранее» из
ADR-003 (комментарий, доклад оцениваются после карточки) — заявитель
отвечает по ходу диалога. Требуется явное решение, разрешающее этот
конкретный случай, а не молчаливое расширение ADR-003.

## Решение

- **Только `caller.reply` 112.** Разрешение узкое: LLM можно вызывать
  из обработчика задачи `caller.reply` (`internal/training/operator112`)
  для сценариев с `caller_mode="free_text"` и заданным профилем
  заявителя. Все остальные виды моделей и все остальные `Kind`
  (`scenario.generate`, `voice.render`, `stt.transcribe`,
  `assessment.evaluate` и будущий `assessment.evaluate` для 112) — по
  ADR-003 без изменений: до занятия или после закрытия карточки. ДДС
  ограничение ADR-003 сохраняет в полном объёме — интерактивного
  ИИ-собеседника у ДДС нет и это решение его не вводит.
- **Модель — локальный сервис, без выхода в интернет.** OpenAI-
  совместимый HTTP `/v1/chat/completions` в изолированной docker-сети
  (та же топология, что ADR-003 предполагал для `llm`-контейнера);
  Ollama допустим только при разработке на Mac, у заказчика — только
  `llama-server` (добавляется после GGUF/замера W0, см.
  `slice-112-5b-plan.md`).
- **Гибрид «правила открывают — модель формулирует».** Какие факты
  доступны и раскрыты ли они уже, решает детерминированный
  regex-классификатор над транскриптом (см. `slice-112-5b-plan.md`,
  решение 1 и 5); модель получает только уже открытые факты и решает
  исключительно формулировку ответа. Модель никогда не решает, можно
  ли раскрыть факт.
- **Модели не передаются:** эталон (`reference`), рубрика, список
  подходящих служб, закрытые (нераскрытые) факты сценария, инструкции
  по оценке обучаемого. Промпт содержит только персонажа, уже открытые
  факты и историю разговора этого хода.
- **Таймаут и попытки.** Один вызов ограничен
  `CALLER_REPLY_TIMEOUT` (как и заглушка в 112-5a); `caller.reply`
  сохраняет `MaxAttempts=2` из ADR-024. Ошибка на первой попытке —
  обычный retry задачи. Ошибка на последней попытке — обработчик
  применяет нейтральную реплику-заглушку («Алло, вас плохо
  слышно… Повторите, пожалуйста.») вместо `HandlerFailure`, чтобы разговор
  не останавливался технической проблемой модели; полное исчерпание
  задачи (например, паника воркера) по-прежнему уходит в
  `Finalizer` → `failed`, как и в 112-5a.
- **Stop и поздний ответ — без изменений от ADR-024.** Ответ,
  посчитанный после `stop_cutoff_log_seq`, не применяется; ход остаётся
  `pending` в evidence. Отмена при удержании/завершении/срыве вызова —
  как в 112-5a.
- **Воспроизводимость.** Каждый ход, отвеченный моделью или
  нейтральной заглушкой при отказе, хранит `source` и `generation`
  (модель, версия промпта, параметры генерации) — RFC-001 §6
  «производные входы оценки тоже фиксируются» распространяется и на
  реплики заявителя, а не только на `assessment_inputs`. Повторная
  генерация одного и того же хода не считается восстановлением
  прошлого ответа — она может дать другой текст.
- **Ёмкость не заявлена до W0.** `CALLER_REPLIER=stub` — значение по
  умолчанию: поставка без модели ведёт себя как 112-5a. `llm` — явный
  опт-ин; сколько одновременных диалогов выдержит целевой сервер, не
  определено этим ADR — это отдельный замер (`slice-112-5b-plan.md`,
  этап 2).

## Варианты

- Оставить ADR-003 буквальным и не разрешать вызов модели по ходу
  разговора — отвергнуто: тогда 112-5b не может подключить ИИ-заявителя
  вообще, а пользовательский результат «поговорить с заявителем своими
  словами» (`slice-planning-112.md` §9) недостижим без интерактивного
  ответа.
- Расширить ADR-003 общим правилом «LLM можно на интерактивном пути,
  если асинхронно» — отвергнуто: слишком широко, открывает дверь для
  вызовов моделей из любой команды ДДС или 112 под предлогом
  асинхронности; узкое разрешение только для `caller.reply` 112 легче
  проверить и отозвать.
- Синхронный вызов модели внутри транзакции `send_caller_message` —
  отвергнуто ещё в ADR-024: держит `items` под блокировкой на время
  вызова модели, чего требования ADR-004 (короткие транзакции команд)
  не допускают.

## Последствия

- `internal/platform/llm/` — минимальный клиент, переиспользуется
  `caller.reply` (112-5b) и будущим `assessment.evaluate` 112 (112-6);
  оба вызывают его только из worker.
- ADR-003 дополняется ссылкой на это уточнение (см. правку файла);
  сам текст ADR-003 не меняется — решение остаётся в силе для всего,
  кроме `caller.reply` 112.
- Недоступность модели во время `caller.reply` — деградация с явным
  `source="fallback"`, не отказ упражнения (тот же принцип, что ADR-003
  §«Последствия» уже фиксирует для LLM/STT в целом).
- Требование замера W0 и выбора `llama-server`/GGUF у заказчика
  остаётся открытым до `slice-112-5b-plan.md`, этап 2 — этот ADR его не
  закрывает.
