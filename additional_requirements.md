# Дополнительные требования и предлагаемые решения

| Требование | Что предлагаем |
|---|---|
| Учет результатов обучения и прогресса операторов | Привязать каждый `run` к оператору; хранить историю прогонов и результатов, прогресс считать по накопленным данным. |
| Аутентификация и роли пользователей | Таблица `users` + роли `operator / instructor / admin`; авторизация через JWT/session, связь оператора с его `runs`. |
| Защита каналов передачи данных | HTTPS/TLS между клиентом и API через Caddy/Nginx; внутренние сервисы — в закрытой сети. |
| Резервное копирование не реже 1 раза в сутки | Ежедневный `pg_dump` PostgreSQL + хранение копий во внешнем S3/Object Storage + процедура восстановления. |
| Работоспособность на заданных программно-аппаратных платформах | Backend и UI не завязывать на GPU; LLM вынести в отдельный inference-сервис с заменяемым endpoint. |
| Локальное использование LLM | Patient Simulator и LLM-as-Judge запускать на отдельном локальном/GPU inference-сервере через HTTP API. |
| Поддержка нескольких одновременных пользователей | Каждый пользователь работает в отдельном `run`; состояние хранится в БД, нагрузка на LLM регулируется очередью `tasks`. |
| Поддержка удаленного контроля учебного процесса | Отдельный Instructor UI: активные/завершенные прогоны, результаты, история, transcript и действия оператора. |
| Время отклика интерфейса ≤ 2 секунд при нагрузке до 100 пользователей | Быстрые API-запросы; тяжелые LLM-операции выполнять асинхронно через `tasks`, результат возвращать через WebSocket/SSE. |
| Не менее 20 одновременных сессий | Изолированные `runs` + очередь `tasks` + пул Dialogue/Judge workers; ограничивать параллелизм inference-сервера. |
| Задержка передачи голоса (VoIP) ≤ 150 мс | Голос вынести в отдельный realtime-канал на WebRTC/RTP + Opus, не передавать аудио через обычный REST. |
| Восстановление после сетевых сбоев до 30 секунд без потери данных | Хранить состояние сессии в PostgreSQL; reconnect клиента + восстановление по `run_id`; использовать idempotency для повторных запросов. |
| Скорость записи в БД ≥ 100 операций/сек | PostgreSQL + connection pool (`pgxpool`/аналог), короткие транзакции и корректные индексы; подтвердить нагрузочным тестом. |
| Формирование аналитических отчетов ≤ 30 секунд | Сохранять готовый `run_result`; отчеты строить по уже агрегированным данным, без повторного запуска LLM. |
| Буферизация данных при временных сбоях | Client-side очередь/буфер неподтвержденных действий + retry после reconnect; на сервере — persistent task queue. |
| Проверка выполнения требований по производительности | Нагрузочные тесты: `k6` для API, `pgbench`/интеграционные тесты для БД, fault-injection для сетевых сбоев. |
| Уровень сложности кейса | Добавить поле `difficulty` к сущности кейса/сценария (`easy / medium / hard` или шкала); использовать при выборе и назначении сценариев. |
| Аудит всех действий пользователей | Добавить append-only `audit_events`: кто, что, когда и над какой сущностью сделал; логировать входы, действия оператора, преподавателя и администратора. |
| Хранение журналов безопасности не менее 6 месяцев | Хранить audit/security logs минимум 6 месяцев; при росте объема — партиционирование PostgreSQL по времени и retention policy. |
| Поддержка Windows 10/11 и Ubuntu 20.04+ | Клиент реализовать как веб-приложение; серверную часть разворачивать в Docker/Linux без зависимости от ОС пользователя. |
| Поддержка Chrome, Firefox и Яндекс.Браузера | Использовать стандартные Web API; добавить smoke/e2e-проверки минимум для Chromium и Firefox. |
| Поддержка IP-телефонии через локальный SIP-сервер | Интегрировать отдельный VoIP-модуль с локальным SIP-сервером (например, Asterisk); аудиопоток не проводить через основной REST API. |
| Поддержка вертикального масштабирования | Компоненты должны работать при увеличении CPU/RAM/GPU без изменения бизнес-логики; не закладывать жесткие ограничения на ресурсы. |
| Возможность горизонтального масштабирования | Backend делать stateless, состояние хранить в PostgreSQL; запускать несколько backend/workers за балансировщиком, используя общую persistent queue. |
| Завершение занятия/задачи Преподавателем | Добавить действие `stop/finish` для активного занятия: корректно перевести `run` в terminal-state, остановить/отменить связанные задачи, сохранить уже накопленные данные и не допускать падения системы. |
| Выбор источника карточек событий преподавателем | Для второй задачи хранить базовый набор карточек и поддержать выбор набора из: системных/сгенерированных карточек, карточек, сформированных обучающимися, или их смешанной выборки. |
